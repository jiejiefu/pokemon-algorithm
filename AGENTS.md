## 2. Directory Architecture

```
pokemon-algorithm/
├── assets/          css/ · js/ · data/ · cries/ · glbs/ · images/
├── docs/            incidents/ — the receipts behind §3, one file per area
├── scripts/         verification: check_*.mjs · test_check_*.mjs · lib/
│                    data pipeline: *.py   (two layers, explained below)
└── data-sources/    raw CSV/XLSX + per-id provenance (never fetched at runtime)
```

`assets/video/` holds the nine generated hero loops (8.9 MB) and the nine stills cut from them (1.1 MB). **All eighteen are tracked** and `index.html` mounts one of each — §3.Z. `make_hero_video.py` regenerates both.

**No `package.json`, no `node_modules`, no build step.** Zero npm dependencies is a property, not an oversight: Node is invoked only as `process.execPath` and every helper lives in `scripts/lib/`. **There is also no CI** — nothing under `.github/workflows/`; the suite is run by hand.

**9,066 of the 9,385 tracked files are binary** (7,062 PNG, 2,000 OGG, plus 4 SVG/GLB) and 95 are code (67 `.mjs`, 28 `.py`). `assets/data/` holds 14 JSON tables and is the single source of truth for every page.

**Ten files under `assets/js/` and `assets/data/`, plus the nine videos under `assets/video/`, are GENERATED and must never be hand-edited** — a key added by hand has a lifetime of one regeneration, and two of the three life.html data defects were exactly that:

Two directories are outside `assets/` on purpose: `data-sources/sv-sources.json` records which host each SV PNG actually came from and is deliberately never served (§3.E), and `docs/incidents/` holds §3's receipts so AGENTS.md can stay small.

**`scripts/` is TWO unrelated toolsets, and the filename prefixes are the only thing separating them.** 68 files are verification — 42 `check_*.mjs`, 17 `test_check_*.mjs` mutation harnesses, 1 standalone test (`test_cry_overlap.mjs`, a manifest entry in `cry-page`) and 8 in `lib/` — driven by `check_all.mjs` and the §4 cache. The other 28 are `*.py` generators and scrapers, run **by hand in the order §5 gives** and never by the suite. They share one directory because nothing couples them but the files they generate, and **splitting them is not free**: a subdirectory each means editing ~100 path strings, 24 of them functional and 14 of those the manifest's own `inputs`, plus one harness that copies a `.py` into a fixture at a fixed relative path. A checker and its harness have to stay put regardless — every harness names its checker by path and imports `./lib/` relatively — which is the same reason `checks/` and `harnesses/` would be the wrong split despite being the obvious one.

**`scripts/lib/` is shared and small on purpose** — `negative.mjs` is the one definition of what "caught by" means, `pool.mjs` the one worker pool (§3.G7), `cdp-port.mjs` the one place a Chrome path and debug port live, `png.mjs` builds its own test PNGs, `mute-tap.mjs` silences audio before any page script, `record-inputs.cjs` proves §4's input lists, `tmp-trees.mjs` is the one registry of temp trees so an interrupted run cannot leave one behind (§3.J), and `cdp-until.mjs` is the one poll-a-page-predicate loop both browser checkers wait with. Editing any of them invalidates every cache entry, which is why they are hashed into every key unconditionally.

## 3. Key Technical Conventions & Invariants

Each subsection below is a **rule**, the **shape of the defect** it came from, and the **checker that guards it**. The narrative and the measurements are in `docs/incidents/`, one file per area, reachable from each section's Background line.

**Four of the twenty-five rules are ENFORCED BY NOTHING, and that is worth knowing rather than discovering:** §3.A (routing and slugs), §3.C (contrast), §3.G5 (suite cost) and §3.G7 (the pool). A rule with no `Guarded by:` line below is not an oversight in this file — it is the §3.G1a shape, where 170 static and 43 CDP checks stayed green on a visibly broken page because they asked whether the prose EXIST rather than what it claims. If you touch one of those four, the evidence is whatever you measure yourself. **§3.J was the fifth and is now partly guarded** — its one numeric claim is checked by `check_tmp_prefixes.mjs`, and the rest of the section (the sweep itself, orphan cleanup, the `tmp-trees.mjs` registry) is still prose.

### A. Routing & Slugs
- **Local & GitHub Pages URLs**: Internal navigation uses query parameters (`detail.html?slug=bulbasaur` or `color.html?slug=bulbasaur`).
- **Nidoran Disambiguation**: `nidoran-f` (#029) and `nidoran-m` (#032) are distinct slugs. A bare `nidoran` slug is strictly disallowed and must not resolve.
- **Form Links**: Alternate forms link back to their base species detail page.
- **detail ⇄ color Reciprocity**: both pages must build their cross-page URL from the one canonical helper — `pokemonDetailUrl()` in `shared.js` and `paletteUrl()` in `color-palette.js`. **Never assemble either URL by hand or by string-replacing `detail.html`**: `color.html` deliberately does *not* inherit detail's clean-URL contract, so the two shapes can diverge and a derived string breaks the day either gains a path segment.

**Background:** [`docs/incidents/page-defects.md#a`](docs/incidents/page-defects.md#a)

### B. Color Extraction & MMCQ System
`assets/data/color_palettes.json` is generated by `scripts/extract_color_palettes_mmcq.py`: a 6-colour MMCQ partition sampled from 96×96 front sprites (alpha ≥ 200), with synthetic centroids **snapped** to the most frequent real pixel in each bounding box. Shares are global pixel frequencies across the sprite, so they sum < 100% (median ~71.95%). Exactly 3 palettes have 5 colours instead of 6 (#201 Unown, #643 Kartana, Bulbasaur shiny) — **never pad these artificially.** `color-thief` is credited for the algorithm; `pokemonpalette` for the colour scales and UI concepts.

**Guarded by:** `check_outfit_page.mjs` re-derives all 2,050 palettes through `mmcq.js` and requires byte-equality.

**Background:** [`docs/incidents/color.md#b`](docs/incidents/color.md#b)

### B1. `colors-generator.html` Is Not A Smaller `color.html`
The two colour pages share a component library (`paletteGridHtml`, `paletteStripHtml`, `.cp-cell`, `.cp-strip`) but **not a layout**: one *reports* a species' measured palette, the other *generates* a theme from a colour you supply.

- **Five sections were DELETED, not merged** (對照·實測色盤 / 生成明暗階 / 套用展示 / 生成組成 / 匯出主題). Two copies of one species' palette is duplication, not comparison. **This page's job ends at the generated palette** — the ramps, the showcase and theme tokens are `color.html`'s.
- **The page's own copy must not describe what was removed.** The meta description and intro both promised 「生成明暗階、套用展示」 after those sections were gone. A search-result summary and the first paragraph are the two places a reader is most likely to believe, and no shape check reads either.
- **`generatedRows()` IS the input colour plus the matched species' real colours** — the generated palette *is* the measurement whenever the input is that species' primary, which is the default landing state.
- **`assets/css/colors-generator.css` exists so this page's rules are not `color.html`'s problem.** Every rule is `cg-`-prefixed and mounted only here. **Never edit an existing `.cp-*`, `.sc-*` or shared token for a generator-only need — add a `cg-` rule.**
- **The 24-cell legendary grid pins the species, not just the colour.** `#FFFFFF` is the primary of **29** species, so re-ranking white would present a Wingull's palette under a card saying Reshiram. `matchOf(id, hex)` therefore builds the record with `rank: -1` — a pin did not win a competition — and the eyebrow reads 你選的, not 最接近. A pin survives re-ranking **only while the input is still one of that species' own six colours**. The grid is built ONCE in `init()`; only its highlight moves, because re-rendering throws away 24 buttons and leaves every reference pointing at detached nodes, which do not bubble.
- **The colour field speaks three notations and the toggle is display only.** `parseColorInput()` accepts HEX/RGB/HSL regardless of what is showing, because a toggle that filtered input would split the typed path from the paste path. `inputFormat` never round-trips through the text — `hsl(180,44%,40%)` reads back as `#399393` — **so flipping the toggle would restate the colour and every number on the page would then describe one the reader never chose.** Three states: parseable commits, a possible prefix says nothing (`hsl(18` is the fourth keystroke), neither flags it and **leaves the previous result on screen**. Ranges are strict, never clamped. The format note appears only on error.

**Expect this shape on any short element id:** every id is a named property of the document, so a bare `scale` in `color.html` is `<div id="scale">`. A missing `const` is not a `ReferenceError` when the document already owns the name, and a `Map`-style lookup on a DOM node answers `undefined` rather than throwing, so any `obj[key] || fallback` quietly becomes `fallback` for every key.

**Guarded by:** `check_color_match.mjs` (220 checks, asserts the ABSENCE of the five removed sections, their containers, their leftover code and their dangling ids) and `check_color_page.mjs`; 28 + 20 mutation cases.

**Background:** [`docs/incidents/color.md#b1`](docs/incidents/color.md#b1)

### B2. Three Colour Namers, One Chroma Gate
`color.html` prints two of them **side by side for the same hex**: the prose is `describeHex(primary)`, the swatch list is `chineseColorName(hex)`. Before the gate they disagreed on **97.6% of primary colours** — and each was separately wrong about greys. Arceus #493's primary `#e6e6ee` has max−min = **8 of 255**, a grey; `describeHex()` read hue 240 and lightness 91.8 and never looked at saturation, so it said **淺藍**, while `chineseColorName()` ran a 100-entry nearest-neighbour over RGB and said **薰衣草紫** (`#E6E6FA`, 12 away in one channel). The page said both.

**Every namer is gated on `chroma()` = max−min, below `NEUTRAL_CHROMA = 16` → `neutralName()`.** Measured on all 12,297 corpus swatches: `describeHex` renamed 1,620, `chineseColorName` 2,387, `colorTemperature` 178 (now all `neutral`), and **0 chromatic swatches changed**.

- **Chroma is absolute and must never be HSL saturation.** `s` is a ratio against lightness, so `#fffff6` measures **s = 100%** while being nine channels from grey — and near-whites are the largest grey bucket (白: 698 of the 2,387). `#e6e6ee` is the mirror image at s = 19%. **Refactor the gate onto `s` and every near-white flips from grey to a loud colour name.**
- **The threshold is in a gap, not merely low.** The corpus chroma histogram is empty between the grey cluster and the coloured one, so **16 through 31 all behave identically**; 32 is where it starts eating. That is why raising it cannot be caught by a "greys are named greys" check.
- **`describeHex()` on a pure grey returned 紅, not 白**, because `max === min` leaves `h` at 0, the first bucket in `hueNames`. That is 1,510 of 12,297.
- **Nearest-in-RGB will always match a grey to a tinted name**, because an entry 8 away in one channel beats every 淺灰 that is 20 away in all three: `#414141` came back **墨綠**.
- **`灰白` exists because 白色 would be a false claim** — `#e6e6ee` is 92% lightness and is not `#ffffff`.
- **`chineseColorNameWithEn()` is gated identically and returns the zh-only grey name** — pairing 灰白 with *Lavender* would assert the exact claim being corrected. It is on no colour page today, which is precisely why it needs its own case.

**Expect this shape when a guard can only be satisfied vacuously:** raising `NEUTRAL_CHROMA` to 255 satisfies all three "must not be chromatic" assertions *and* the demotion check at once, because there are then no chromatic swatches left. The detector has to be an assertion about colours that ARE still chromatic.

**Guarded by:** `check_color_palettes.mjs` + 9 mutation cases against a scratch copy of the module (the 11 pre-existing cases mutate the palette *data*, which cannot reach this code at all).

**Background:** [`docs/incidents/color.md#b2`](docs/incidents/color.md#b2)

### C. Contrast & Accessibility Rules
- **Color Contrast (WCAG AA)**: 4.5:1 for standard text, 3:1 for large text and UI components.
- **Measurement Method**: verify contrast by sampling decoded screenshot pixels via Canvas/CDP, **not** via `getComputedStyle()` — which misses alpha blending, backdrop filters and radial gradients.
- **Typography**: CJK-first stack in `--font-sans` (`PingFang TC`, `Noto Sans TC`, `Microsoft JhengHei`).
- **Theme Switching**: handled inline in `<head>` before first paint; toggling fires `themechange` for Canvas redraws.
- **Reduced Motion**: honored across CSS and JS — sprites snap to target coordinates instead of lerping.

**Background:** [`docs/incidents/page-defects.md#c`](docs/incidents/page-defects.md#c)

### D. Type Profiles & Scoped Translations

### E. Scarlet/Violet Artwork & Provenance
`assets/js/sv-index.js` is generated by `scripts/extract_sv_index.py` from the PNGs actually on disk. **It is not a list of what exists upstream, and it must never be hand-edited.** `assets/images/scarlet-violet/` holds 1,225 PNGs (the 1,025-ID roster plus 200 unclaimed variants); unclaimed files are counted and reported but never added.

Artwork is fetched by `scripts/fetch_sv_sprites.py`, **PokeAPI first**, falling back to InfoPoke only when the primary host returns no valid PNG — the fallback exists because PokeAPI's SV set is incomplete, so it is not a second source of truth. **The frontend credits PokeAPI only**; `types.html` must not name the fallback anywhere a reader can see. The real per-file answer lives in `data-sources/sv-sources.json`, deliberately outside `assets/` so it is never served.

The roster is complete today, so the stand-in path is dormant: `hasSv()` is true for every species and `.chip-thumb.is-sub` is never applied. **The code stays** so a future upstream removal degrades to the 96px sprite floor instead of a broken image.

**`move.html` draws them at 56px with `object-fit: contain` AND `object-position: bottom`, and that is where §3.AA's 25% number is deliberately NOT used.** The SV set is 120×112 and its subject is BOTTOM-ANCHORED with the empty space above; the 96px sprite is uniformly framed. Measured over 28/56/96px and three alpha thresholds, the SV subject sits **25.0–26.3% of the box low** against the sprite set. `types.html`'s `.chip-thumb.is-sv` corrects it with `translateY(-23%)`, and **that correction must not be copied here**: types.html's chip puts the thumbnail and the name on ONE line, so the offset lines the two up. `move.html`'s card puts the image on its own row above the name, there is nothing to line up against, and the bottom-anchored framing is what the page wants. The bottom alignment is therefore achieved by `object-position: bottom` rather than by moving anything — which is also why `width`/`height` alone would be wrong: that stretches the art 6% horizontally AND scales it to fill the box, lifting the subject 3.7px off the card's own baseline. **`contain` without `object-position` passes an assertion about the first and fails this page anyway**, so the two are always asserted together.

`image-rendering` is **absent** from `.mv-learner img`, and that is a correction rather than an omission: the house convention is `crisp-edges` and it appears only on **upscales** (`shared.css:947` draws the 96px sprite at 140px). Both art sets here are drawn **down** — 96→56 and 120→56, by non-integer factors, where nearest-neighbour drops pixels unevenly and reads worse than smooth. The rule previously said `pixelated`, which is the legacy alias for the same thing with the same problem one declaration further from the project's naming.

**Guarded by:** `check_sv_index.mjs` + 15 mutation cases; `move.html`'s half of the pair by `check_moves_page.mjs` and 4 mutation cases, and its RENDERED half by `check_moves_page_browser.mjs`, which measures the subject's gap to the card's bottom edge off the live canvas rather than reading `object-position` back — `bottom` is the authored keyword and `getComputedStyle` returns `50% 100%`, which is §3.G1a's pixel check in a property instead of a colour.

### F. Cry Audio — `gb-apu.js` Is Transcribed, Not Reasoned
`assets/js/gb-apu.js` re-synthesises pokered's 38 base cries. It is a pure module with no DOM, Web Audio or fetch, which is the only reason its claims are checkable. **It is verified against the reference's own OUTPUT, not against a description of it** — `gen1_conformance.json` holds, per species, the output length plus 48 sampled values of the 8-bit form the reference page's Download button produces, generated by driving that page in headless Chrome. Current result: all 151 lengths match exactly, 98.7% of sampled values are byte-identical, every remaining one within one 8-bit step.

*This distinction is the single most important thing in this section.* Six bugs had the APU confidently disagreeing with the reference while **agreeing with every other file in the project**, because every assertion compared it to a *description* — and a description can be wrong in ways that are self-consistent. **Nothing short of comparing output found any of them.**

- **The length parameter is the stored byte MINUS `0x80`, not its signed reading.** Reading it signed gives a multiplier `0x80` larger, making every note **1.5× too long**.
- **The duty register holds the PACKED byte**, not the pattern array — the reference reads `duty & 3`, so an array coerces to `NaN` then `0`, silently selecting the 12.5% window on every note whose low two bits are not `00`. The two channels whose low bits happened to be `0` matched by luck, which is what made this look like tuning rather than a bug.
- **The mix is NOT peak-normalised.** Three channels at a third each cannot clip; normalising only rescaled every cry and made a soloed channel as loud as a full one.
- **Every register is in samples at the Game Boy's clock and each must be scaled to the output rate — including the noise LFSR clock, which was not.** At 65,536 Hz the LFSR ran once per 512 *output* samples: 128 Hz where the hardware means 2,048. The symptom was a cry correct in every respect except that **it had no hiss in it** — 76 zero crossings per second against the reference's 1,533.
- **…and that is precisely what a native-rate conformance comparison is blind to.** At 1,048,576 Hz the conversion factor is exactly 1 and the bug is a no-op. **So the rate-dependent checks are rate-independent by construction: the same species must report the same noise clocks and render the same grain at 65,536 and at 1,048,576.** Expect this shape: a quantity that only matters on the way to the speakers can only be checked on the way to the speakers.
- **The master volume has been removed rather than checked.** `sliderToMaster()` mapped a 0..10 page slider onto the channel scale's 0..15, which was a conversion between two numbers that were already the same unit, so there was nothing for it to be right about. The page now presents 0..15 directly and defaults to 3.
- **`sound_loop` IS applied** (the reference's "unsupported" label refers to its UI, not its data), `count` is the number of *times* the block plays, and loop targets are stored as `"Ch5"` rather than literal labels.
- **The ring-out is bounded only where the envelope can never empty.** A sweep of `0` means it never does, so 16 frames is the bound there. Bounding *every* note is wrong and was: a legitimate tail is 240 frames at the largest sweep, and a flat 16-frame cap silently truncated seven species. **Those seven were then recorded as a "known set" on the reasoning that a tolerance beat a red test** — covering up a bound that would equally have hidden a truncation twice as large. A named exception list is for upstream quirks you cannot fix, never for your own truncation.
- **The synthesis rate is 65,536 Hz, not the real 1,048,576**, because Web Audio caps a buffer at 96,000. The ratio is exactly 1/16, so nothing drifts.

**Background:** [`docs/incidents/cry.md#f`](docs/incidents/cry.md#f) — including all six documented failures (per-quarter-period duty rotation, continuously-decaying envelope, time-stretched noise, single-field noise rate, no ring-out, byte-minus-0x80 length), each written wrong first.

**Guarded by:** `check_gen1_apu.mjs` (92 checks) and `check_gen1_cries.mjs` (40 checks). `test_check_gen1_apu.mjs` (39 mutation cases) is **deliberately not a manifest entry** — see §4.

### G. The Two Cry Pages
Driven over CDP because they make claims no static checker can. **A playback cursor's guard must be `!== null`, never `> 0`:** `AudioContext.currentTime` reads exactly `0` on the first play, so `startedAt > 0` reported "not started" for the entire first playback and the cursor never appeared.

- **The waveform is cached in an offscreen canvas**, bound with `const` from the first line. There is no "get the visible context, then reassign it to the cache" step — which is how `cries.html` threw a TypeError instead of drawing.
- **`cryPlayer.play()` resolves when a cry ENDS**, so a caller had no way to know when playback began; it takes an additive `onStart` hook carrying the duration and the clock reading.
- **Both pages share ONE autoplay switch, and it must never fire on load** (`assets/js/cry-autoplay.js`, one module rather than two copies). On `cries-gen1.html` the flag is a *parameter* because `select()` serves boot and clicks alike; on `cries.html` it is a read inside two click handlers, so the check counts call sites on comment-stripped source.

So `scripts/lib/mute-tap.mjs` is injected **before any page script** and replaces `AudioContext.destination` with a gain node at zero, asserted by reading the live `AudioParam` rather than a value recorded at install time, so the question answered is "is the output muted *now*".

- **A filter and a scroll position are different quantities and must not share a field.** `cries.html` had one `state.gen` serving as both, so 第 1 世代 asked for 60 cards out of all 1,025 and showed exactly what the unfiltered page showed.
- **A checker that presses play must CONFIRM the press landed**, because a page that re-renders a control's markup makes the captured node detached, a detached node does not bubble, and the click is a silent no-op — which surfaced as a flake (`x=669` idle, `x=696` under load) that would have been "fixed" by widening a tolerance.

### G1. The Spectrum Page — A Port That Is Checked Against Its Own Extractor
**No spectrogram is stored.** `analyze_cries.py` already computes the band to get its MFCC, so the spectrum is one function away; a stored bank would be ~2.3 MB and would go stale on every re-encode. The second reason is that **a port can be checked against the thing it ports**; a stored image is a claim.

- **`analyze_cries.py`'s `resample()` has TWO BUGS, recorded rather than fixed, because fixing them moves the stored table.** It scales by `n_out / n_fft` where zero-padding does not change `X`, so the amplitude-preserving scale is **1.0** — a 100 Hz tone resampled from 32,728 Hz comes back at 0.1465 of its amplitude. And it keeps `n_out / 2` bins of an `n_fft`-point transform, so its top kept bin sits at a **duration-dependent** frequency (4.1 kHz for a 0.7 s signal, against the 8 kHz a resample to 16 kHz must keep). Measured cost: **31 of 34 features have a median relative difference of `0.00e+00`**, because the cries barely use the top of the band. **`m0` alone moves systematically**, by exactly `log(n_out / n_fft) · √26` — about a quarter of `m0`'s variance is a function of how long the file is, and `cries.html` standardises `m0` before its search.
- **The module does NOT copy either bug.** It exports `UNCOMPARABLE = [peak, rms, m0]` and `M0_SCALE_OFFSET = √26`, and the checker asserts the m0 relationship as an **IDENTITY rather than a tolerance** — satisfied by exactly one relationship between the two numbers. A tolerance would have been satisfied by a mutation whose own difference is under 5%.
- **`UNCOMPARABLE` HAS TWO CAUSES and the page says so in two sentences.** `peak` and `rms` are a *limit of the browser* (measured at the true source rate, which `decodeAudioData` makes unrecoverable); `m0` is a *defect upstream*. Conflating them tells a reader to distrust a tool when the tool is right.
- **The page reports five features and not a relative difference for the other 29.** Across the 31 comparable features the browser and `cry_features.json` differ by a **median 5.5%** and by **1,181%** on the worst — and that worst is an `ms` column whose stored magnitude is about 0.002. The five reported are `dur`, `zcr`, `centroid`, `rolloff85`, `flux`. **`flatness` was in that set on the reasoning that it is a ratio bounded by 1 and therefore stable, and measured 31%** — it is scale-invariant and ill-conditioned, a ratio of two nearly equal numbers. **That is the second time in this project a property which sounds like a guarantee turned out to be an unrelated one.**
- **The live curve is a second measurement, and the caption says so** — 1024 *linear* bins at the *device* rate over a 2,048-point window with smoothing 0.3, folded into the same 26 mel bands. It answers 「where is the energy *right now*」 at 60fps, which an offline grid cannot do at all.
- **THE REVEAL IS NOT A STREAMING ANALYSIS, and the intro says so.** The whole spectrogram is computed before the reader presses play; playback uncovers one set of pixels.
- **The plot is NEAREST-NEIGHBOUR on both axes, and the blockiness IS the resolution** — 10 ms on a fixed hop, so a 0.18 s cry really does put ~55 pixels between two measurements. **The colour ramp is deliberately theme-INDEPENDENT**, because re-mapping a scale per theme would mean the same number in the same cell reading as two different things.
- **The live line and fill are the species' own `rgb`, lifted only as far as the plot ground requires** (`assets/js/species-ramp.js`). **The floor is 3:1 because this is a GRAPHICAL OBJECT, and 68 of 1,025 species need it.** **「黑色系寶可夢看不見」 is the wrong diagnosis**: the four worst are *desaturated, not dark*, and 197 species (19.2%) have a grey average colour altogether — the same `chroma()` gate as §3.B2. **`contrast` must be `shared.js`'s own, passed in, never re-derived** — a luminance written into `species-ramp.js` would disagree with every contrast figure in the project.

**Background:** [`docs/incidents/cry.md#g1`](docs/incidents/cry.md#g1) (including §3.G1a: a stray `</div>` auto-placed seven children as four rows while **170 static and 43 CDP checks stayed green**).

### G2. The Header Is Not One Thing
Two defects produced a visibly broken page with **no console output, no failed request and no exception** — because the header's contents are owned by `shared.js` at runtime, so hand-written markup in those containers is a duplication question, not a style question.

- **A bare `class="header"` is not a missing-style page — it is a valid class that renders the column layout.** The row layout comes from a *separate* rule listing six modifier classes, so a page carrying only the base class falls through and every other nav check passes on it. Measured: the header grew 55px → 98px and the nav overlapped the theme toggle. **Expect this shape whenever a base class is the mobile layout and a modifier supplies the desktop one** — a bare base class is a valid, rendering, wrong page.
- **The theme toggle's own icons are injected, and the runtime's guard is the trap.** `initThemeToggle()` adds its pair only `if (!btn.querySelector('.icon-sun'))`, so a page hardcoding a *differently-classed* pair satisfies nothing: the guard is still true, the canonical pair is injected *as well*, and the button ends up with four children in a 34px grid box, one painting outside it. **Leave the button empty and let the runtime own its contents**, exactly as the nav container is left empty.

### G3. Race Mode — Six Lanes, and the One Shape That Renders Nothing
It shipped with **every lane blank** and no console output, the same family as §3.B1's bare `scale`: **a bare name that resolves to the module's variable instead of the caller's.**

- **`paint()`, `ring()` and `sweep()` all closed over the module-level `ctx`**, the single-mode canvas. `frameRace()` cleared `lane.ctx` then called `paint()`, which drew 130 sprites a frame into a canvas `setMode()` had set `hidden`. All three helpers now take the context and timestamp from the caller, and `sweep()` returns whether it is *still running* so the caller clears its own field.
- **Count ink by ALPHA, and let the assertion return false.** Measured over 5 layouts × 4 sizes with real sprites, min ink per lane was **24,573 → 110,893** — a FLOOR, not a bound, because sprites are mid-lerp on every frame.
- **The lane layout is `data-lanes` on the container, and it is spelled out rather than derived** — 4 lanes is 2×2, *not* 3+1, and five's `span 3` on its last two lanes is positional, which is why `buildRace()` **appends** `.al-result` rather than prepending it.
- **`align-content: stretch` is load-bearing, not cosmetic.** A `center`ed row track is sized to its *content*, so the canvas has no free space to grow into and `flex: 1 1 auto` on it is a no-op: two lanes at n=1,025 gave 483×302 canvases with `center`, and 483×655 with `stretch`.
- **`finishRace()` re-measures AFTER it writes the panel**, because the lane rows are `1fr` and filling an empty `<p>` makes every canvas shrink again.
- **`maxLoggedEvents: 0` on every lane**, because a race lane is the only `SortRun` on this site that never rewinds — the log costs ~33 MB per lane at n=1,025 and nothing would read it.
- **A race lane's cost is DESTINATION AREA, not sprite count.** Six 311×289 lanes total 539k px, less than the single-mode canvas this page already runs at 60fps.

### G4. The Sorting Page Finally Has A Checker
`sort` was the newest group and the defect above shipped through a 41-script suite: no checker read the page's DOM or its stylesheet, so six permanently blank canvases were invisible to everything the manifest covered. `check_sorting_page.mjs` (102 checks) is split in two, and the split is the design:

- **STATIC, 65 checks, ~0.2 s** — reads `sorting.html` / `algo.css` / `sort-run.js` / `shared.js` off disk. A stylesheet contract can be checked by reading it.
- **RENDERED, 37 checks, ~12 s** — drives the real page over CDP and counts ink by alpha.
- **The rendered half answers every sprite with a 71-byte stub, and that is a deliberate trade.** The page boots by fetching 1,025 sprites at ~130 MB, which was 85% of the runtime. **The stub still catches everything §3.G3 is about** (sprites painted into a hidden canvas give zero ink whichever sprite they are, so the original defect is caught in full), and **what it gives up is that the sprite paths resolve and the PNGs decode** — `PokemonNode.draw()` skips an image whose `naturalWidth` is 0. **The PNG is built, not pasted** — a corrupt stub leaves every lane blank and the checker fails for a reason that has nothing to do with the page, so the chunk/CRC32 constructor re-parses its own output and a bad signature is a startup throw, not 37 red checks.
- **THE STUB IS PROVEN LIVE, or the speedup is a claim nothing checks.** The intercepted-request count is asserted `>= 1,025`, and the glob is read out of `ASSETS.images` rather than written down. **Its ink figures are higher than the real ones and not comparable** — an opaque stub fills its destination box; §3.G3's `24,573 → 110,893` is the real-sprite measurement and stays as the historical figure.
- **THE FAST LOOP IS `--static` ON THE HARNESS, and its placement is the point.** `node scripts/test_check_sorting_page.mjs --static` — 0.5 s. It is **not a flag on the checker** (§4's rule), and it sits **above the harness's two baselines**, because it originally sat below them and the fast loop took longer than the thing it shortcut.
- **THE STRIP IS GUARDED BY A CHECK COUNT, not by "it still passes".** The harness deletes everything between the `RENDERED HALF` sentinels and requires the stripped copy to pass having dropped **exactly 37** checks. That number is **hardcoded, and updating it is the point**: deriving it from the source would be tautological.
- **`Network.setCacheDisabled` IS NOT WHAT KEEPS THE RUN FRESH.** One run reported the old `.al-lanes` rule and the first explanation was a stale cache; it was a concurrent session that had reverted `algo.css` on disk. **Believing the flag was the safeguard means believing the page is being tested current when nothing was checking it.**

### G5. The Cry Suite Was Slow For Three Unrelated Reasons, And Only One Of Them Was A Payload
The obvious move was to stub the cry suite the way §3.G4 stubbed the sorting sprites. **The measurement came first, and the stub fits exactly one cell.** Sorted by where the time actually went: `test_check_gen1_apu` 54.4 s is **CPU**; `test_check_cry_index` 22.6 s → 6.1 s is **a payload** (31 MB copied 22 times); the three CDP checkers' 42.6 s → 12 s is **fixed `setTimeout`** — 35.5 of it sleeping, and they were never waiting on the network.

- **`test_check_cry_index.mjs` builds its working tree once and each case restores what it touched.** The corpus is still the real 31 MB. **The trap this shape invites is a hand-maintained list of "paths a case may touch"** — a second copy of the truth, where a case grows a mutation, forgets the list, and the *next* case runs against a dirty tree and passes for the wrong reason. So there is no list: each case records its own path, and disabling the restore makes cases fail, which is what proves it is load-bearing.
- **A FIXED SLEEP IS A GUESS, AND A GUESS FAILS IN BOTH DIRECTIONS.** Every ceiling used exceeds the sleep it replaced, so tolerance only goes up, and a timeout returns `false` so the assertion still runs and still reports its real number.
- **A CDP COMMAND RESOLVING IS NOT THE PAGE HAVING APPLIED IT**, and the symptom is a checker that is red on a correct page. `check_spectrum_browser.mjs` measured `innerWidth` on the line after `Emulation.clearDeviceMetricsOverride` and asserted it equalled `NARROW`; the command returns while the renderer still reports the override's own width, so the read got 1280 against a 756 default. Instrumented: **+0 ms answered 1280, +50 ms answered 756**, and it stayed there through 1500 ms. Green at 13:44 with an 8.67 s run, then four consecutive reds with nothing in the tree changed — and inserting any delay made it pass, which is the definition of the race. **Two ways this reads as something else entirely**, both hit here: as a page defect (the page was fine), and as a broken assertion (it was correct — `NARROW` is the checker's own default, measured 20 lines earlier, and `clear` restores exactly that). **Expect this shape wherever a checker reads state immediately after commanding the browser to change it.** The same unguarded shape sits in `check_outfit_browser.mjs`, whose `clear` is followed by twelve `getBoundingClientRect()` reads — **but MEASURED there it does not race: across four runs it restored synchronously, 0 ms already answering 756, where this one needed ~50 ms.** The visible difference is that outfit's `ev()` already waits 300 ms after its `set`, which drains a queued resize before the `clear` arrives, while this checker waits on neither side of its own. So that one is **hardening, not a bug fix**, and it is now guarded: the default width is read *before* the override, the restore is polled against it, and a named ceiling is quoted. **An unasserted restore is not a restore** — and note the second half of that sentence's lesson: the guard was worth adding precisely because a race that cannot be reproduced is still a race nobody would be told about.
- **A WAIT AND A SAMPLING INTERVAL LOOK IDENTICAL IN THE SOURCE AND MEAN OPPOSITE THINGS.** The 130 ms between two `getImageData` calls is the *measurement window* of a "did this canvas MOVE" assertion, so it stays. Conversely the 2200 ms "let it play, then stop it" interval was replaced with 500 ms, not with a poll, and **trying the poll made the file SLOWER (14.6 s → 17.6 s)**.
- **TWO OF THESE EDITS FOUND REAL BUGS, IN OPPOSITE DIRECTIONS.** A poll that fires too early **turned a red into a green**: waiting for the AudioContext to exist returned instantly, before the page had read the stored mute off disk, so a *failing* check passed. The fix polls for the precondition for *reading a live measurement*: that the value has **stopped changing**. And an assertion that assumes a precondition nobody established **can never pass**: `check_spectrum_browser.mjs` asserted `theme === 'light'` while headless Chrome reports `prefers-color-scheme: light`, so it failed for its whole life while reporting a message about the ramp. **Expect this shape whenever a check names an END state and never reads the START state.**
- **WHAT DID NOT GET FASTER, AND WHY IT CANNOT, IS WHY IT IS NOT IN THE SUITE.** `test_check_gen1_apu.mjs` runs 34 s and cannot be made cheaper: 17 heavy cases each render 151 species at the native rate, and `renderSpeciesCry` is pure, so there is nothing to cache, share or stub. **The entry was removed rather than flagged**, and the file stays runnable by hand. **What that gives up is named, not glossed:** `check_gen1_apu.mjs` still runs, so the synthesis is still compared against the reference every pass; what is gone is the proof that each of its 92 assertions would fail if the thing it polices stopped being true.
- **THE REPLACEMENT IS A FOUR-ROW AUDIT IN THE RUNNER, and it is weak on purpose.** It reads the retired harness and fails if any of its 39 `expect` strings no longer names an assertion the checker contains. **It lives in `check_all.mjs` because a guard that reads the file under test runs in every fixture too** — 22 of the 39 cases run a tree whose checker has been stripped, so the guard read a stripped source, could not find the assertions 17 expectations name, and emitted 17 failures into the one assertion that exists to make stripping safe. **A fixture is not the file; the runner is not a fixture.**

### G6. State Shared Through Storage Is Not State a Per-Page Test Can See
`sorting.html` starts with its cry switch off, which is correct. It expressed that as `cryPlayer.muted = true`, and **that setter persists** — so merely *loading* the page wrote `{muted: true}` and `cries.html`, `detail.html` and `spectrum.html` went permanently silent, with no control of their own to undo it. **No test could see it, because the bug needed a VISIT ORDER**, and every checker runs on a fresh `--user-data-dir`. `cries-gen1.html` was unaffected because it builds its own `AudioContext` — which is exactly why the report read as two unrelated bugs.

- **THE FIRST FIX CLOSED ONE GATE AND LEFT A WORSE ONE, and the shape is the point.** `muteForView()` closes the load path, but `#save()` is also reached from the volume setter, which serialised the *effective* mute — so the page's default rode out through a slider the reader was using for an unrelated reason, which is worse than one written on load because **it presents as the reader's own doing.**
- **One field cannot carry both decisions because `#save()` cannot tell them apart.** `#storedMuted` is the reader's choice and the only one written; `#viewMuted` is a page's default and lives in memory. **`#applyGain()` and `get muted()` must both read the OR** — `#storedMuted` alone makes `sorting.html` loud by default, `#viewMuted` alone ignores an explicit un-mute. Neither wrong answer throws.
- **A WAIT FOR NAVIGATION MUST BE GATED ON SOMETHING ONLY THE DESTINATION HAS.** The cross-page wait was gated on `nav[data-nav] a`, which **the page being navigated away from also has**, so the wait returned instantly against the old document. `Page.navigate` resolves when the navigation is committed to the browser, not when `Runtime.evaluate` reaches the new document, and **the two documents share an origin — so anything they have in common is evidence of nothing.**
- **THE MEASUREMENT HAS TO DISTINGUISH "MUTED BY THE CHECKER" FROM "SILENT".** The tap zeroes `ctx.destination`, so the probe's own gain is 0 by construction; the player's level is read one node upstream. **Expect this shape anywhere a test silences the thing under test: discard the output, measure upstream of it.**

**Guarded by:** `check_cries_browser.mjs`'s cross-page cry-volume regression.

### G7. Nine Harnesses Were Running One Child At A Time, And The Fix Is One Module
`scripts/lib/pool.mjs` exists because nine of the fourteen harnesses were the same construct: independent cases, each its own `node` process against its own temp tree, run one at a time by a `for` loop around an `execFileSync`. **Every report is byte-identical to the version it replaced, exit code included** — that is the whole verification, and it is the only one that counts.

- **DECLARATION ORDER OUT IS PART OF THE CONTRACT, not an accident of scheduling.** The obvious implementation logs from inside the worker, which makes output order a property of the scheduler — so two green runs stop diffing and a red case cannot be found by reading. `pool()` returns one result per task in the order they were given and the caller prints after the drain.
- **`POOL` IS CAPPED AT 4 AND NOT AT THE CORE COUNT, and that is a real choice on a 10-core machine.** Each worker is a full JIT-compiling interpreter rather than a thread, and other work shares this machine: a run that saturates every core makes the editor and the server sluggish for its duration.
- **A POOL'S PREMISE IS THAT CASES ARE INDEPENDENT, and four harnesses cannot use it at all** because their cases share ONE working tree and restore it between cases. **There is no assertion for this and there cannot be: it is a property of what the case does to the directory, and the harness knows it because it wrote the harness.**
- **ELEVEN NOW, AND TWO OF THEM ALSO LEAKED STDERR.** `execSync` inherits stderr by default, so a failing child's report went to the *parent's* stderr instead of into the captured `out` — half the output arriving out of band means no case could rely on `caughtBy`.
- **SEVEN OF THE ELEVEN USED `execFileSync('node', …)`, WHICH IS A DIFFERENT INTERPRETER FROM `process.execPath`.** A baseline and its mutations have to run the same machine to be comparable.

### Q. Terrain Cost Is Rec.709 Luma, And That Is A Decision, Not An Omission
`computeTerrainCost()` (`assets/js/maze-pathfinding.js:342`) is two steps and **no colour space at all**: `alpha < 50 → Infinity`, `luminance = 0.2126R + 0.7152G + 0.0722B`, `cost = 1 + (255 − luminance)/255 · (maxCost − 1)`. Hue and saturation are discarded. **Pure colours therefore have a fixed global order on every sprite** — measured at `maxCost = 6`: 白 1.000 · 黃 1.361 · 青 2.063 · 綠 2.424 · 洋紅 4.576 · 紅 4.937 · **藍 5.639** · 黑 6.000. Blue is dearest and yellow cheapest purely because Rec.709 gives green 71.5%, red 21.3% and **blue 7.2%**.

**THE REASON IS AN INVARIANT, NOT COLOUR SCIENCE.** Cost is a strictly monotonic function of the brightness the renderer actually draws, so **a reader can look at the grid and predict where A\* will go.** A model that diverges from the visible image breaks that promise *silently* — the page still shows the sprite, the numbers still print, and nothing says the two have come apart. For a page whose claim is 「看到的就是要付的」 that is a worse failure than a lumpy landscape. And luminance-based brightness is itself perceptual (Rec.709 is video's Y′), so the invariant and perceptual accuracy do not actually fight here.

**Measured over 33,143,750 pixels from 147 sprites**, cost at `maxCost = 6`:

| model | min | p25 | median | p75 | max |
| :--- | ---: | ---: | ---: | ---: | ---: |
| **Rec.709 luma (shipped)** | 1.000 | 2.219 | **3.148** | 4.144 | 6.000 |
| CIELAB L\* | 1.000 | 2.074 | 2.915 | 3.919 | 6.000 |
| OKLab L | 1.000 | 1.936 | **2.643** | 3.504 | 6.000 |

**THE THREE WEAKNESSES ARE NAMED IN THE SOURCE SO THEY ARE NOT REDISCOVERED AS BUGS.** Y′ is luma, not luminance, so the dark end is over-weighted — that is the whole of the median gap; cost steps are not perceptually uniform, because a 0.1 gap between two near-blacks is as big a *number* as one between two near-whites but only the second is visible; and blue is nearly invisible to the weights.

- **A. Keep luma.** The decision.
- **B. OKLab L.** Perceptually uniform, and `rgbToOklab()` **already exists** in `color-match.js` — whose docblock names this exact class of decision as the reason one conversion must have one implementation. Best evidence-to-effort ratio. Costs 1,600 conversions per contrast change, and makes 「what you see is what you pay」 approximate.
- **C. Slope / elevation.** `cost = 1 + k·max(0, h(next) − h(current))`, descending free. What game AI actually does, and the most interesting pedagogically, but a **redesign rather than a fix**: cost becomes a property of a *move*, 「路徑成本」 changes meaning, and `octileHeuristic`'s admissibility has to be re-proved rather than inherited.
- **D. Local contrast.** Charge only for change, so a flat pale wing is free and the map's *structure* is what costs.

**WHAT WOULD JUSTIFY MOVING OFF A** is evidence that a reader cannot predict the route from the image — not 「which model looks nicer」. Rec.709 fails that in the **darks**, not the light, which is where the interesting paths are.

**Expect this shape whenever a measurement is taken with a different implementation than the one under test.** An offline decoder was used to claim terrain endpoints could be an isolated cell, and the claim was **wrong** — re-measured through the page's own `drawImage`, **144/147 sprites are solvable with zero isolated starts**. Same sprite, same 40×40, opposite answer, because an area-average box filter treats a transparent pixel as a black pixel and Chrome's `drawImage` premultiplies. **The three that do fail are real and are a different defect:** their passable region splits into several components, and the bbox-corner rule puts start and goal in different ones (#904: start in 368 cells, goal in **1**), so the reader gets 「無解」 on a solvable map. The 9 sprites that genuinely fail are a **different** defect — see §3.T — **and a second probe of the same question got it wrong differently**, letting diagonal moves into impassable cells, which inflated every count it printed while leaving its conclusion intact. A scratch harness is a checker with no assertions. See [`#r`](docs/incidents/page-defects.md#r).

**Background:** [`docs/incidents/page-defects.md#q`](docs/incidents/page-defects.md#q)

**Guarded by:** nothing — the model is a constant, not a claim with a threshold. The corpus histogram above is a hand measurement; `check_maze_page.mjs` asserts that `computeTerrainCost` is still the single cost function and that the page reads its alpha threshold from the module.

### T. The Terrain Endpoints Were The Extent Of The Specks, Not Of The Pokémon
`computeTerrainEndpoints()` took the bounding box of **every passable cell**, then `findNearestPassable` at each corner. On a sprite with a detached fragment — Beautifly's wing tip, Flygon's wing, an anti-aliased speck on Overqwil — that corner is the FRAGMENT, and start and goal land in different components. **Measured through the page's own `drawImage` over 257 sprites: 9 (3.5%) report 「無解」 on walkable maps, zero isolated starts, and the start is CORRECT in all three named cases while the goal is not.**

- **THE SINGLE-RUN FIX IS SURGICAL, AND THE BLAST RADIUS IS WHY.** The old rule is tried first and returned untouched whenever `terrainReachable(start, end)` holds — **248 of 257 keep byte-identical endpoints and the fallback never runs.** The unconditional version was measured and rejected: it moves endpoints on **7.4%**, of which **10 sprites are currently working fine**. The fallback is correct **by construction** — the ring scan is restricted to the body, so both ends land inside it.
- **THE PATROL IS NOT SURGICAL**, because its semantics are unambiguous: its five points are *this Pokémon's centre and corners*, and a bbox over stray pixels is not that. Measured over 1,028 legs, the all-passable bbox leaves **28 legs unreachable on 22 sprites (8.6%)**; the body's bbox leaves **zero**.
- **`largestComponent()` LIVES IN THE MODULE SO ALL OF THIS CAN BE RUN**, and its tie-break is **scan order, first wins** — the strict `>` is the contract, because the alternative makes the result depend on where the scan started.
- **EXPECT THIS SHAPE WHENEVER A FIX IS DEFENDED BY A SINGLE NUMBER.** The first measurement here looked at patrol leg **length**, found no difference, and nearly argued against the change. The defect was leg **REACHABILITY**, which it never computed — a quantity with nothing to do with length. **Measuring the wrong quantity is worse than not measuring**, because the number says 「this fixes nothing」 with exactly the same confidence as a number that would have said the opposite.
- **AND EXPECT A SCRATCH HARNESS TO BE A CHECKER WITH NO ASSERTIONS.** `at(x, y)` returning a fresh object per call does not give a wrong answer, it gives **an unbounded loop** — `seen` is a `Set`, so membership is by identity. The first fixture did exactly that and the checker died with `RangeError: Set maximum size exceeded`.

**EVERY SLUG IN `PLANNED_PAGES` MUST BE ABSENT AS A FILE, and this one had been present for a while.** The row read 「色帶已足夠作答，缺的是出題、計分與難度」 for a page that answered all three gaps in the same commit it shipped — so the array's *only* load-bearing claim, the one `docs/missing-pages.md` states as a numeric fact and mirrors row for row, was false. **Nothing renders from that array** (`collections.html` reads `COLLECTION_GROUPS`), so no reader saw the lie and no checker reads either table; the only thing that exposed it was deleting the row's title during a rename and noticing the `why` beside it no longer described anything. **THE GUESS BOX HAS TWO AUTOCOMPLETE LAYERS BECAUSE NEITHER ONE ALONE SERVES THE STATED NEED** — 「知道是哪一隻，但打不出全名」.

- **The custom list matches on SUBSTRING, so `伊布` finds 水伊布.** A `<datalist>` matches on **prefix** and would find only 伊布. The custom list also knows which species are already guessed and can disable them; a datalist cannot express that without offering a value the reader cannot complete to.
- **The datalist is the only layer a phone's software keyboard will read.** The input was `autocomplete="off"` with no `list`, so there were **no** keyboard suggestions at all — the reader had to discover the dropdown. **It is built ONCE in `init()`**, never per keystroke: 1,025 options rebuilt on every `input` event is ~40 KB of DOM churn on the page whose whole premise is that the reader types a lot.

### Y. `cry-game.html` — 叫聲猜謎, And The Axis That Had To Be Measured Before It Could Be Written
Ported from `pokemoncries.com`. Ten questions a round, four nameless sprites each, one cry to listen to. **The design was measured twice and rejected twice; both rejections are the reason this section exists.**

- **THE NAME IS ONE HALF OF A PAIR, and the pair is why `color-game.html` is 顏色猜謎.** 叫聲猜謎 / 顏色猜謎 — four characters, one shared suffix, differing only in the medium. **This page's name is what made 猜謎遊戲 ambiguous**, so the naming rule and the rule about not renaming one of the four sites without the rest live in **§3.W**, not here. Read them before changing either title, `<h1>`, NAV label, or share string.

- **THE DIFFICULTY AXIS WAS RANK BANDS FIRST, AND 困難 AND 地獄 DID NOT SEPARATE.** The obvious encoding of 「how hard is this question」 is how similar the three distractors are to the answer. Rank bands over the neighbour list — 簡單 from the far half, 困難 from the near quartile, 地獄 the three nearest — read as obviously correct and are not. **Measured across all ten pools (all 1,025 plus each generation), `p90(困難) − p10(地獄)` was negative in every one: −0.093, −0.255, −0.186, −0.194, −0.204, −0.161, −0.204, −0.235, −0.262, −0.195.** Two of the three tiers were the same tier, and the only symptom would have been a difficulty tab that changes nothing a player can hear. **The reason is structural: with four options the answer competes against exactly three others, so a question's difficulty is its SINGLE hardest distractor — and three drawn at random from the near quartile put that one at rank ~21 of 256, which is almost as confusable as rank 3.** Expect this shape on any axis expressed as a window over a ranked list when the question consumes a fixed small number from it.

- **SO DIFFICULTY IS A CEILING ON ONE NUMBER.** Sort the neighbours, drop everything above the tier's limit, take the first three: `easy 0.35 · hard 0.65 · hell Infinity`. A question's difficulty is then the ceiling *by construction*, so `check_cry_game_similarity.mjs` asserts `hardestSim <= ceiling` per question as an **identity, not a tolerance** — the same comparison the module filters on. `Infinity` is not a special case anywhere: the filter is `sim <= ceiling`. The property that makes it shippable is measured, not argued: **across 10 pools × 3 tiers × 6,150 species checks, 0 ceiling violations and 0 degraded questions**, and measured hardest-distractor similarity is now **0.349 / 0.647 / 0.738–0.879** by pool, monotone and separated by ~0.30 and ~0.19 in all ten.

- **THE GENERATION FILTER IS A POOL, NOT A DIFFICULTY.** The reference's only axis was the generation, and it cannot be: Gen I has 151 members and Gen VI has 72, so 「第一世代」 and 「第六世代」 at the same distractor policy are not comparable rounds. It survives as a chip row, and its list is **derived from `availableGenerations()`** — a chip list and the pool filter that has to agree with it are one value, not two (§3.P).

- **ALL 34 DIMENSIONS, NOT cries.html's ROBUST FIVE.** Cosine over the standardised `ROBUST` five measures **0.996 at p50 for every pair** — five near-positive dimensions have no angular spread, so the metric saturates and no band is distinguishable. **Expect this shape on any cosine over very few correlated positive dimensions: it does not measure distance, it measures that everything is similar.** All 34 give a 3rd-nearest of p1 0.552 / p50 0.793 / p99 0.949. **`m0` is kept deliberately against §3.G1's `UNCOMPARABLE`** — its documented defect is that it moves with file length, which makes it a duration proxy, and two cries of the same length do sound alike. A dimension that is a defect when comparing two implementations of one analysis is signal when asking 「do these two sound alike」.

- **`cry-game.js` CONTAINS NO `Math.random` AT ALL.** `buildRound` and `eliminateIndex` default `rand` to `Math.random` and neither default is overridden, so the claim is *enforceable* rather than 「this page only reaches for randomness where the module allows」 — which is a shape a reader has to check by eye. The same reason `game-tips.js` is a module (§3.W).

- **THE NAMES ARE HIDDEN UNTIL THE ANSWER.** The reference prints the species name on all four cards, which makes the game 「remember which cry belongs to which name」 — unanswerable by anyone who has not memorised the dex, and nothing to do with recognition. Here a card is a picture and a number while the round plays. **§3.W's greyscale rule is deliberately NOT reversed**: there the sprite was a leak *beside* the clue; here it *is* the answer.

- **FOUR DEFECTS FOUND BY DRIVING THE PAGE, NONE OF THEM REACHABLE FROM A SHAPE ASSERTION.** `check_cry_game.mjs` had **134 assertions green throughout all four**:
  - **The round ended one question early.** `advance()` asked `indexOfCurrent + 1 >= length`, but writing the pick had already advanced `indexOfCurrent`. - **THE HEADER MODIFIER WAS `header-cries`, WHICH IS NOT A CLASS ANYWHERE.** Invented from the group's name, and `check_cry_game.mjs` passed it because it asserted `used[0] === 'cries'` — a name the page happened to carry rather than whether `shared.css` defines it. Measured after a single card press — unawaited `play()` starts within 1.2 s with **no further gesture**, repeatedly. ### Z. `index.html` Is Two Sections And A Clip, And 今日推薦 Took The Other Eight
The homepage used to be nine content sections. It is now a hero and five cards, and everything else moved to `today.html`, which is the first row under 圖鑑. This section records the three decisions that are not derivable from the code, because all three are choices someone could re-litigate from scratch.

- **THE SCRUB WRITES `currentTime` AND NEVER CALLS `play()`.** The hero is a 240vh track whose sticky layer holds one generation's 10 s clip, and the reader's progress through the track is written straight into `video.currentTime`. Autoplay would give the reader a loop they did not ask for and could not stop; scrub gives them a position that is a function of where they are. **Scrolling UP plays the clip backwards**, and that falls out of the mechanism rather than being a feature — `currentTime` is a seek, and a seek to a smaller number goes to a smaller number. A play/pause transport cannot do it without a second implementation of time.
- **PROGRESS DIVIDES BY `rect.height - innerHeight`, AND THE SECOND TERM IS THE WHOLE CLAIM.** Drop it and the denominator is the entire track, progress tops out at 1 − 1/2.4 = **0.583**, and the last 42% of the clip is unreachable **while everything still looks correct**. Measured through the browser checker: with the term, `currentTime` equals `progress × duration` to a worst error of **0.000 s** across five stops, and the clip reaches **10.00 s of 10 s**.
- **BOTH ENDS OF THE CLIP ARE BLANK, AND THAT IS DECLARED RATHER THAN FIXED — BUT THE PAGE DOES NOT LAND ON ONE OF THEM, AND IT USED TO BE DOCUMENTED AS IF IT DID.** `make_hero_video.py` builds the roster across the clip's first 65% and fades it back out over the last 13%, so frame 0 and frame 299 both contain no sprites. **Measured offline off the shipped bytes in the checker's own left band: frame 0 = 0.00% ink, frame 299 = 0.00%, frame 195 = 23.01%.** **The author was shown this and chose to keep the full clip** (「維持 0%→100%」) over re-mapping the scrub onto the wave, which is the one-line alternative.
  - **THE 0% STOP HAS TWO LEGITIMATE ANSWERS AND THE PAGE RACES BETWEEN THEM.** **LANDING** on a fresh load: `MIN_SEEK_DELTA` makes `seek()` refuse a write within one frame of where it already is, so at the top of the track nothing is written, no frame is presented, and the compositor is still showing the **poster** — the COMPLETED roster, cut at `POSTER_FRACTION` 0.65, measured 22.75% in that band. **ARRIVING** back from 30%: currentTime was at 3.0s, so the write happens, frame 0 is presented, and the band reads 0.00%. **`check_home_hero_browser.mjs` asserted the poster, passed once, and went red on the next run** — the two answers differ by 23 points of ink, so no tolerance could have held both. **Expect this shape whenever a state is reached by two routes and the assertion names one of them.**
  - **SO THE SENTENCE 「A READER THEREFORE LANDS ON AN EMPTY HERO AND SCROLLS OFF ONE」 WAS WRONG, AND IT WAS WRONG IN THE READER'S FAVOUR.** They land on a finished roster, and fade out to the blank field at the top once they have scrolled. What is asserted now is the part that is not a race — the clip is parked on frame 0 at 0% — and the part that carries the risk, which nothing asserted for as long as this file existed: **that arriving back at the top from 30% DOES reach the blank frame 0** (0.00% ink). `MIN_SEEK_DELTA` creeping up to a second, or `seek()` gaining an early return, would park the reader on the poster however far they scrolled, and every other assertion in the file would still pass — the identity, the monotonicity, the middle stops.
  - **THE OLD FAILURE MESSAGE NAMED A CAUSE ITS OWN RUN HAD JUST DISPROVED**: 「the scrub is no longer 0 -> 1」, printed on a run where the identity assertion *above* reported `currentTime == progress × duration` to a worst error of **0.000s**. The scrub was always 0 → 1. A message that names a cause its own run has contradicted is worse than none. §3.G9's rule one section over.
- **THE POSTER IS NOT A PRE-PLAY FLASH.** Nothing calls `play()`, so `poster` is not transient: until the first seek it **is** what is on screen. One file covers the ~200 ms before metadata, a reduced-motion reader (frozen on the *same frame* the poster was cut from — `POSTER_FRACTION` is read out of `make_hero_video.py`'s `PHASE["build_end"]` rather than written down, because 0.65 in two places is two places to be wrong and both still produce a valid number), and a load that never arrives. There is no second fallback asset and no metadata timeout: a clip still downloading shows its poster, and a deadline would discard a download that is 90% done.
- **THE DAY IS ONE IMPLEMENTATION, TWO CALLERS.** `hero-gen.js` **imports `taipeiDateKey` from `daily-pick.js`** rather than computing a date. Two date keys computed two ways is how the homepage says one generation and another Pokémon for four hours. **THE EPOCH IS IN THE FUTURE AND THE WRAP IS THE POINT**: `GEN_ONE_DATE` is 2026-10-18 and the day this shipped was 2026-10-16, so `dayOffset` wraps **in both directions** — 10-16 is the eighth generation, 10-17 the ninth, 10-18 the first — and every date in the calendar maps to exactly one of the nine with no special case for the gap. A JS `%` keeps the dividend's sign, so `((o % 9) + 9) % 9` is load-bearing: without the inner `+9` a pre-epoch date indexes off the end of the array and yields `undefined`, which renders as generation 1 with nothing logged.
- **THE HERO IS A DARK BAND IN LIGHT THEME, ON PURPOSE.** The clip bakes `--bg-primary` and has no alpha channel, so there is nothing to blend and the hero cannot follow the theme. **The scrim therefore fades to the clip's OWN background (`#0b1020`) and not to `--bg-primary`** — fading to the theme's token means the bottom of a dark clip dissolves into a white page in light theme, which reads as a rendering fault. What is left is a deliberate edge. The author's call.
- **THE PANEL IS DARK IN BOTH THEMES, WITH ITS OWN ACCENT.** `--accent-gold` is crimson in light theme and measures **1.63:1** on this panel, so the hero declares `--home-hero-accent: #f5c542` rather than reaching for the shared token. The fill is **`rgba(6, 9, 20, 0.7)`** and the h1 reads at **4.75:1** against the panel composited over **pure white** — the bound no frame can exceed, and the assertion — and **8.44–9.40:1** from decoded pixels across the wave.
- **THE PANEL'S ALPHA IS A FLOOR DERIVED FROM WCAG, NOT A TASTE, and it was 0.8 until a reader asked to see through it.** A sprite can be any colour up to pure white, so the ground behind the title can be no darker than the fill composited over white — a figure depending on no frame and no scroll position, which is why `check_home_hero_browser.mjs`'s own docblock calls it unfoolable and why `check_home_hero.mjs` can compute it from the two declarations. Measured across the whole panel: **0.85 → h1 8.36 · 0.80 → 6.98 · 0.75 → 5.73 · 0.70 → 4.73 · 0.65 → 3.93 ✗ · 0.60 → 3.27 ✗ · 0.50 → 2.30 ✗ · 0.40 → 1.67 ✗.** **0.65 is the first value under 4.5:1, so 0.70 is the most transparent this panel can be** — the request was for 0.5, which is 2.30:1, and the primary button is unaffected either way because it paints the accent at full alpha (a fixed 11.30:1). **The bound is computed, never restated**, so the floor cannot drift away from WCAG the way a written-down `0.7` could. **Expect this shape anywhere a translucency is a design lever: it is also an accessibility measurement, and the two questions have one answer.**
- **AND ALPHA ALONE COULD NOT DO IT — THE BLUR WAS WHAT WAS HIDING THE SPRITES.** At 0.8 with `blur(10px)` the panel is a colour wash: nothing of a Pokémon's shape survives it, so dropping the alpha to 0.7 moved `rgb(56,58,67)` to `rgb(81,83,91)` and bought a *slightly lighter wash*. **`backdrop-filter: blur(3px)`, and the blur costs no contrast at all**, which is why it is the safer of the two levers and why both were pulled together. **And a blur is invisible to every contrast assertion, so it carries its own**: `check_home_hero.mjs` reads the radius out of its own declaration and requires ≤3px, because a checker that only guards what it can measure lets this go back to 100px silently.
- **THE STYLESHEET PARSING IS NOW ASSERTED, AND IT IS HERE BECAUSE IT DID NOT.** Every rule-shaped assertion in `check_home_hero.mjs` is a **regex over the `<style>` block's text**, and a regex cannot tell valid CSS from a broken one. Adding the alpha guard proved it: a comment in `index.html` was closed one delimiter early, the orphaned prose became live CSS, and the browser **discarded the rest of the block** — the panel lost its fill (computed alpha **0**), the h1 lost its accent and inherited `--text-primary`, and the hero rendered unstyled **while all 96 checks stayed green**, because every one of them was reading text the browser had already thrown away. **Then this file's own docblock reproduced it by naming the closing delimiter inside itself**, since a CSS comment does not nest. So the guard is a **count of comment openers against closers**, which is the one shape in a stylesheet that can silently truncate everything after it, and it cannot be satisfied vacuously — there is no reading of this page in which the two counts differ. **Expect this shape whenever a check reads a file as text: a rule can be present, correctly spelled, and not exist.**
- **THE PANEL IS A TITLE CARD — h1, the two CTAs and the scroll hint, and nothing else.** It was 760 of `max-width` and a measured **736×436 at 1280×900 — 27.9% of the viewport**, dead centre over a full-bleed roster grid; now **340×238, 7.0%**. **The phone was the worse case and is why this was worth doing: 350×421 at 390×844, 44.8% of the screen, is now 262×207, 16.5%.** The lede, 已更新至第 9 世代 and the three counts live in `.home-intro`, between the track and the feature grid. Three things that are decisions rather than code:
  - **`max-width: 760px` WAS ALREADY NOT BINDING, and is not binding now — the cap that decides this panel's width is the lede's `max-width: 660px`, which is what took it to 736.** With the lede gone the panel shrink-to-fits its widest child, the 42px h1 at 264px, and 760 binds only above ~300% browser zoom (where the title alone is 756px). **Expect this shape whenever a `max-width` on a shrink-to-fit flex item starts reading as dead weight** — the honest statement is that it is now a zoom guard, and it was a no-op before this change for a reason nobody could see from the stylesheet.
  - **THE SCROLL HINT STAYS IN THE PANEL** for two separate reasons: 「向下捲動播放」 is a claim about the *clip*, so moving it below the track makes it describe something the reader can no longer see; and it inherits the panel's legibility instead of needing a contrast surface of its own. It is the reason `#f5c542` and the 34px of padding above the h1 are **untouched** — which is why `check_home_hero_browser.mjs` needed no edit when the fill went from 0.8 to 0.7. The panel has since moved twice: narrowing it took the decoded pixels from 8.43–9.15:1 to **11.40–11.64:1** (the crop is the panel's padding strip above the title, and a 270px strip is less likely to contain a bright sprite than a 776px one), and dropping the fill to 0.7 with a 3px blur took them to **8.44–9.40:1**. The analytic bound followed the alpha down, 6.98:1 → **4.75:1**, and that is the floor.
  - **THE INTRO BLOCK IS BELOW A 240vh TRACK, so it lands at y=2215 on a 3030px page.** h1 + the two ways out are above the fold and the sentence saying what the site IS comes after the thing it is about. That is the two-act page, and it is why nothing above the fold got quieter. The document grew 3030 → 3263px at 1280×900 and 4216 → 4437 at 390×844.
- **THE THREE COUNTS ARE CLAIMS ABOUT OTHER PAGES AND ARE RE-DERIVED.** 1,025 comes from `pokemon_data.json`'s length, 9 from `GENERATION_COUNT`, 6 from `sorting-algorithms.js`'s `ALGO_IDS`. All three are hand-written markup and all three go stale quietly otherwise — the same shape as the four 精選系列 counts that drifted behind a 敬請期待 badge behind `check_categories.mjs`.

**MOVING TEXT OUT OF THE PANEL IS A REWRITE, NOT A MOVE — because the panel's colours are not the page's colours.** `#ffffff`, `#f4f6fc`, `#cfd6e8` and `#d7dbee` are tuned for `rgba(6,9,20,0.8)`; on the page's own `--bg-primary` they measure **~1.05:1** in light theme, so the paragraph and the three counts would have been elements that exist and are invisible. Every one became a token (`--text-primary` / `--text-secondary`), and `rgba(255,255,255,0.14)` on `.home-hero-stats` became `var(--hairline)` — a white 14% rule is not a subtle border on a white page, it is **no border**, and the numbers read as unattached. **Expect this shape anywhere a hardcoded colour crosses from an opaque local surface to the page's theme, and remember that no dark-theme screenshot can answer it.**

**`text-align: center` ON `.home-intro` IS DECLARED, NOT INHERITED, and the reason is the cheapest defect in the change.** `.home-hero-lede` used to centre itself off `.home-hero-sticky { text-align: center }` — one ancestor up, through a class nobody reads when looking at the lede's own rule. Moving the block out removed that ancestor, and the failure mode is not a red line: every rule still exists, no declaration is invalid, nothing throws. The paragraph is simply left-aligned under a centred title. **Expect this shape on any element that moves out of a container whose layout properties it was reading by inheritance** — the assertion is a `text-align` declaration on `.home-intro` and not "something centres it", because an inherited `center` satisfies the latter and breaks again the moment the block moves.

**AND `at()` IN `check_home_hero.mjs` WAS PROVING THE STYLESHEET'S ORDER WHILE ITS LABEL CLAIMED THE MARKUP'S.** The three hero selectors each appear twice — once as a rule inside `<style>` and once as an attribute — and the stylesheet comes first, so `htmlCode.indexOf` returned CSS offsets. The assertion passed **by coincidence**: both lists happen to read media, scrim, content. Reorder the markup and it stayed green; move a declaration and it went red for a reason with nothing to do with the page. It now slices past `</style>` first. **A check that reports the right verdict about the wrong thing is worse than no check, because a reader stops looking at it** — §3.J's `.cache` holding keys the manifest no longer has, one layer down. The same fix is why the new panel-contents assertion reads a block delimited on `\n {8}</div>` rather than the first `</div>`: `.home-hero-cta` closes at ten spaces, so the lazier delimiter stops inside the panel and reports the CTA's children (§3.P's second vacuous shape, written by the person who had just recorded it).

**THREE MEASUREMENT BUGS THIS COST, ALL OF WHICH REPORTED A CONFIDENT NUMBER** — the shape §3.G5 names, arrived at from a third direction.

- **`Page.captureScreenshot`'s `clip` is in PAGE coordinates, not viewport.** It is right at `scrollY === 0` and silently wrong the moment the page moves. Measured before the fix: the left band read **22.4% ink at 25% of the track and 0.0% at 75%**, which looked exactly like a hero showing the wrong frames and was a crop landing on the document's own header — the band image came back with `.header` drawn through the middle of it.
- **A BRIGHTEST-PIXEL SEARCH INSIDE A BOX CONTAINING THE TEXT FINDS ONLY THE TEXT.** The first contrast measurement cropped the whole panel and took its brightest pixel as the "worst case ground"; `#f5c542` is L=241, so the verdict was the title against itself at **1.44:1** on a panel that composites to 6.97:1 (the alpha at the time; 4.75:1 now). The crop is now the padding directly above the title, **inset by the corner radius** — the rounded corners are where there is no panel, and including them measured 1.57:1.
- **`video.seeking === false` IS ALREADY FALSE BEFORE THE SCRUB'S rAF HAS RUN.** Waiting on it photographed the frame the reader was never shown. `requestVideoFrameCallback` is the *right* API and was tried first — it fired on **1 of 5 seeks**, because a paused video that is seeked does not reliably present in headless Chrome. What works is waiting for `currentTime` to **move and then stop moving**, which is this project's own recorded rule for reading a live measurement. **Expect this shape wherever a property a checker reads and the thing a camera photographs are two different events.**

**Guarded by:** `check_home_hero.mjs` (89, 0.2 s, group `home` — imports both modules so it can *run* the date maths rather than regex it, and reads the track height out of `home-hero.js`'s own constant and the poster fraction out of `make_hero_video.py`) + `test_check_home_hero.mjs` (19 cases, pooled).

**THE RENDERED HALF WAS RETIRED FOR A HANG THAT WAS NOT A HANG — and every ceiling in that file was aimed at nothing.** `check_home_hero_browser.mjs` hung for 12 minutes inside tier B three times, at 0% CPU, holding the other browser entries open. A 30 s ceiling on **every CDP call** and a 4-minute file watchdog were added *because of* the hang, and **neither fired under the condition it was added for**.

**THE HANG WAS A MISSING `process.exit()`.** The file never killed Chrome and never exited, so the CDP WebSocket and the spawned child kept its event loop alive *after it had printed its verdict*. The checks finished in well under a minute and the process then sat there indefinitely — which from outside is indistinguishable from a hang: a running row, no cache write, a pool that never drains. **A checker that has finished and does not exit is the same symptom as one that is stuck, and nothing in the output distinguishes them.**

**THE WAITS WERE THE OTHER HALF, AND THEY WERE IMPOSSIBLE BY CONSTRUCTION.** Measured per-`scrollTo` once the file could be trusted to finish:

| section | before | after | what it was doing |
| :-- | --: | --: | :-- |
| reduced motion | **16.7 s** | 0.3 s | two `scrollTo()` calls whose `seekSettled()` polls for a seek to LAND — under reduced motion the clip is frozen on purpose, so it never lands and each poll burned its full 8 s |
| the five forward stops | 9.1 s | 1.2 s | the 0% stop polls for the clip to MOVE; it is already at 0, so it burned 8 s and returned `landed: false` |
| the reverse scrub | 8.4 s | 0.4 s | a `scrollTo(1)` straight after a run that ended at 1 — the same impossible wait, another 8 s |
| contrast, both halves | 0.9 s | 0.9 s | the cheapest thing in the file, all along |
| **TOTAL** | **36.6 s** | **4.0 s** | |

**`seekSettled()` NOW POLLS FOR THE POSITION, NOT FOR THE MOVEMENT.** The precondition a screenshot needs is "the clip is AT this position and is not mid-seek", which is true immediately when the target is where we already are. The two-consecutive-stable requirement stays, because it is the margin against the hazard §3.Z records twice — currentTime reaching its target while the compositor has not presented the frame yet. **Dropping it would have traded 16 s of dead time for a screenshot of the wrong frame.** And the `if (f > 0)` guard that exempted the 0% stop is **gone**: all five stops are asserted, so the file now carries **53 checks rather than 50** — the freed budget bought an assertion rather than a deletion.

**THE FILE PRINTS WHERE ITS TIME WENT, every run, because §4's rule about a slow check is that the question to ask is what it is actually computing** — and the answer was visible nowhere. `at()` was already called at every section boundary, so this cost one `Date.now()` each and turns 「the browser checker is slow」 into a number per section. **The cost is charged to the section that RAN, not the one about to run**, which is the half that is easy to get backwards and makes every row name the wrong work; and `at()` alone cannot close the final section, so `closeSection()` is called once more at the end.

**THE WATCHDOG IS ONE-SHOT AND NOT RESET PER SECTION**, so a legitimately slow run is killed at 240 s whether it is making progress or not. That is deliberate — the fix for 「this file is too slow」 is to make it cheaper, and **§3.Z records what happened the last time a ceiling was raised to hide a cost instead.**

**AND IT STILL IS NOT A MANIFEST ENTRY**, which is now a weaker argument than it was: at 53 checks and ~4 s it is no longer expensive, and **§3.P's objection — a page whose only rendered checker does not run — is the reason to put it back rather than the reason to leave it out.**

**WHAT IS GIVEN UP, named.** Nothing about the page: the scrub identity at 0.000 s, the reverse scrub, reduced motion freezing on the poster frame, the 4.75:1 worst-case contrast and the blank end at 0.00% ink are all still measured and all still true. What is no longer **enforced** is that they stay true — a future change that breaks the scrub, the freeze or the panel's opacity is caught by the static half's arithmetic and by nothing else. **And that is a real gap: §3.C is explicit that contrast is measured from decoded pixels, so no static assertion can stand in for it.** The entry is written out verbatim in `check_all.mjs` with its inputs, so putting it back is one block rather than a reconstruction.

### AA. `moves.html` / `move.html` — 919 招式, And The Four Bugs Only A Browser Could See

`moves_zh.json` shipped **782** moves for a year, because `fetch_moves.py` only emitted the ones the 1,025 reference. PokeAPI has **919** non-shadow moves, and the missing 137 are Z-moves, Max Moves, Hisuian 四季之符 and 掙扎 — a move no Pokémon learns is still a catalogue entry, and a 招式 page is a database. `move.html` carries **no nav row and no `pages` entry**, exactly as `detail.html` does; `moves.html` has both, because `check_color_page.mjs` requires a row-claimed page to appear in its group's `pages` or the aria-current lands inside a `[hidden]` panel.

- **EFFECT TEXT HAS TWO PROVENANCES AND THE BOUNDARY IS A GENERATION LINE.** 826 rows are PokeAPI's `flavor_text_entries` in zh-hant — the same sentence InfoPoke publishes, already in Traditional. The 93 that are ids 827–919, the whole of Generation 9, have no zh-hant flavour entry and are InfoPoke's Simplified run through OpenCC `s2twp`. **InfPoke's NUMBERS AND NAMES ARE NOT READ AT ALL**, measured against PokeAPI across all 937 rows: type disagrees on 126, power on 104, PP on 122, and its name column is mixed script and differs from the official zh-hant on 64 (`力量转换` vs `力量轉換`). Two columns are read out of its 8-column table: the id and the effect.
- **CONVERTING THE 826 WOULD MAKE THEM WORSE, and this is why the split is a boundary rather than a convenience.** `s2twp` would change **18** of them away from official Taiwanese wording — 起風's `刮起狂風` → `颳起狂風`, 污泥攻擊's `投擲污泥` → `投擲汙泥`, 念力's `發送` → `傳送`. **So the checker asserts IDEMPOTENCE, not 「contains no Simplified characters」.** A hand-written Simplified set flags 手, 岩 and 污 — all correct Traditional in this corpus — and fires on 565 of 919 rows, which is §3.S's vacuity shape wearing a correctness hat. `s2twp(shipped) === shipped` is satisfied by exactly one condition: the conversion ran to completion on the rows it was meant to run on.
- **`total` COUNTS DISTINCT POKÉMON AND 473 OF 782 MOVES NEED THAT.** `learnsets.json` is a union over every generation, so a move that was a TM in Gen 4 and a level-up in Gen 5 is counted twice for that Pokémon. 拍擊 has 89 method slots for **87** species. Summing prints 「89 隻可學」 for a move 87 Pokémon can learn and the reader cannot tell which number was meant; the four tab counts stay raw, which is what makes them add up to more than the total.
- **FOUR BUGS THAT NO STATIC CHECKER COULD HAVE FOUND, and one of them was in the checker.** §3.G4's split is the reason this page has both halves. `check_moves_page.mjs` (155 checks, 0.2 s) reads the files and **runs** `filterMoves`/`movePowerText`/`moveUrl` over the real 919; `check_moves_page_browser.mjs` (73 checks, 28 s) presses things. The rendered half's first run found:
  - **`wireRoving`'s `apply` receives the SELECTED BUTTON, not its key.** Passing the element where a string was expected made `panel.dataset.learnTab !== element` true for every panel, so a tab click hid the one already hidden and unhid none: **0 panels shown while `aria-selected` read perfectly.** The signature is in the docblock (`(active: Element) => void`) and the caller got it wrong anyway — which is why the assertion reads the **box**, not the attribute.
  - **`Number('true')` is `NaN`, and the learnability chip went through `Number()`.** The filter matched every row and the page looked unfiltered, because 「nothing was excluded」 is exactly what an unfiltered list looks like.
  - **A row taken out of `Object.entries(moves)` has no `.id` of its own**, so `learners[String(move.id)]` was `learners["undefined"]` and the entire learner panel rendered empty. **No exception, no console output, and every static assertion about the file passed** — §3.I's shape one indirection down.
  - **The "default viewport" was captured lazily, while the 390px override was still in force**, so the restore asserted 「back to 390」 and failed on a correct page. §4 records the same mistake in `check_spectrum_browser.mjs`; capture it at module load, before any override exists.
- **THE FILE HUNG AFTER PRINTING `PASS`, which is §3.Z's exact symptom.** The CDP WebSocket and the spawned Chrome keep the event loop alive, so falling off the end is not exiting. `check_home_hero_browser.mjs` hung 12 minutes in tier B three times for this, and the watchdog added to fix it never fired under the condition it was written for. The fix is one `process.exit(0)`.
- **`power: 0` IS A SENTINEL IN 16 ROWS AND A NUMBER IN ONE.** 硬壓 is physical and its power scales with the target's remaining HP from 0 to 100; the other sixteen are status moves where `null` would read the same. **Normalising 0 to null would have erased a documented mechanic** — §3.B1's rule applied to a sentinel that is a sentinel in 16 places and a value in 1. Named as `VARIABLE_POWER_MOVES` so a second one goes red. **`accuracy: 0` is 必中**, and 迅子利刃's own effect text says 「必定命中」 two lines below, so it renders as 必中 and never as 0%.

The fact rows are ABSENT rather than 無 — §3.B2's distinction, enforced by `fact()` returning `''` for null.
- **THE PAYLOAD SPLIT IS ASSERTED IN BOTH DIRECTIONS.** `moves.html` loads `move_learners_count.json` (54 KB) for 「N 隻可學」 on 919 rows; `move.html` loads `move_learners.json` (424 KB) for the list. Asserting only the half that saves bytes would pass on a `moves.html` that also pulls the index.
- **`indent=2` IS NOT APPLIED TO THE TWO NEW INDEXES, and that is a decision with a reason.** Neither is ever hand-edited — both are inverted out of `learnsets.json` by the pass that just ran — so the diff-readability the other two files buy does not apply, while the cost does: it puts every Pokémon id on its own line and inflates `move_learners.json` from 409 KB to 1130 KB. **A file whose whole reason to exist is to be smaller than another file should not pay a 2.8× formatting tax to look like its neighbours.**
- **THE SHADOW BLOCK IS EXCLUDED BY ID, AND THE SCRIPT ASSERTS THE REASON RATHER THAN THE EXCLUSION.** A `startsWith('shadow-')` test is wrong — 剪刀黑星 Shadow Claw, 暗影 punches Shadow Punch, 暗影球 Shadow Ball and 暗影之力 Shadow Force are ordinary moves that begin with the same four letters. What is asserted is that the excluded block is still unnameable, unlearnable and unflavoured, so it goes red the moment one of those stops being true.

**THE LEARNER CARDS SHOW THE OFFICIAL SCARLET/VIOLET ARTWORK, and there is NO VERTICAL OFFSET ON THIS PAGE** — §3.E records the measurement and why `types.html`'s `translateY(-23%)` must not be copied here. The user chose the bottom-anchored framing deliberately. **There is no 「顯示全部」 cap either**: the worst case is 守住 with 1,003 learners, and the page loads all of them. 58 of the 919 moves exceed 300 learners and 26 exceed 500, but the median is 27 and those are all 守住/替身/睡覺/挺住 — moves a reader reaches on purpose, once.

**Guarded by:** `check_moves_data.mjs` (127,868 checks, 0.1 s — the split, both inversions, every field's range, and the variable-power exception) + `check_moves_page.mjs` (184, 0.2 s) + `check_moves_page_browser.mjs` (89, 30 s) + `test_check_moves_page.mjs` (27 mutation cases, 2 s). **The browser half still has no harness of its own**, which is the same trade §3.Z priced: each browser case would boot its own Chrome, so the mutations live in the static half and cover the same claims from the other side.

### AB. `types.html` Is One Page And Moves Is Two — And The Payload Argument Runs The Wrong Way

Asked and answered, so it does not have to be re-litigated: **do not merge `move.html` into `moves.html`, and do not split `types.html` into an overview plus a `type.html?type=`.** Both structures are already right. **The intuition that would change them — 「one file is smaller than two」 — is the one number here that does not measure the thing**, and the measured payload runs the *opposite* way.

**This is a decision record rather than an incident: nothing here has broken, and there is no defect shape behind it.** It is written down because both structures look arbitrary from the outside, and the obvious next question is the wrong one.

| view | loads | bytes |
| :--- | :--- | ---: |
| `types.html?type=fire` (one file) | `type_profiles` 67K + `pokemon_data` **2.8M** + `moves_zh` 496K + `abilities_zh` 19K | **~3.4 MB** |
| `moves.html` (list) | `moves_zh` 496K + `move_learners_count` 54K | **550 KB** |
| `move.html?move=X` (detail) | `moves_zh` 496K + `move_learners` 424K | **920 KB** |

- **SPLITTING `types.html` SAVES 86 KB OF 3.4 MB — 2.5%.** The detail view needs `pokemon_data.json` (the roster) and `moves_zh.json` (the move chips) either way; `type_profiles.json` + `abilities_zh.json` are the 86 KB. A split would give a 2.87 MB overview and a 3.38 MB detail page, and the only thing bought is a second document. **So `types.html` being one file has never been a bandwidth decision** — which is the premise the merge argument silently rests on.
- **MERGING THE MOVE PAGES COSTS +424 KB ON THE LIST, A 77% INCREASE.** `moves.html` would load `move_learners.json` for a learner list a reader may never open: 550 KB → 974 KB, 393 → ~730 lines, and two mutually-exclusive render roots in one file.
- **THE DECIDING VARIABLE IS CARDINALITY AND SHAPE DIVERGENCE, NOT FILE COUNT.** 18 types, all the same block structure (roster / effectiveness / abilities / moves / trainers) → one template applied 18 times. 919 moves, where the list wants filter + search + URL state and the detail wants four learn-method tabs + a learner roster → two templates, two files. **Expect this shape whenever a param'd detail view is proposed or removed: ask how many records there are and whether the list and the detail want the same shape. The byte count is the last question, and here it is the one pointing the wrong way.**
- **BOTH MODELS ARE FULL-PAGE RELOADS TODAY, so the single file buys no switching speed.** The type links are `<a href="types.html?type=...">` (types.html:1112), not an SPA swap. All a shared document saves is re-downloading markup the HTTP cache already holds — so 「一個檔案切換比較快」 is not a benefit this project has, at either end.
- **ON A DEEP LINK THE OVERVIEW IS CHROME AROUND THE DETAIL.** `renderTypeDetail()` rewrites the hero — kicker, title, lede and tint all become the type's (types.html:1217-1219) — while all 18 type cards and the 18×18 chart still render underneath. So `types.html?type=fire` is 「整張表包著一個詳情區塊」, and a reader who followed one link paid for the whole chart. **That is the honest cost of this structure and it is a real one**; the measurement above is what says the alternative costs more.
- **THE NAV ROW IS THE ONE THING ONLY A SEPARATE DOCUMENT CAN HAVE.** `move.html` carries no nav row and no `pages` entry, exactly as `detail.html` does (§3.AA). Merging it would force it into `moves.html`'s navigation structure.

**Guarded by:** nothing, and that is the right state for a structural judgement — it is a decision, not a claim with a threshold. **What IS guarded is the two-file split's precondition**: `check_moves_page.mjs:109,113` asserts each page loads only its own half of the payload, in both directions (§3.AA's "payload split is asserted in both directions"), so the split's *reason* cannot quietly stop being true even though nothing checks the file count. **Nothing would notice `types.html` being split into two files, and that is the intended coverage** — a reviewer is what guards it, and the table is here so they do not have to re-derive it.

**Note that this section is deliberately NOT counted in §3's opening list of unguarded rules.** That list says 「four of the twenty-five」, and §3.J's own rule is that a count typed into prose goes stale; §3.V's 「35 → 36 prefixes」 is the receipt. **So: the count in that sentence was already unreliable before this section, and editing it here would replace one unverified number with another.**

### AC. `abilities.html` / `ability.html` — 314 特性, And The Holder Map Cannot Come From Our Own Roster

Two pages, split because §3.AB's rule says so: 314 records, and the list wants filter + search + URL state while the detail wants an effect and a species roster. **`ability.html` carries no nav row**, exactly as `move.html` and `detail.html` do — it is reached by drilling in from a card, and `check_abilities_page.mjs` asserts that absence, because an assertion that a name is *present* cannot express "must not be" (§3.W's `role="img"` lesson).

**THE USER CHOSE 374 AND THE ANSWER IS 314, and the gap is not a preference.** PokeAPI holds 374 abilities; the 60 at id ≥ 10001 have **no name in any language, no effect text in any language, and zero holders anywhere in the API**. They are the ability-side twin of `fetch_moves.py`'s `SHADOW_BLOCK_START`, and §3.AA's rule is applied verbatim: **excluded by id, with the REASON asserted** — the fetcher measures and reports all three zero counts, so the day upstream gives one of those rows a name, a description or a holder, the block has to be re-admitted rather than silently dropped again. Shipping 60 blank rectangles would have put a 16% hole in a page whose entire subject is the description.

- **THE HOLDER MAP IS READ FROM POKEAPI AND CANNOT BE INVERTED FROM `pokemon_data.json`.** Our roster references 284 of the 314; the 30 it does not are **form-exclusive** — 原始大地 belongs to Primal Groudon, 對決 to Mega Evolutions, battle-bond to Greninja-Ash. `pokemon_data.json` cannot supply them: **Groudon and Zacian both carry `forms: []`**, and the one forme record it does keep (Gyarados, `{id, base_id, form, name_en, filename}`) **has no `abilities` field**. So `ability_species.json` is built from PokeAPI's `ability[].pokemon[]`, and the guard that keeps it honest is the round-trip in `check_abilities_data.mjs`: every (species, ability) pair `pokemon_data.json` claims must appear in the index with the right hidden flag.
- **THE BASE SPECIES IS RESOLVED BY `species.id`, NEVER BY MATCHING NAMES — and the first attempt matched names.** `/pokemon/{name}` returns `species` as a *stub*, so the id is the trailing number of its URL (what `fetch_moves.py`'s `resource_id()` already does). Name matching looked like missing data rather than like a wrong key: **14 ordinary species failed it**, and twelve of those were our own spelling errors (the bullet below). Nothing in the output looked wrong; the abilities those 14 hold were just quietly reported as form-only holders. **After the twelve corrections the figure is 2** — `Farfetch'd` and `Sirfetch'd`, where the disagreement is only the apostrophe (PokeAPI uses `’`), which is not a typo and does not change the slug. The resolution stays on `species.id` anyway: two disagreements are enough to justify a key that needs no string matching, and the next one would otherwise be a third.
- **`Farfetch'd`'s ASCII APOSTROPHE IS DELIBERATE and must not be "corrected" to PokeAPI's typographic `’`.** It is the spelling the official International List carries, and the slug is `farfetch-d` either way — `pokemonSlug()` folds both to the same separator — so changing it would buy nothing and lose the one source this project treats as authoritative for names.
- **TWELVE SPECIES CARRIED A MISSPELLED ENGLISH NAME, and it was a reader who found it, not a checker.** `#591` is `"Amoongus"`; PokeAPI's id 591 is `amoonguss`. **Every PokeAPI-based lookup on that species misses it by name**, and the site's own slug is `amoongus`, so `detail.html?slug=amoonguss` was a dead link. The full audit then found eleven more — Houndoor, Tailow, Minum, Scoliopede, Gumchoos, Palosand, Thwakey, Skowvet, Zamazanta, Meowscarda, Toadscruel — **every one a letter transposition, and every one changing the slug**, so twelve species were unreachable by their canonical URL. All twelve are now corrected in `data-sources/International List of Pokémon Names.xlsx` (the defect was in the SOURCE; `enhance_pokemon_data.py` copied it faithfully) and applied through to `pokemon_data.json`, `evolution_chains.json`, `graph_data.json` and `ability_species.json`. The cross-check is free and worth stating: these are **exactly the 14-species drift set this section's previous bullet describes**, found independently two weeks apart by two different methods.
- **THE DEFECT WAS IN THE SOURCE XLSX, NOT IN `pokemon_data.json`, and that is why the fix did not go through `enhance_pokemon_data.py`.** §5's rule is that a generated file is fixed at its generator — but the generator was faithful here, and **running it produces a DIFFERENT ROSTER**: 1,350 records against the committed 1,025, because one of its CSV inputs now carries the 325 formes too. **So `enhance_pokemon_data.py` does not currently reproduce `pokemon_data.json`, and that is an open question this project has not answered.** Until it does, the twelve corrections were applied as guarded text edits, each gated on the old string appearing exactly once in the file, and the roster was verified byte-identical outside those 36 fields. **A generator that cannot reproduce its own output is a bigger problem than the twelve typos it caused**, and it is the reason a hand-edit is defensible here rather than the usual sin.
- **`es` AND `it` TRACK `en` FOR THOSE TWELVE, because they never had a translation.** 1005 of 1025 species have `es === en`, so "no localised name → copy the English string" is the file's own convention and the corrections follow it. `#889`'s typo had additionally propagated into `fr` and `de`, where it is also corrected — Zamazenta is spelled identically in every language, as Zacian is.
- **THE ROW CARRIES THE ROSTER'S OWN `nameEn`, NOT POKEAPI'S SLUG, because the canonical slug helper disagrees with PokeAPI for 14 species.** `pokemonSlug()` turns `"Farfetch'd"` into `farfetch-d` while PokeAPI calls the species `farfetchd`; storing PokeAPI's string would dead-link 14 species. `nameZh` rides along so the holder grid is not a page of English names. **14 dead links is the number that matters — each is a card that renders and goes nowhere.**
- **THREE COUNTS MEAN THREE DIFFERENT THINGS AND THE PAGE MUST NOT CONFLATE THEM.** `holders` counts PokeAPI Pokémon including formes (**47** for 威嚇), `speciesCount` counts distinct base species (**37**), and `formCount` is the difference. Asserting only one passes a page printing 「47 隻寶可夢」 for an ability 37 species actually have.
- **THE EFFECT SENTENCE HAS TWO PROVENANCES, AND THE SPLIT IS NOT A ROUND NUMBER.** 267 of 314 carry PokeAPI's zh-hant flavour text; **47 carry no Chinese effect at all** and fall back to `effectEn`, which is PokeAPI's English kept in **its own field** — §3.D's `blurbEn` rule, because merging English into `effect` would pass it off as our translation and shipping the row blank would print nothing on 15% of the page. **`s2twp` fires 0 times** and the row is pinned at 0 rather than deleted, so the first ability that does convert turns the checker red instead of silently switching provenance under a page that renders two languages. **Three abilities have no Chinese NAME** (`eelevate`, `fire-mane`, `aura-guard`) and render `nameEn` with a visible italic marker — three is a measured number, not a list of things someone remembered.
- **ONE ABILITY SHIPS WITH NO HOLDER AT ALL, and the empty state is the honest one.** 面影輝映 belongs to a Terastallized Ogerpon, which PokeAPI has no Pokémon record for. It is a real ability with a real description, so it stays; a hard `speciesCount >= 1` would delete it, and §3.AA's rule is that a named exception list is for upstream quirks, never for our own omission.
- **A BASE SPECIES CAN LEGITIMATELY APPEAR UNDER BOTH FLAGS, and folding by `baseId` alone invented a conflict.** Rock Head is Kantonian Marowak's REGULAR ability and Alolan Marowak's HIDDEN one, so the index carries `marowak`, `marowak-alola` and `marowak-totem` — **three rows, one `baseId`, two flags**. `splitAbilityHolders()` folds by base species and marks it hidden once any forme is, keeping the forme names so the page can say *why*. **The checker matches the (baseId, isHidden) TRIPLE**: collapsing to one row per baseId and keeping the last fails on 857 pairs that are all correct.
- **HIDDENNESS IS `slug === hidden_ability`, NOT "came from the `abilities` list"** — a species lists its hidden ability in BOTH arrays (Houndstone: `["sand-rush","fluffy"]` with `hidden_ability: "fluffy"`, and PokeAPI agrees: fluffy is slot 3). Deriving hiddenness from which array a slug was found in fails on 857 correct pairs, **which is how a checker teaches its reader to ignore it**.
- **`abilities.css` IS `ab-`-PREFIXED AND MOUNTED ON THESE TWO PAGES ONLY**, for §3.B1's reason. It must not use `--page-accent`: shared.css declares it on the `.header-*` modifiers, so in a body it resolves to the inherited value and reads as a colour that happens to be wrong. **The check reads the comment-stripped copy**, because the file's own header comment names the token to explain the ban — §3.S's fix again. The holder images carry **no `image-rendering`**, for §3.E's reason: the house convention is for *upscales*, and 96→56 is a downscale by a non-integer factor.

**THE HOLDER ARTWORK IS THE SCARLET/VIOLET SET, NOT THE 96px SPRITE, and it costs no payload.** `hasSv()` and `svUrl()` are both keyed on the id alone, so `ability.html` gets official artwork from the `baseId` the holder index already carries and **still never loads `pokemon_data.json`** — §3.AB's slim-index decision survives the change intact, and the sprite path stays as a dormant fallback with move.html's sr-only note. All 1,025 holder species have artwork, so that fallback never fires today (§3.E's rule: the code stays so an upstream removal degrades into the 96px floor rather than a broken image). **`object-fit` and `object-position` are asserted TOGETHER, never apart**, for §3.E's reason: the SV set is bottom-anchored with the space above it, so `contain` alone passes a "does it fit" assertion while leaving the subject ~3.7px above the card's own baseline. **There is deliberately no `translateY`** — `types.html` needs one because its chips pair image and name on one line, these cards do not.

**A SOLID ACCENT FILL NEEDS `--on-accent`, AND `--text-primary` IS THE WORST POSSIBLE PARTNER IN BOTH THEMES — because the fill inverts with the theme.** `--accent-gold-surface` is opaque: amber `#f5c542` in dark, Poké Ball red `#b3122a` in light. `--text-primary` is near-black in light and near-white in dark, so it lands on the *dark* end of the fill every time. Measured from decoded pixels, not from the token values:

| | `--text-primary` | `--on-accent` |
| :--- | ---: | ---: |
| light, white/black on `#b3122a` | **2.56:1** ✗ | **6.92:1** ✓ |
| dark, near-white on `#f5c542` | **1.44:1** ✗ | **11.62:1** ✓ |

It shipped that way on both the `有隱藏特性` badge and `.ab-chip[aria-pressed='true']`, and a reader reported the badge as unreadable. **The same rule was wrong on `moves.html`'s pressed chip all along** and is fixed here too — three rules, one cause. `algo.css`'s `.al-chip[data-checked="true"]` already had it right and is the precedent. **The guard asserts the PAIRING, not a token**: a rule may use either colour, as long as a gold fill does not sit under a primary-text colour, and it is read against the comment-stripped copy because both files' own comments now name these tokens to explain the rule (§3.S in JavaScript — the same trap the first draft of the payload assertion walked into, where testing `!/pokemon_data\.json/` went red the moment a comment named the file to explain why it is avoided, so that one now looks for the *load* rather than the string). **Both fills are solid, with no alpha, gradient or `backdrop-filter`, so §3.C's "measure from pixels" rule has nothing to add here** — and the measured 6.92 / 11.62 came back identical to the arithmetic, which is the check that saying so was true rather than convenient.

**THE PAYLOAD SPLIT IS ASSERTED IN BOTH DIRECTIONS.** `abilities.html` loads `abilities.json` (135 KB) only — **every count it prints is already baked in**, and loading the 379 KB holder index would be 8× the payload for a number it already has. `ability.html` adds the index and **neither page loads `pokemon_data.json` (2.8 MB)**, because the index carries the name and the id the holder grid needs. §3.AB's reasoning applied one level down: the split is only defensible because the half that stays is genuinely unnecessary.

## 4. Verification & Testing Commands

Run regression checks whenever modifying data structures, selectors, or color logic.

**`.cache/` IS THE SKIP CACHE, AND DELETING IT COSTS ONE SLOW RUN AND NOTHING ELSE.** `scripts/check_all.mjs` writes `.cache/check-state.json` — one content hash per checker over the files it declared in `inputs` (globs expanded first), plus the previous green run's duration and timestamp. Unchanged inputs mean the entry is skipped and reported with the cost it last cost. It is the whole reason a second full run is **0.0 s** rather than 87 s, and the gitignored ~10 KB is the cheapest performance work in the project. Three things about it are named because each is a way the mechanism can be green and wrong:

- **A FAIL never refreshes an entry**, so a `last 6.0s` is always a green run's measurement. A duration remembered from a failing one would be the one number on the page that does not describe a passing check.
- **`--force` exists for a checker that passed for a reason other than its inputs** — a missing Chrome, a stale server. The cache trusts the last green result on this machine and nothing else.
- **A FAIL is not a skip either.** Nothing is written on the failure path, so the next run re-runs it rather than remembering it as answered.

`.cache/recorded-inputs.json` is written only by `--prove-inputs`, and `.cache/algo-neg/` is a harness scratch tree rather than state — a leftover there means some run was interrupted, and deleting it is harmless.

**`node scripts/check_all.mjs` runs everything, and skips whatever cannot have changed.** The suite is **72 manifest entries run by hand** — and that total is `--help`'s, not this sentence's: the group table there sums to it and a full run's own footer (`62 ran, 6 skipped`) sums to it again. **A count typed into this file is exactly what §3.J says goes stale, so the derivation is the two places that can be re-run rather than the one place that cannot be re-read.** The checker/harness split is deliberately not restated here for the same reason; `--help` prints each group and its most expensive entry. **`check_graph_chip_network.mjs` (§3.V) is one of them because 精選分類 had no reader anywhere in the suite before it** — the chip filter drew 93 sprites with 0 edges between them and the only checker for that page is `manual: true` **and** `serial: true`, so it is both the most expensive entry and the one least likely to run. And the entries are not equally expensive: `check_gen1_apu.mjs` is 5.6 s of which 4.5 s is one pass over the 151-species corpus at 1,048,576 Hz (146,311,704 samples). **Measured on this machine: 166 s of checker time cold, finished in 88 s of wall clock now that the runner has two tiers, and 0.0 s of work when nothing relevant moved.** Over half of that cold run is headless Chrome — the 11 `needsServer` CDP checkers plus `test_check_sorting_page.mjs`, whose 25 cases each boot one — and 20% is four CPU-bound pure-Node entries. The other 42 entries total ~19 s, so a "slow suite" is really a handful of browsers. The four spectrum scripts add ~9 s cold, and two of them (`check_spectrogram_port.mjs` and its mutation suite) need the venv, so a machine without it skips those with the reason printed rather than passing.

- **There is deliberately no `--quick` flag on any checker.** `check_gen1_apu.mjs` already says why: "a supported way to skip the conformance comparison is exactly how it would stop happening." A flag is a promise the reader has to remember to keep. The skip lives in the runner, is derived from file CONTENT, and a skipped checker says so on its own line with the reason.
- **Every manifest entry gets ONE line with a time column, and the column makes three different claims.** `6.0s` is measured this run, `last 6.0s` is a cache hit reporting the previous green run's measured duration (stored as `${name}~` beside the key and the `@` timestamp), and `-` is a row that never ran — a missing script, or a CDP checker with no server on `:5500`. One `row()` helper emits all of them, because five call sites each padding their own column is five chances for the table to drift; it pads the detail but never truncates it, because an `ok` line must fit 56 columns while a skip naming the Runtime Server rule must keep that sentence whole. Two traps are named in the source: the durations live in a **non-cached region of the output's meaning, not in `budget`** — a cache hit's number is real but was not paid for this run, which is why the legend says so and the summary total still sums only what ran; and the cached value is read with `== null`, because `Number(null)` is `0` and would print `last 0.0s` for every entry written before durations were stored. A `▶` line precedes each run because `execFile` buffers — without it, the 10 s of `test_check_sorting_page.mjs` is a terminal that looks hung.
- **The input lists are PROVEN, not reviewed.** `--prove-inputs` runs each checker under `scripts/lib/record-inputs.cjs`, a CommonJS preload that records every repo file it opens, and fails if the recording disagrees with the manifest. Miss one file and the checker is skipped after that file changed, so the run is green having verified nothing — strictly worse than no cache, because it looks like coverage. A grep cannot answer it, for the reason `check_nav_pages.mjs` documents about `rg -l initHeaderNav *.html`. Two directions are both required: **read but not declared** (the dangerous one) and **declared but not read** (a typo or a checker that stopped reading something). Proven by breaking the manifest in a scratch copy — both fire.
- **It is a `-r` preload and not `--import`, and the difference is silent.** Node snapshots a builtin's ESM named exports when the module is first linked, so `import { readFileSync } from 'node:fs'` binds the ORIGINAL function and a patch applied by an `--import` module afterwards is never seen. Measured: with `--import`, `check_color_palettes.mjs` recorded five files and missed both JSON tables it plainly reads. A CJS preload runs before the main module is linked, so the same patch is picked up by every named import.
- **What is always in the key, whatever a checker declares:** the checker itself, the checker a negative harness exists to attack, every file in `scripts/lib/`, and `check_all.mjs` itself. Editing a checker therefore invalidates its own entry with nothing extra for a maintainer to remember, and changing the cache's own rules cannot reuse entries the old rules produced.
- **Three entries are honestly unverifiable and say so on every run.** `check_gen1_page.mjs` and `check_cries_browser.mjs` open NO repo file — their pages arrive over HTTP from Live Server — so their input lists are read off the HTML by hand. **`test_check_js_syntax.mjs` (§3.I1) opens no repo file either, and for the opposite reason: it writes its own one-page fixture rather than copying the 23 real ones, so its `inputs` names only the checker it attacks, which §4 already keys on unconditionally.** That is the weakest claim in the manifest and it is printed as such rather than hidden behind a green tick. The recording is what *establishes* that they touch nothing, rather than a comment claiming it.
- **`check_spectrogram_port.mjs` prints `SKIP` and EXITS 0 when `../.venv` is absent**, so a machine without Python reports that entry as green. Read the line, not the exit code, when the venv matters — the same reason §3.G5's audit lives in the runner rather than in a fixture.
- **Also named, because each is a way this can be green and wrong:** a file read only on a branch NOT taken during the recording is not seen (mitigated by the checker's own hash being in the key); existence probes are keyed on `path:size`, not content; files over 256 KB — the cry corpus, the GLBs — are keyed on `path:size:mtime` rather than content; and the cache trusts the last green result on this machine, so `--force` exists for a checker that passed for a reason other than its inputs.
- **Groups are `algo`, `color`, `cry-apu`, `cry-data`, `cry-page`, `data`, `home`, `model`, `nav`, `sort`, `type`** — eleven. `home` is `index.html`'s hero and is its own group because one half is static and one boots Chrome; putting a ~34 s browser checker inside `nav` would make the cheapest group in the suite the most expensive one to reason about. `--skip=cry` covers `cry-apu`/`cry-data`/`cry-page` without naming them; `--only=`, `--force` and `--no-cache` also work. `node scripts/check_all.mjs --help` prints them with each group's last measured cost, so the runner can be asked what it costs rather than read to find out.
- **The runner runs TWO TIERS, both pooled at three — and TWO Tier B entries are flagged `serial: true` and opt out.** Tier A is the 59 entries not marked `browser: true`; Tier B is the 13 browser entries, of which **`check_graph_browser.mjs` and `check_life_browser.mjs` run alone**. Both go through `lib/pool.mjs` and both print **after the drain, in declaration order** — §3.G7's contract, because an order that follows the scheduler cannot be diffed between two green runs. **The two halves of Tier B are RE-INTERLEAVED into declaration order before printing, and that is load-bearing**: printing the serial half before the pooled half would make the report depend on which entries carry the flag — §3.G7's contract obeyed inside each half and broken across them. The serial half runs first so it is never idle-waiting on the pool. Tier B used to be serial throughout: see the next two bullets for why that stopped being true, and why two entries came back. Measured: **~99 s of wall clock became ~68 s**, while the reported checker time went *up* by about 10 s, because concurrent browsers contend (`check_life_browser.mjs` is 5.1 s alone and 13 s in a pool of three). **The two numbers are different claims and the legend says so** — read the wall-clock figure, not the total, when you are waiting for one.
- **`serial: true` EXISTS FOR TWO ENTRIES, and the §4 note that un-serialised Tier B is not evidence it does not apply.** `cdpPort()`'s pid-derived windows overlapped, which retired Tier B's serial run — that argument is entirely about **colliding ports** and says nothing about CPU or GPU. `check_graph_browser.mjs` measured **3 of 3 failures pooled and 3 of 3 passes standalone**, same tree, same server, same machine; Chrome's own stderr says why (`CVDisplayLinkCreateWithCGDisplay failed. CVReturn: -6670`, repeated, on a 1,346-node page at 60fps) and the CDP side reports it as the **byte-identical** message a real navigation produces. §4 already accepts contention as a *cost*; this is not a cost, it is a **failure**, and **a red that appears only when the pool's draw puts a second full-corpus WebGL graph beside it trains a reader that red can mean nothing.** It costs ~6 s of wall clock, and the harness beside it stays pooled because it serves a trimmed fixture. **The fix was verified both ways — 3 pooled failures on a `git stash`ed clean tree — because "it passes now" is not evidence of anything.**
- **`browser: true` is a seventh `needsServer`-shaped flag, and the two sets differ by one.** **Twelve** entries need the Runtime Server. **Thirteen** are browsers. The extra is `test_check_sorting_page.mjs`, which boots Chrome 25 times without needing the server — so a split keyed on `needsServer` would have put the single most expensive harness into the pool.
- **NO CHECKER USES A COMPUTED DEBUG PORT ANY MORE, so `assertPortFree()` is GONE and Tier B can be parallel.** Every browser launches with `--remote-debugging-port=0` and reads the number back from `<profile>/DevToolsActivePort` via `waitForDebugPort()`. The OS assigns a port nothing else was given, so the collision class is deleted rather than tolerated. This matters because `cdpPort()` — `base + (pid % 120)` — overlapped: **20 of its 21 base pairs**, once the 120-wide window is counted, and a collision was a ~1-in-120 flake per pair that `assertPortFree()` turned into a loud abort. Retiring it is a **net gain**, not a removed guard: its job was to stop a checker driving a browser it did not start, and §3.J's orphan incident becomes unreachable rather than merely unlikely. **Two schemes were tried first and both were worse than the pid-derived one**: an explicit `9600 + index` is deterministic, so one interrupted run poisons that index for every later run. The history is in `waitForDebugPort`'s docblock.
- **`--only` is a PREFIX MATCH and is REPEATABLE**, and it was silently neither-correct-nor-wrong until recently: `flagValue()` used `argv.find`, so `--only=a --only=b` ran only the first group and reported a clean `0 failed`. The failure mode is the point — nothing said a group had been ignored. `--only=a,b` and `--only=a --only=b` now select the same entries.
- **Twelve entries need the Runtime Server and all THIRTEEN browsers are `manual`.** The `needsServer` set is the eleven browser entries that serve a page plus `check_types_browser.mjs`; the `manual` set is the thirteen browser entries, which since §3.G9 has been exactly the `browser: true` set. **`manual` does NOT skip execution** — it is read in three places, all inside `--prove-inputs` — so marking an entry `manual` costs nothing in runs and is what makes the runner print the hand-read-inputs caveat instead of ticking the row. §3.X's checker is the first to need that distinction written down. **That coincidence is a trap rather than a coincidence** — `manual` is what makes the runner print the caveat about hand-read input lists instead of ticking the row, so an entry that grows a repo-file read without losing `manual: true` is silently under-reported. **The runner probes with `CRY_PORT` only, while those nine honour `CRY_PORT`, `LIFE_PORT`, `SORT_PORT` and `OUTFIT_PORT`** — so overriding one without the others leaves the probe disagreeing with the checkers it is gating.
- **THE PROBE MUST NOT BE `fetch()`.** A liveness probe wants no connection pool: `fetch` runs on undici, which holds the socket open for keep-alive, and an open socket keeps the event loop alive. Measured, same URL and same 1.5 s ceiling: **`fetch` finished its work at 31 ms and exited at 6033 ms; `http.request` with `agent:false` exited at 29 ms.** The symptom looked like a broken skip cache — a fully-cached run took 6.5 s of wall clock to do 0.09 s of work. It also must not read `res.ok`, which is a `fetch` `Response` property and `undefined` on an `IncomingMessage`: that version answered false against a live server and skipped all six browser entries without reporting an error.
- **`.cache/check-state.json` can hold MORE KEYS THAN THE MANIFEST HAS ENTRIES.** A retired entry is left behind on write, because the write path copies the previous state and adds to it. `--help` reads the same `~` durations, so a ghost is a cost figure on the page for a check that no longer runs.

**AND THIS IS NO LONGER ADVICE — running the whole suite is forbidden on this machine.** It used to read 「AND IF YOU ALREADY KNOW YOU ONLY NEEDED ONE GROUP, RUNNING THE WHOLE SUITE IS STILL CHEAP」, which was true of the skip cache and false of the machine: a *cached* second run is 0.0 s, but the first run after an unrelated edit still pays for every browser checker whose inputs moved, and **all eleven are headless Chrome**. See the rule at the top of this file. What survives of the original thought is only the narrow half — **`--only` is for the case where you want the answer *now*, it is not a correctness measure, and `--force` on a group you did not touch buys nothing.** The way to verify a change is to name the checkers it touches:

```bash
node scripts/check_moves_data.mjs && node scripts/check_moves_page.mjs   # 0.1s + 0.2s, no browser
```

A for-loop over the affected names is equally acceptable and is what a session should do when a change spans several entries — the list comes from the table above, and `node scripts/check_all.mjs --help` prints each group's cost when the file in your hand is not in any row.

**`--only=cry` IS A PREFIX MATCH, NOT A LIST, and that is why it is the right default.** `inGroup()` tests `group === f || group.startsWith(f + '-')`, so `--only=cry` picks up three groups and `--skip=cry` drops three, without anyone maintaining a fourth list of what "cry" means.

**ONE RUN CONFIRMS A FIX; LOOPING IS NOT THE DEFAULT.** This is the rule the reader asked to have written down, because an agent's instinct is to run something five times and call it stable — so the instinct is named here rather than left to be argued out of.

- **After changing a checker or a page, ONE run is the evidence.** If it is green, the change is verified. Do not run it again "to be sure".
- **THE REASON, and it is the same one as `--quick`:** a second run proves nothing about the change, because nothing changed between the two runs. What a repeat measures is the ENVIRONMENT — load, contention, a leftover process — and a thing that passed once and failed once under the pool has told you it is flaky, not that it is fixed. Reading it that way is how a real defect gets "fixed" by adding a timeout (§3.Z's own history: three separate timeouts in one browser checker, each papering over the previous one).
- **WHAT A LOOP IS FOR, and it is narrower than it looks.** Looping is for a check you believe is **inherently** timing-dependent and want a pass RATE for: `check_graph_browser.mjs` was measured at "3 of 3 failures pooled, 3 of 3 passes standalone" (§3.G9) and that ratio was the finding. A single red under the pool is not a rate. If you cannot say in one sentence which number the loop is producing, do not run it.
- **IF IT FAILED, DO NOT RE-RUN TO SEE IF IT PASSES.** That is the specific thing to avoid: a red followed by a green reads as "flaky, fine", and `check_sorting_page.mjs` already has one recorded 2-of-34 that way (§3.G4). Re-run it **only** with `--force` and **only** to find out which of two things it is — a real regression or contention — and say which one you concluded. If neither, that is the answer.
- **A HANG IS NOT A FLAKE AND IS NEVER CONFIRMED BY A RE-RUN.** `check_home_hero_browser.mjs` hung for 18 minutes in tier B once, holding the other nine browser entries open, with every individual wait in it already on a ceiling. It now carries a 4-minute watchdog that names the section it was in and exits 2. **If a watchdog fires, the check is broken and the fix is in the checker** — raising the timeout is the one move that is certainly wrong.

**WHAT NOT TO DO.** There is no `--quick`, and §4's rule says why: a flag that skips a check is a promise, and the promise is what stops being kept. When `test_check_gen1_apu.mjs` had to come out of the suite, it came out by being **removed**, with the file left runnable and the cost of the removal written down — not by a flag. If a check is too slow to run, the two legitimate moves are to make it cheaper (§3.G5's fixture and pool work) or to take it out of the manifest and say what is no longer proven.

**AND WHEN YOU DO NOT KNOW WHICH GROUP OWNS A FILE, ASK.** `node scripts/check_all.mjs --prove-inputs` answers "which checkers read this file" from the recording rather than from a guess, and it is the same recording that keeps the cache honest. A grep cannot: `rg -l initHeaderNav *.html` lists `sorting.html` because its import names the symbol, and two other pages only because they mention it in a comment.

**WHAT IS LEFT IS ONE ENTRY.** `test_check_graph_browser.mjs` at 40 s is now larger than every other entry combined, and its cost is four sequential Chrome boots. The two ways to cut it are to drop a case (four to three buys about 8 s and gives up a proven assertion) or to reuse one browser across the cases, which needs the checker to accept an external Chrome. Neither is done. Everything else in the suite is 63 s of work in 35 s of clock.

**What is left is a browser or it is the APU.** Of the ten most expensive entries, five are CDP checkers or the sorting checker, one is `check_gen1_apu.mjs`'s 151-species corpus render, and the rest are harnesses whose cost is one browser boot each. §3.G7 removed every harness-shaped cost that was removable; what remains is the work itself.

**A mutation case is only as expensive as the thing it is attacking**, and that is now the whole question when a harness looks slow. `test_check_color_match.mjs` went **42 s → 2.2 s** across two commits, and neither commit was about a hard case — both were an unexamined default. The first was that its 28 cases ran sequentially (§3.G7). The second was that the checker it attacks spent 1,118 ms of its 1,310 ms scanning all 4,545 corpus colours to re-derive a frequency that has not moved since the corpus was 6,148 colours; the figure is now a pinned `6`, and the rule it documents is still exercised by the `#20317b` assertions beside it. `test_check_sv_index.mjs` went 22 s → 3 s because it copied 2,250 images into a fresh tree per case.

**So the question to ask of a slow check is "what is this actually computing?", and the answer is usually in the profile rather than in the code.** Timing each `check()` individually found the one that mattered in a second; the section headings said `primary-first ranking`, which reads like arithmetic on a few species and is in fact a full-corpus sweep. §4's rule about a checker that prints a description whether it passes or fails has a sibling here: **a check's name is a claim about its cost, and the name is not evidence.**

## 6. Git Workflow Rules

- **No Push Without Explicit Permission**: Commit freely, but **never run `git push`** — not for a first push, not for a branch, not for a fix, not because CI is red. The remote is only pushed when the user says so in their own words, and a request to commit is not a request to push. When it is unclear whether more work is coming, assume it is and stay local. Check what is pending with `git log --oneline origin/<branch>..HEAD`.
- **Atomic Commits**: Commit at the end of every coherent unit of work (e.g. one bug fix, one component layout, one page enhancement).
- **Batch by direction, not by file**: One commit per *direction of change*, and a direction may legitimately touch several files — a fix plus the test that proves it, a refactor plus the docs that describe it, or one invariant tightened across every checker that enforces it. Splitting those apart produces a history where no commit is independently verifiable, which is the thing atomicity is for. Do not split work that only makes sense together, and do not merge work that could be reverted separately.
- **The line is unrelatedness, not file count.** Lumping genuinely unrelated modifications together is still wrong — a colour-palette fix and a nav fix are two directions even if they land the same afternoon. But "one commit per file" and "one commit per hunk" are both wrong in the other direction: they bury each commit's intent in bookkeeping. When in doubt, ask whether reverting this commit alone would leave the repo coherent; if yes, it is its own commit, and if no, it belonged with whatever it is entangled with.
- **Targeted Staging**: Stage only the specific files touched by the unit (`git add path/to/file`). Never use `git add -A` or `git add .` to avoid capturing untracked scratch files.
- **Meaningful Messages**: State what changed, why, and any specific metrics or design choices involved.
- **NO `Co-Authored-By` TRAILER, AND THE EXACT STRING IS NAMED HERE ON PURPOSE**: commit messages end after the prose. Do not append `Co-Authored-By: Claude Opus 4.8 (1M context) <noreply@anthropic.com>`, or any `Co-Authored-By:` / `Generated with:` / `Signed-off-by:` line, or any other trailer that credits a tool. **This is not a style preference — the string is written out because an agent's own instructions may tell it to add one, and "my runtime said so" is exactly how it gets here.** On 2026-10-10 all 22 commits carrying that trailer were rewritten to remove it, and the rewrite touched every SHA in the repo, so the cost of getting it wrong is not one commit. The history is the user's alone; an agent's contribution is legible from the diff without being signed.
