# AGENTS.md — Pokémon Algorithm Visualization Lab

## Project Overview
Static HTML/JS/CSS site (GitHub Pages ready) visualizing algorithms with 1025 Pokémon sprites.
- **index.html** — Landing page: hero + 3 feature cards + full 1025 Pokédex grid (click → detail)
- **sorting.html** — Sorting lab: 6 algorithms (Bubble, Selection, Insertion, Quick, Merge, Heap) with animated Canvas grid
- **maze.html** — Pathfinding: BFS/DFS on pixelated Pokémon sprites (40×40 grid, recursive backtracker)
- **pokedex.html** — Searchable/filterable Pokédex with fuzzy autocomplete, type/color/gen filters
- **detail.html** — Pokémon detail page (slug or id query): 3-col glass top card (identity / names・檔案・特性 / 培育・生蛋), stats + radar, type effectiveness, evolution, **moves (4 real tabs)**, descriptions
- **404.html** — GitHub Pages fallback: rewrites `/detail/<slug>` to `detail.html?slug=...&from404=1`

## Critical Runtime Requirement
**Must serve via HTTP server** — `file://` fails due to CORS on `fetch('pokemon_data.json')` and image loads.
- VS Code: "Live Server" extension (right-click index.html → Open with Live Server)
- CLI: `npx serve` / `python -m http.server` / `php -S localhost:8000`

## Key Technical Patterns
- **Generator-based animation**: `sorting-algorithms.js` exports `function* algoSteps(arr)` yielding per frame; `sorting.html` drives via `requestAnimationFrame` calling `.next()`
- **Lerp smoothing**: `PokemonNode.update()` interpolates `x/y → targetX/targetY` at 0.15 speed
- **Canvas grid**: 40 cols × 26 rows (1025 Pokémon), 28px padding
- **Color**: Official PokeAPI color (green/blue/red/yellow/purple/pink/brown/black/white/gray) — replaces computed `color_group`
- **RGB card glow**: `createPokemonCard()` sets `--card-accent-rgb` from `pokemon.rgb`; `shared.css` renders a neutral drop shadow plus a two-layer RGB glow (14px @ 0.55, 40px @ 0.35) on `.card:hover`
- **Slug routing**: `pokemonSlug()` normalizes `names.en`; `pokemonDetailUrl()` returns the Live-Server-safe `detail.html?slug=<slug>`, `pokemonDetailPath()` returns the clean `detail/<slug>` used only for `history.replaceState`
- **Radar chart**: Canvas-based stats visualization in detail page
- **Type effectiveness**: Computed client-side from dual-type combination
- **Move tabs**: `renderMoveSection()` in `shared.js` emits a real `tablist` (WAI-ARIA tabs with roving tabindex, Arrow/Home/End). `detail.html`'s `renderMoves()` gates both fetches behind an `IntersectionObserver` (`rootMargin: 400px`), since learnsets.json is 4.3 MB raw (223 KB gzipped, against 614 KB for the pokemon_data.json every page already loads); both loaders cache on `window` like `loadEvolutionChain()`
- **ES Modules**: All JS uses `type="module"` with relative imports from `assets/js/shared.js`. `pokemon-lexicon.js` imports `shared.js`, so `shared.js` cannot import it back — the `MOVE_*` label maps live in `shared.js` and are re-exported from `pokemon-lexicon.js`
- **Fuzzy search**: `<input list="pokemon-suggestions">` with `<datalist>` populated from all names (id, zh, en, ja)

## Gotchas
1. **No build step** — edit HTML/JS directly; changes reflect on reload
2. **1025 images + JSON** — initial load ~200 MB; first paint shows "載入進度" counter
3. **Generator exhaustion**: `sortGenerator = null` resets; `yield` frequency controls animation speed (insertion sort yields every 5 inserts)
4. **GitHub Pages**: Ensure repo settings → Pages → Source: "Deploy from branch" / root folder
5. **Asset paths**: All HTML files reference `assets/images/pokemon/`, `assets/js/shared.js`, `assets/data/pokemon_data.json`
6. **Virtualenv required**: Python scripts need `.venv` with pandas, openpyxl, httpx, lxml, beautifulsoup4. The interpreter used for this repo is `../.venv/bin/python` (i.e. `Visual_Studio_Code/.venv`), not a project-local `.venv`
7. **Chinese descriptions**: 1025/1025 have text1 (primary), 1025/1025 have text2 (secondary) from tw.portal-pokemon.com. Scraper handles both single-escaped and double-escaped Next.js streaming formats.
8. **Detail page URL**: `detail.html?slug=bulbasaur` is the internal link format (works on Live Server, `python -m http.server`, and GitHub Pages). The legacy `detail.html?id=25` form still works. Clean URLs (`/detail/bulbasaur`) are only resolvable on GitHub Pages, where `404.html` redirects to `?slug=...&from404=1` and `detail.html` restores the clean path with `history.replaceState`. VS Code Live Server returns `Cannot GET /detail/bulbasaur` for direct clean-URL visits — always navigate via the `?slug=` form during local development.
9. **text2 fallback**: If tw.portal-pokemon.com doesn't have text2, it's left empty (no wiki.52poke.com fallback)
10. **The colour swatch is the official colour, not the sprite's average**: `createPokemonCard()` renders types only; on cards the color is expressed solely through the RGB hover glow. The swatch exists only on the detail page, and it is a bare 12px `.color-dot` next to the English name in `.color-swatch` — there is no text on the swatch, so `getReadableTextColor()` and the old `badgeStyle()` contrast-ladder for `.color-badge` are **both gone**; `badgeStyle()` now only styles the type-effectiveness badges. The fill is `COLOR_HEX[p.color]` from `pokemon-lexicon.js` (PokeAPI's 10 canonical values), **not** `pokemon.rgb`: `p.rgb` is the sprite's pixel average, and the nearest official colour to it is a *different* colour for **870 of 1025** records (Bulbasaur's `rgb(150,192,168)` reads Gray, not Green), so an `p.rgb`-filled dot next to the word "Green" is a visible contradiction. `p.rgb` keeps its other job — `--card-accent-rgb`, i.e. the top card's aurora and the card glow. **The dot's 1px ring must be opaque** (`box-shadow: 0 0 0 1px rgb(var(--hairline-rgb))`), and this is measured, not stylistic: the ring is adjacent to the dot *and* the card at once, so there is no second ring available to specialise one side, and the dot only has to clear 3:1 against one of the two. Across all 2050 colour × theme pairs against the worst-case tinted card, alpha 0.55 bottoms out at **1.62:1** — a gray `#a9a9a9` dot landing almost exactly on a half-alpha ring — and every value up to 0.9 still fails (0.7 fails green in dark at 2.40, 0.9 fails red in light at 2.95). Opaque clears at **3.10:1**. Do not "soften" that ring; re-run the numeric sweep over all 10 `COLOR_HEX` values if you touch it.
11. **Type chart source of truth**: `assets/js/type-chart.js` is generated from the 52poke 屬性相剋表 「第六世代起／正常對戰」 grid and is the *only* sanctioned chart — never hand-write matchups and never copy them from PokeAPI. PokeAPI's per-type `damage_relations` are one-sided: merging `*_damage_from` and `*_damage_to` across all 18 types still leaves most of the 324 cells unspecified, and because the directions never overlap it reports no conflicts, so the gap is silent (`/api/v2/type/normal` has no `half_damage_from`; `psychic` mis-assigns rows). Pokémon Showdown's `data/typechart.ts` on master is a modded chart (carries a `prankster` ability key and a Stellar row). Regenerate with `python scripts/extract_type_chart.py`, which pins all 120 non-neutral cells against a hand-written reference profile and cross-checks every cell's text against its CSS class. Revalidate runtime behaviour with `node scripts/check_type_chart.mjs`.
12. **Dual types multiply, never union**: `typeEffectiveness()` multiplies the two defender rows so 2×½=1× drops out and 2×2=4× / ½×½=¼× emerge. An earlier hand-written version unioned the two types' weakness lists and then ran an inverted dedup pass, which reported Water and Ground as 2× weaknesses for a Fire/Flying Pokémon and surfaced no immunities at all.
13. **The detail page is a single scroll, with one exception**: every section renders at once (top card → stats → type effectiveness → evolution → moves → descriptions), so it is printable and linkable. The top card itself merged what used to be the hero and the 基本資料 section, so it holds identity + names/檔案/特性 + 培育/生蛋 and nothing else — the only 上一隻・下一隻 pager is the page-level `.detail-footer` under it (gotcha 28). The exception is the moves section, which is four real tabs (等級提升 / 招式學習器 / 遺傳招式 / 傳授招式) to match InfoPoke. All four panels **are** in the DOM — the inactive three carry the `hidden` attribute, which is what a tab widget needs for its ARIA relationships to hold — so they are the only sections a screen reader and Ctrl+F cannot reach, and `@media print` overrides `display` to reveal each one under its `data-move-tab-label`. That attribute is not decoration; removing it silently drops the print headings. All other sections carry `aria-labelledby` pointing at their heading id; decorative icons are inline `<svg aria-hidden="true" focusable="false">`.
14. **The radar canvas is sized from its rendered box**: `drawRadarChart()` reads `clientWidth` and multiplies by `devicePixelRatio` for the backing store, because the canvas is fluid in CSS (`max-width: 320px`, `aspect-ratio: 1`). Setting only the `width`/`height` attributes would render at 1× on retina. It is redrawn on a debounced `resize`. It also shares `STAT_MAX` (255) with the bars so the two views agree — an earlier `/200` scale made strong Pokémon read as a flat hexagon. **The polygon wash has to come from a token, not a literal alpha**, because `--accent-gold-rgb` is a bright yellow in dark and a dark brown in light: the same 0.3 that reads as a warm glow in dark reads as a mud-coloured shadow in light, which is exactly what it was reported as. `--radar-fill` (dark `0.13` / light `0.06`) and `--radar-stroke` (dark `0.8` / light `0.6`) are read back off the stylesheet per repaint via `readThemeToken()`, for the same reason `rgbaHairline()` is — a `<canvas>` cannot see `var(--x)`. Lower the light fill before lowering the stroke; the outline is what carries the shape. The neighbouring `.stat-row` is a `3.4em 2.6em minmax(0,1fr)` grid, so **a stat label wider than 3.4em overlaps the value column** — `能力總和 / 720` did exactly that, and the fix was to drop `/ 720` from the label rather than widen the column, because the `.section-note` above the section already states that stats peak at 255 and the total at 720. Do not put a scale back into a label; put it in the note. **The seven bars are one column, and the radar is sized to fit them.** `.stat-bars` was `repeat(auto-fit, minmax(210px, 1fr))`, which put the six stats in 3 columns of 234px inside the 792px bars column at desktop, so each `.stat-track` came out **118px** while `.stat-total` — carrying `grid-column: 1 / -1` — spanned all three at **626px**. The six bars were 5.3× shorter than the total they are read against, and *only* above ~600px, because below that auto-fit had already collapsed to one column and every track was equal — a desktop-only bug that looks like a preference. `grid-template-columns: minmax(0, 1fr)` makes the equal length structural rather than incidental: all seven rows are `.stat-row`/`.stat-total` and share one template, so the tracks match by construction instead of by tuning a `minmax()` until it happens to divide evenly. Do not reintroduce a column count — if the bars ever need to be narrower than the radar leaves room for, cap `.stat-bars` or move the radar, but keep all seven rows at one track width. **The radar is right, the bars left**, which is why `.stats-layout` declares `minmax(0, 1fr) minmax(0, 320px)` *and* `.radar-frame` carries `order: 2`; declaring `320px 1fr` and reordering would put the radar in the `1fr` track and squeeze the seven bars into 320px. `drawRadarChart()` then caps `canvas.style.maxWidth` to `.stat-bars`' **measured** height (**246px** at 1180px) so the radar's bottom is flush with the 能力總和 row instead of hanging 74px below it. That figure is measured rather than hardcoded because the block is six rows plus a summary, so its height comes out of font metrics and platform line-height and is not a stable number. The cap applies only while the two share a row (their `top`s are equal); below the 900px breakpoint `.radar-frame`'s `order: -1` lifts the radar above the bars, where flush is meaningless, so the stylesheet's 320px stands. All three redraw paths funnel through `drawRadarChart` — `renderStats`, the debounced `resize`, and `themechange` — so the cap cannot go stale, and the sizing is one-directional (canvas ← bars) so there is no layout feedback loop. The chart is square by construction, and shrinking it does not clip the 12px axis labels: the transparent margin measures L/R 14px, T 6px, B 5px at 246px against L/R 19px at 320px, because the tight top/bottom comes from the fixed 26px inset minus the 15px label offset rather than from the width.
15. **`renderEvolutionChain()` assigns `innerHTML` unconditionally**: 505 of the 541 chains in `evolution_chains.json` carry no `variants` key, so an assignment that lived inside the variants branch left the evolution section blank for 93% of Pokémon. Its CSS lives in `detail.css` under "Evolution chain" — that markup is emitted by `shared.js`, so deleting the old inline `<style>` block in `detail.html` silently unstyled it.
16. **Genus translations are scraped, not vendored**: `assets/js/genus-zh.js` is generated from `https://wiki.52poke.com/zh-hant/分类` (1051 rows → 734 genus, 715/715 covered), so regenerating needs network and is deliberately **not** byte-idempotent — upstream edits show up as a diff. That is the point: switching from the old checked-in dump already picked up two corrections (`Ghost Flame Pokémon` 磷火→鬼火, `Hexpert Pokémon` 咒術師→詛咒師), neither of which any of our 1025 Pokémon uses. The `zh-hant` page must be fetched **by URL**: `api.php?action=parse` returns the default *simplified* variant (`全国编号`), so the `全國編號` header marker never matches. `api.php` also rejects the full URL as a title — it normalizes to `Https://…` and reports the page missing — so `PAGE_TITLE` stays a bare `分类` for the revision lookup. Provenance is recorded in `GENUS_SOURCE` alongside the chart's `TYPE_CHART_SOURCE`.
17. **Hero carries 繁體, the badge row carries 簡體**: `NAMES` in `detail.html` has no `zh` entry because the hero `<h1>` is already `names.zh`. It does *not* filter out a simplified name that happens to equal the traditional one — 359 of 1025 are character-for-character identical (妙蛙草, 巴大蝶, 波波) and hiding those made the badge row a different length per page, which read as a bug. The data still carries all 9 `names` keys on all 1025 records, but the badge row renders only 5 (簡體 日文 法文 德文 韓文) on every page. The other four are deliberately not shown: `zh` and `en` are already the `<h1>` and the `.hero-title-en` line under it, and `es`/`it` are excluded because 1005 and 1004 of them are a character-for-character copy of `en`, so they read as padding. `pokemon_data.json` keeps them regardless — 20 `es` and 21 `it` names are genuine translations (Iron Thorns → Ferropúas / Spineferree, Type: Null → Código Cero / Tipo Zero), all Gen 7 paradox and Gen 9, so **an unread `names.es` is not a bug**: re-adding two lines to `NAMES` in `detail.html` brings them back. Removing them from the data as well would mean editing `enhance_pokemon_data.py` too, or the next regeneration restores them.
18. **The learnsets are an all-generation union, and each method has one right answer**: `fetch_moves.py` unions every version group, so the counts are far larger than InfoPoke's, which only ever loaded one generation (Bulbasaur is 16/68/19/22 for us vs 12/60/8/6 there). Level-up takes the *lowest* level any game offered, never the latest game's. The four methods are independent and overlap freely — a move reachable three ways appears three times, and the sections must not dedupe across them. 459 of 1025 have no egg moves and 138 no tutor moves, so the empty state is normal, not a bug.
19. **A machine code is not a number**: rows are `[moveId, code, generation]` with codes like `TM01`/`TR09`/`HM06`, and the prefix is load-bearing. PokeAPI ships 8 HMs (`hm01`–`hm08`), 230 TMs (`tm00`–`tm229`, three digits from Gen 9) and 100 TRs (`tr00`–`tr99`) — the TR range overlaps the TM range completely, so storing `9` instead of `TR09` renders one as the other. Bulbasaur has both a real `TM17` and a `TR17`. The number also has no single correct value per move, since a code is reused across games: Bulbasaur has two moves coded `TM01` and three coded `TM31`, each from a different generation. `moveTableHtml()` therefore flags only the codes reused *within the rendered tab* with a `†` and puts the source generation in a tooltip — the count has to be taken over the whole tab, before the two-column split described in #22, or a pair straddling the midpoint loses its flag.
20. **The two `typeBadge` helpers differ on purpose**: `.type-badge` is defined only in `detail.css` (a 14px hero pill), and the pokedex cards have no rule for it outside the detail page, so their 10px size is inline. `typeBadgeHtml()` is therefore the CSS-sized hero pill and `typeBadgeSmHtml()` the self-contained compact one used by cards and the move tables — using the wrong one silently resizes the cards. Both capitalise the slug first, because PokeAPI returns `normal` while `TYPE_EN_ZH`/`TYPE_COLORS` are keyed `Normal`.
21. **Move rows come in two shapes**: level rows are `[moveId, level]` and machine rows are `[moveId, code, generation]`, but egg and tutor are a *flat list of bare move ids* (`[13, 80, 92]`), because "inherited from a parent that knew it" is the whole fact PokeAPI offers. `moveTableHtml()` normalises with `Array.isArray(row) ? row : [row]`; indexing `row[0]` without that check renders an entire egg list as a single row.
22. **A move tab is two tables, not one**: `moveTablesHtml()` splits each tab's rows in half into a `.move-tables` grid, matching InfoPoke's `grid-cols-1 lg:grid-cols-2`, because a machine tab runs to 340 rows. Three things are load-bearing and each was a bug first. (a) The split is at **1100px**, and that number is a *preference*, not a measured threshold — it follows InfoPoke's `lg` / `grid-cols-2`, nudged slightly to suit this page's `max-width: 1180px` content column. Do not cite overflow as the reason: measured with the grid force-enabled, the 6-column machine table spills **0px at every width from 960 to 1400px** (426px half at 960, 458px at 1024, 496px at 1100, 536px at 1400), so stacking earlier was never required for correctness. What *is* measured is the two sides of the breakpoint: side-by-side at 1100px, stacked at 1099px. Re-measure with `getBoundingClientRect` if the column count or the content column width changes. (b) `machineCodeTally()` runs **once over the full list** in `moveTablesHtml()` and is passed into both halves via `opts.codeTally`; rows are sorted by code, so a split can land exactly between the two moves sharing one, and a per-half tally would silently drop their `†` (see #19). (c) A **single-row tab is not split** — one table in a two-column grid leaves an orphan header bar with nothing under it, which reads as a rendering fault. Zero rows never reach `moveTablesHtml()`; the caller renders the empty state. Each half carries an `sr-only` `<caption>` with its range (`等級提升 1–34`) so the two tables do not announce the same accessible name, and `@media print` promotes that caption to visible because print is ~794px, below the breakpoint, so the halves stack with no visible boundary. Also deliberate departures from InfoPoke: the level column header is `Lv.`, matching InfoPoke's own `Lv.` over its narrow `w-8` column, and the machine table keeps its 6th `招式機` column, which InfoPoke's data model has no field for. Do not "fix" this back to `等級` expecting a layout reason — measured across 320/390/480/700/1100/1400px, `等級` never wraps here; it is simply 4–9px wider, which is what the narrower header buys the numeric column. Sorting is ours, not InfoPoke's. The damage class is emitted as `move-class-physical|special|status` on the `td`, and `.move-col-class` is a **three**-class selector because `.move-table td` outranks two — the same specificity trap that once cost `.move-col-num` its right alignment. Tints were contrast-checked against the lightest surface a cell can sit on (`#2a2a2a`): 物理 `#dddddd` = 10.57:1, 特殊 `#5cb3f7` = 6.32:1, 變化 `#ffa726` = 7.39:1.

23. **`sorting.html` was dead on arrival, and the failures hid each other**: it imported a name `shared.js` never exported (`shuffleArray`), so the module died at parse with a `SyntaxError` — which masked two more faults that had therefore *never run*. All three are now fixed; the reason they were invisible is the point. (a) `loadAllPokemonNodes` was **never in the import list** while the unused `getGridStartPositions` was, so `init()` threw a `ReferenceError` that its own `try/catch` swallowed into a `console.error` — the page reported "載入失敗！請確認是否使用 Local Server" for what is not a server problem, and the canvas stayed empty. Check the *import list*, not what `shared.js` exports: an export that is not imported is not in module scope. (b) The 8 control buttons were inline `onclick="runAlgorithm('bubble')"`, and an inline handler resolves its callee on the **global object**, so every one raised `ReferenceError` — the six `*Steps` generators survive this only because `sorting-algorithms.js` is a *classic* `<script src>`, whose top-level function declarations really are global. Same construct in `maze.html:12` is fine for the same reason; do not "fix" the two pages to match. Buttons are now `data-action` / `data-algorithm` + `addEventListener`, as in `pokedex.html`. (c) `groupByColor()` read `p.data.color_group`, a computed key **0 of 1025** records carry, so the whole roster fell into one fallback corner. It now reads PokeAPI's `color` via the same `capitalize()` the type badges use (see #20) — the official colour is the source of truth and the computed grouping is gone.
24. **White and Gray are separate clusters, and the jitter needs statistics to test**: `COLOR_CENTERS` is keyed by `capitalize(color)` over a `Uniform(-80, 80)` jitter (σ = 160/√12 = 46.19px, matching a measured ~46px spread). The 10 colours are `blue 170, brown 147, green 130, gray 107, red 97, white 88, yellow 88, purple 87, pink 60, black 51`. White and Gray were one `"White/Gray"` slot, which put **195 of 1025** into a single 160px box of 24px sprites — about six across, so five or six layers of overlap and no readable cluster. Gray took the empty bottom-left corner at (200, 700); the other ten centres are unchanged. Do not assert a fixed pixel tolerance on a cluster's mean: the standard error of the mean over *n* sprites is 46.19/√*n*, so ~5px for Blue and ~6.5px for Black, and a 12px threshold fails Yellow (n=88) about 1% of the time on pure noise. Bound each colour by 4·SE instead, and check the *mean of many trials* stays at 0 — that separates noise from a systematic offset. The canvas is 1200×800 and every centre is at most 1080/780 once jittered, so the last sprite row cannot fall off it. `Orange` is a legal PokeAPI colour no record uses, kept so a future one has a slot.
25. **A button that is wired can still be doing nothing, and a button that is wired wrong throws only on click**: `renderLoop` only calls `updateGridPositions()` while a generator is live, so verifying the page means clicking all 8 controls and watching pixels move, not reading the console once. Two measurement traps cost real time here. `requestAnimationFrame` *does* run under headless Chrome with and without `--disable-gpu` (122 frames in 2s ≈ 60fps), so a blank canvas is never a headless artefact — and a blank canvas with 0 console errors means `draw()` is bailing on its `img.complete && naturalWidth !== 0` guard, i.e. the images, not the paint. The nodes interpolate at 0.15/frame (`(1-0.15)^n`), so **anything measured within ~2s of a click is mid-lerp**: a settled grid and a freshly clicked cluster differ enough to look like a bug. Allow 4s. Read the canvas with `getImageData` and check `alpha > 8`; the settled grid occupies bbox `[42,38,1157,761]`, exactly `START_X 54 + 39×28 = 1146` plus half a sprite, and the clustered state must put **100%** of painted pixels inside a cluster box. Note `pokemons` is module-scoped, so a CDP probe cannot read it — pixels are the only black-box channel.
26. **The pokéball is a favicon only, and emoji are banned site-wide**: the requirement is that the icon is visible in the browser/application *tab* and nowhere in page content. A visible `.site-logo` `<img>` was built into all four header titles and then removed on the user's explicit instruction, along with its `logo-128.png` and its `.site-logo` rule — and later `pokeball-icon.png` was deleted on the user's instruction too, so the two files below are all that remain. No `<img>` of a pokéball exists in any `<body>`. The decorative `⚡` flanking the titles and the `📖` in the detail title went with it; a title needs no ornament when the tab already carries the mark. `404.html` gets no favicon `<link>`: it is served for arbitrary paths (see gotcha 8, `/detail/<slug>`), where a *relative* `assets/…` href resolves to `/detail/assets/…` and 404s again, and it has no `shared.css` and redirects before anything renders. **Attribution — `favicon-32.png` and `apple-touch-icon.png` are not my artwork.** They are the pokéball app-icon set from a Reddit post, downscaled with `sips -z W H src --out dst` from a 512×512 master that has since been deleted: <https://www.reddit.com/r/PTCGP/comments/1h3i9ys/i_made_more_app_icons_for_yall/> ("I made more app icons for YALL", r/PTCGP). The post's author could not be resolved — Reddit blocks automated access to the thread and JSON, `old.reddit`, and three Redlib mirrors all refused, and the author field was never read — so **`POST_AUTHOR` is still unverified and must be filled in from the thread before crediting anyone.** Credit the artist, not the platform, and do not re-derive either file from the 32×32 `favicon-32.png`: with the master gone that source is the highest quality left, so upscaling it to 180×180 is visibly blurry. Recover the original 512×512 art from the thread instead.

27. **Icons are inline SVG, and the header nav has two sources of truth**: emoji are banned — they are font-dependent, cannot inherit `currentColor`, and render differently per OS, which is what made the old `🎯`/`🎮`/`📖`/`🔀`/`🎨`/`⬅` read as unprofessional. Every icon is `<svg class="icon" viewBox="0 0 24 24" aria-hidden="true" focusable="false">` wrapping one filled Material-style path, matching the hand-written icons already in `detail.html`. `.icon` is sized in `em` (`width/height: 1em`, `vertical-align: -0.125em`, `margin-right: 0.3em`) so one rule covers a 13px `.btn`, a 16px nav link and a 16px `.view-all-link` with no per-component override; `.icon-trailing` moves the gap to the left for icons that follow their text, and `.feature-icon .icon` is the one fixed-size case (40px, `fill: var(--feature-accent)` — it was `font-size: 48px` back when it held an emoji glyph). The `aria-hidden` is not optional: the adjacent text label always carries the meaning, so an exposed icon would double-announce it. The trap: `initHeaderNav()` in `shared.js` **assigns `.header-nav`'s `innerHTML` unconditionally**, so the static `<nav>` in `index.html`/`pokedex.html` is replaced at runtime — editing only the HTML leaves the old markup live until the first paint. The nav labels and their icons therefore live in `ICON_PATHS` + `iconSvg()` in `shared.js`, and `ICON_PATHS` holds only the three the nav actually renders; the other four (`shuffle`, `palette`, `back`, `forward`) exist solely as static markup and are deliberately not duplicated into the map. `createFeatureCard()`'s `icon` option is SVG markup, not a character.

28. **The detail top card is three columns, and the glass has to have something behind it**: `.top-hero-card` replaces the old two-column `.hero` + separate 基本資料 section, following InfoPoke's layout — **column 1** `#pokemon-id` / `<h1>` / English name / 475×475 sprite / type badges, **column 2** 名字・檔案・特性, **column 3** 培育・生蛋 — at `grid-template-columns: 3fr 4fr 5fr` from **1024px** and one column below. The **only** 上一隻・下一隻 pager is now the page-level one under the card (`.detail-footer`); the duplicate that used to sit under the sprite was removed as redundant, and `renderPager()` writes only `pokemon-prev-foot` / `pokemon-next-foot`. The five group headings are real `<h2 class="group-title">` elements and are the `aria-labelledby` targets of their `.info-group`; the stats/radar section stays its own full-width section below, because squeezing a 320px canvas into a 255px column makes the radar labels collide. **True glassmorphism needs a backdrop, and the page has none**: the body is a flat `#121212`, so a `backdrop-filter` on the card had nothing to refract and read as a flat grey box. The card therefore paints its own aurora on `::before` — `radial-gradient`s in `rgba(var(--card-accent-rgb), .32)` / `.18` plus a gold `linear-gradient` — and `renderDetail()` sets `--card-accent-rgb` from `pokemon.rgb` on the element, the same convention and variable name as `createPokemonCard()`. The aurora is a pseudo-element rather than the element's own background *because a pseudo-element cannot be a backdrop for its own parent*, so putting both on `.top-hero-card` would blur nothing. `overflow: hidden` clips it to the rounded corners. There is an `@supports not (backdrop-filter)` fallback at `rgba(28,28,32,.94)`. The card also **overrides `--text-muted` to `#bdbdbd`**: the glass is lighter than the page, so the site's `#aaaaaa` no longer clears AA there — Chansey's `rgb(214,178,192)` is the palest of the 1025 and put a 12px `.names-grid .lang` at *exactly* 4.50:1, the same zero-margin trap as gotcha 10, and that figure is a model of the gradient rather than a sampled pixel. `#bdbdbd` measures 5.5:1; the tightest remaining row is 5.04:1. Re-run the probe before changing either. The **fact rows are dense left-right rows, not cards**: label plus value, **no dotted leader** — the `.fact::after` (`order: 1`, `flex: 1 1 auto`, 1px dotted border) that used to join them is gone, because across a two-column grid it carried more visual weight than the rows themselves. The value keeps its flush-right position from `margin-left: auto` (still `flex: 0 1 auto` — giving it `1 1` would strand a gap after the value). `.fact-grid` is two columns from **400px** and one below, because the label is `nowrap` and the widest is 基礎經驗值: measured on Dragonite, 374px → 130px columns and clean 40px rows, 360px → 45px, 340px → 62px, and **320px → 94px columns with the value actually clipped**. Re-measure with `getBoundingClientRect` if a label or the content column changes.

29. **`gender_rate` and `hatch_counter` are on the species, and Phase 1 deletes them**: both come from `/pokemon-species/{id}`, **not** `/pokemon/{id}` — the latter does not carry them at all and does not say so, the keys are simply absent, so a script reading them there gets `None` for all 1025 records and reports success. `gender_rate` is eighths *female*: `-1` is genderless (155 of 1025), `0` is female-only (26), `8` is male-only (37); the page divides by 8 and shows InfoPoke's `♂87.5% ♀12.5%`. `hatch_counter` is rendered verbatim as `${p.hatch_counter} 週期` and **must not be normalised**: it takes 11 distinct values across the 1025 records (5, 10, 15, 20, 25, 30, 35, 40, 50, 80, 120), and they track the line's generation, not its stage count — the "20 for single-stage, 35 for two-stage" rule is folklore, and Ho-Oh/Mew/Palkia/Terapagos are all 120 while Terapagos alone is 5. Bulbasaur and Magnemite are 20, so a sample of two both being 20 is what makes the rule look true. Only sanity-check that it is a positive int. Both are written **in place** into `pokemon_data.json` rather than a new file: every page already loads that file, so two small integers per record cost ~8 KB raw and need no extra request and no lazy loader — unlike `learnsets.json` (4.3 MB) which earns a separate file and an `IntersectionObserver` per gotcha 13. `build_pokemon_entry()` is a **whitelist** dict assembled from the CSVs, so a Phase 1 re-run rebuilds every record and drops any key it does not name; `enhance_pokemon_data.py` now carries both from `existing`, which is why the workflow order is Phase 1 → `fetch_breeding_data.py`, and why running Phase 1 *alone* resets them. Note the carry-through uses `is not None`, not truthiness: `gender_rate: 0` is a real value (female-only) that a truthy check would silently rewrite to `-1`. The script validates before writing and aborts rather than emitting 1025 plausible-looking wrong values. `♂`/`♀` (U+2642/U+2640) are **data symbols**, in the same category as the ones inside `Nidoran♀`/`Nidoran♂` — see gotcha 26's emoji ban, which does not apply to them.

30. **Shiny is a CSS filter placeholder, and `pokemonSlug()` cannot address Nidoran♂**: the toggle is `aria-pressed` + an `#pokemon-sprite.is-shiny` `hue-rotate(-28deg) saturate(165%) brightness(1.12) contrast(1.05)` filter, because no shiny artwork exists in `pokemon_data.json` or on disk. `official_sprite_url` is the 96×96 *pixel* sprite, not artwork and not shiny. The real file is PokeAPI `/pokemon/{id}` → `other["official-artwork"]["front_shiny"]`, or the plain-artwork variant at `files/official-artwork/shiny/{id}.png`; when it lands, `toggleShiny()` becomes a `src` swap and `.is-shiny` stops setting `filter`. The button is hidden in print and the filter is reset there, because printing a recoloured placeholder would misrepresent it as real artwork. **Separately, `pokemonSlug()` normalises `names.en` to `[a-z0-9]`, which strips the symbol, so `Nidoran♀` and `Nidoran♂` both slug to `nidoran`** — `find()` returns the first match, so Nidoran♂ (id 32) is reachable only via the legacy `detail.html?id=32` and has no slug URL. This is **pre-existing** and left alone: the pager is id-based (`id ± 1`), so it never needs the colliding slug, and fixing it means changing the URL scheme, which also touches gotcha 8's clean-URL contract and `404.html`. Do not "fix" the slug without doing that work too.
31. **Theme is applied before first paint, and only a deliberate choice may be stored**: each of the 5 pages carries a small pre-paint script that sets `documentElement.dataset.theme`, because a theme applied from a module after the first paint is a visible flash. `setTheme(theme, { persist = true })` in `shared.js` is the only writer: `localStorage` is wrapped in `try/catch` (private mode throws on `setItem`) and every read of the preference goes through `hasPreference()`. **The OS listener must call `setTheme(..., { persist: false })`** — the earlier version omitted the flag, so the first `prefers-color-scheme` event wrote the resolved theme into `pokemon-theme` and pinned it: the page then looked correct but silently stopped following the system, and a reload could not tell the two cases apart. An explicit choice still wins over later OS changes, because `hasPreference()` gates the listener. `setTheme` also dispatches a `themechange` event, which is the *only* reason a `<canvas>` can follow a theme switch: `maze.html` and `sorting.html` re-enter `renderLoop()`, and `detail.html` redraws the radar. A `<canvas>` cannot see `var(--x)`, so its colours are read per repaint through `readThemeToken()` — the same reason `rgbaHairline()` and `--radar-fill` exist as tokens. Two more traps: the toggle is `aria-pressed` (**true in light**), and `@media print` forces `color-scheme: light` plus its own token overrides, since a dark page wastes ink and `--accent-gold` is a bright yellow in dark. Finally, `hexToRgb` is exported from `shared.js` and imported from there — `pokemon-lexicon.js` imports `shared.js`, so exporting it from the lexicon and importing it the other way round is a cycle, and a missing export is a **`SyntaxError` at parse time that kills the whole module** rather than a runtime failure in one function.
