## A. Routing & Slugs
- **Local & GitHub Pages URLs**: Internal navigation uses query parameters (`detail.html?slug=bulbasaur` or `color.html?slug=bulbasaur`).
- **Nidoran Disambiguation**:
  - `nidoran-f` (#029) and `nidoran-m` (#032) are distinct slugs.
  - A bare `nidoran` slug is strictly disallowed and must not resolve.
- **Form Links**: Alternate forms link back to their base species detail page.
- **detail ⇄ color Reciprocity**: `detail.html` and `color.html` link to each other (`單一色盤` ↔ `完整資料頁`), and both must build their cross-page URL from the one canonical helper — `pokemonDetailUrl()` in `shared.js` and `paletteUrl()` in `color-palette.js`. **Never assemble either URL by hand or by string-replacing `detail.html`** — `paletteUrl()`'s docblock gives the reason: `color.html` deliberately does *not* inherit detail's clean-URL contract, so the two shapes can diverge and a derived string breaks the day either gains a path segment. `detail.html` imports `paletteUrl` from `color-palette.js` for exactly this reason; that module has no top-level side effects, so the one-function import costs a parse and nothing else.

## C. Contrast & Accessibility Rules
- **Color Contrast (WCAG AA)**: Minimum 4.5:1 for standard text, 3:1 for large text and UI components.
- **Measurement Method**: Verify contrast by sampling decoded screenshot pixels via Canvas/CDP, not via `getComputedStyle()` (which misses alpha blending, backdrop filters, and radial gradients).
- **Typography**: CJK-first font stack in `--font-sans` (`PingFang TC`, `Noto Sans TC`, `Microsoft JhengHei`) to avoid mismatched English/Chinese rendering.
- **Theme Switching**: Handled inline in `<head>` before first paint to prevent flashes. Toggling triggers a `themechange` event for Canvas redraws.
- **Reduced Motion**: Honored across CSS and JavaScript. Sprites snap immediately to target coordinates instead of lerping.

## D. Type Profiles & Scoped Translations
`assets/data/type_profiles.json` is generated by `scripts/fetch_type_profiles.py`, which scrapes the InfoPoke `/types/[id]` Nuxt chunk. InfoPoke publishes **no zh-TW catalogue** for this route — its own zh-TW pages render raw i18n keys — so the file mixes three provenances and they are kept in separate fields rather than merged:

- `blurbEn` / `battleTipsEn` / `categoryNoteEn` and `entriesEn[].effect` are **English upstream**. They are shown in `types.html` inside a collapsed block explicitly labelled as upstream English, never passed off as a translation of ours.
- `entries[].effect` is **Simplified Chinese upstream**, converted with `OpenCC` `s2twp` and pinned by `requirements.txt`. This is the only zh-TW effect text on the page.
- `trainers[].roleZh` is **this project's own translation** of InfoPoke's English role titles. Trainer and city proper nouns stay English.

Two consequences worth knowing before editing `types.html`:

- **Ability names come from our data, not the scrape.** `types.html` builds the ability list from `pokemon_data.json[].abilities` + `abilities_zh.json` and borrows only effect text from the scrape, matched on the official Chinese name. InfoPoke's own zh-TW ability names are its own translations (悠遊自如 for Swift Swim, 仙氣護衛 for Fairy Aura) and a few of its entries are not real abilities at all. 59 of 74 scraped ability names join; `check_type_profiles.mjs` pins that floor at 70% so the join cannot silently collapse.
- **Type relationships come only from `type-chart.js`.** Never from InfoPoke and never from `type_profiles.json`. `Electric → Water` is `2×`; that is correct and matches PokeAPI, the InfoPoke grid, and the wiki.

## E. Scarlet/Violet Artwork & Provenance
`assets/js/sv-index.js` is generated by `scripts/extract_sv_index.py` from the PNGs actually on disk. It is **not** a list of what exists upstream, and it must never be hand-edited.

- `assets/images/scarlet-violet/` holds 1,225 PNGs: the 1,025-ID roster plus 200 unclaimed variants (`10001+`, top-level alternate forms, gendered suffixes). Unclaimed files are counted and reported but never added to the roster.
- Artwork is fetched by `scripts/fetch_sv_sprites.py`: **PokeAPI first**, falling back to InfoPoke only when the primary host does not return a valid PNG. The fallback exists because PokeAPI's SV set is incomplete; it is not a second source of truth.
- **The frontend credits PokeAPI only.** `SV_SOURCE` in the generated module names the primary host, and `types.html` must not name the fallback anywhere a reader can see it. The real per-file answer lives in `data-sources/sv-sources.json`, which records which host each id actually came from. That file is deliberately outside `assets/` so it is never served to the browser.
- The roster is complete today (1,025/1,025), so the stand-in path in `types.html` is dormant: `hasSv()` is true for every species, the ring badge and the stand-in count render nothing, and `.chip-thumb.is-sub` is never applied. The code stays so a future upstream removal degrades to the 96px `assets/images/sprite/` floor instead of a broken image.
- `node scripts/check_sv_index.mjs` guards all of the above, including that the roster is not stale, that `types.html` still imports both `hasSv` and `svUrl`, that the `onerror` net is intact, that both badge tones exist, and that the count is suppressed at zero. `node scripts/test_check_sv_index.mjs` mutates a scratch copy of the tree to prove each guard can actually fail.

## H. Category Pages vs. `types.html` — Two Different Questions

`category.html?cat=dragon` and `types.html?type=dragon` both exist and both list the same 70 species. **A category page must never link to `types.html`, and must never be merged into it.** Decided by the user when the Dragon page was added; do not re-propose the cross-link.

- A **category page** answers 「有哪些龍屬性寶可夢」 — a roster plus an introduction. Its `prose` and `notes` are this project's own zh-Hant editorial, which is the point: it is the detailed species introduction.
- **`types.html`** answers 「龍屬性的招式、特性、道具、訓練家與相剋關係」 — battle mechanics, and the only place the effectiveness matrix appears. Its prose is upstream English by design (§3.D), so it is not a substitute for a zh-Hant introduction and must not be given one.
- The two are complementary, not overlapping, so a reader who needs the mechanics follows the site's own type browser from the nav. Adding a "see also types.html" link to the category template was considered and declined: it would put a battle-mechanics page on the path of someone who asked a species question.

**Adding a category is a three-list edit, in this order.** `CATEGORIES` (append the config), `CATEGORY_SLUGS` (append the slug — it is a literal list, *not* `Object.keys(CATEGORIES)`, and `category.html` falls back to element `[0]` on an unknown slug, so never insert at the front), and `NON_HUB_SLUGS` or `COLLECTION_GROUPS`. All three are literal lists on purpose: `check_categories.mjs` asserts `CATEGORY_SLUGS \ HUB_SLUGS === NON_HUB_SLUGS` and hub order against `CATEGORY_SLUGS.filter(...)` with `===` on the exact array, so a category that reaches the hub by omission is impossible by construction. Appending is the only insertion that leaves both orders untouched.

- `totalCards === 11` in `check_categories.mjs` is a hardcoded count of the hub. Prefer `NON_HUB_SLUGS` (the 600族 and 龍屬性 precedent): the homepage already links both from the 熱門搜尋 row, and the collections hub is a different navigation surface that neither page needs to appear in.

## L. `outfit.html` Gains Two Ways In, And `new File([blob], name)` Silently Drops The MIME Type

The page takes a photo three ways: the file picker, two bundled presets, and a pasted URL. The first shipped as one line each and the second shipped broken.

**`new File(parts, name)` DOES NOT INHERIT `blob.type` — THE `type` OPTION DEFAULTS TO `""`.** So `loadSample()`'s first version built a File from a `response.blob()` of a perfectly good JPEG, handed it to the existing `loadFile()`, and `loadFile`'s own guard read `!file.type.startsWith('image/')` and printed **「這不是一個圖片檔。請選 JPG、PNG 或 WebP。」** — about a file the same server had just answered `Content-Type: image/jpeg` for. No exception, no console output, and the thumbnail on screen was the very picture it refused. `check_outfit_browser.mjs` caught it with 「the caption names the preset photo's real dimensions」, which is a *shape* claim rather than a colour claim, so it fired on the rejected load rather than on anything visual. Both call sites now pass `{ type: blob.type }` explicitly, and the browser checker's mutation case (delete that third argument) still fails — verified, not assumed.

Expect this shape anywhere a `Blob` becomes a `File`: the two look like the same object and share neither this field nor any other.

**THE PRESET ROW IS A SIBLING OF `.of-drop`, NEVER A CHILD, because the file input covers the zone.** `.of-file-input` is `position:absolute; inset:0` at `opacity:0` (outfit.css:121) — deliberately, so the real control is focusable and in the tab order. Anything nested inside `.of-drop` therefore sits *under* the input and never receives a click, and it looks correct in review because a thumbnail inside an upload box is exactly where a thumbnail belongs. §3.G2's bare `class="header"` in the same shape: a valid declaration producing a valid, wrong page.

**A PASTED URL IS NOT OURS TO DECIDE, AND THE PAGE SAYS SO IN THREE SEPARATE PLACES.** A static host cannot proxy, so `fetch` on a cross-origin image succeeds **only** when that server answers `Access-Control-Allow-Origin`. Measured for this page: `raw.githubusercontent.com`, `upload.wikimedia.org`, `images.unsplash.com` and `picsum.photos` all send `access-control-allow-origin: *`; Facebook/Instagram album URLs do not. So `loadUrl()` distinguishes four outcomes, because a bare CORS rejection is a `TypeError` whose message says nothing about the cause:

| state | why it is a separate branch |
| :--- | :--- |
| not a URL | `new URL()` threw; name it rather than sending it to `fetch` |
| non-`http(s)` scheme | `javascript:` is the dangerous one, and it is why the scheme is checked rather than left to `fetch` |
| fetched, not `image/*` | a 404 page, a paywall and a hotlink block all arrive as `200 text/html`; caught here, because `createImageBitmap` would throw later with a message about the *image* rather than the response |
| CORS-blocked | the single most likely outcome, and the only one the reader can act on — so it gets its own sentence, not 「失敗」 |

**ONLY THE REJECTION PATH IS CHECKED IN THE BROWSER SUITE, AND THAT IS THE WHOLE OF IT.** Asserting a *successful* remote fetch needs a second origin that sends CORS, and every checker here runs on one host — it would be asserting on Live Server's own behaviour. `check_outfit_browser.mjs` therefore drives all four rejection states and says in a comment why the fifth is absent, because "we didn't test the working case" is otherwise a thing a reader has to notice themselves.

**THE PRIVACY NOTE GAINED A CLAUSE, because the feature made the sentence less absolute than it was.** 「照片不會離開你的裝置」 was true and load-bearing, and a URL fetch *is* a request that leaves the device. The note now says which of the two the reader is doing, in the same enumerating style as the rest of that paragraph: the claim is about a photo, not about the network, and a new network path on a page whose headline promise is about network is exactly the change that should force the sentence to be re-read.

**`SAMPLES` IS PARSED OUT OF THE HTML BY `check_outfit_page.mjs`, NOT RESTATED.** Every declared path is asserted to exist, be over 1 KB, be repo-relative (an absolute URL would bypass the manifest's coverage and make the presets track someone else's server), and be ASCII so it needs no escaping. A hardcoded copy would keep passing after the page moved a preset — the same reasoning `check_nav_pages` uses for the six header-modifier names.

## M. An Author `display` Beats `[hidden]`, And The Obvious Fix For An Empty Card Does Not Work

`.of-readout` opened the page as an empty 40px card — a border, a background and 1.25rem of padding around three `hidden` sections. **Putting `hidden` on the wrapper does not fix it**, and that is the whole finding: an author `display: grid` beats the user-agent's `[hidden] { display: none }`, because the UA sheet loses to *any* author declaration regardless of specificity. Measured in headless Chrome on the same box:

```
inline display:grid + hidden   -> computed=grid   h=0
stylesheet .g{display:grid} + hidden -> computed=grid
stylesheet .n{display:none}    + hidden -> computed=none
```

So it needed `.of-readout[hidden] { display: none; }` — the fix `shared.css` already uses for `.site-nav-drawer[hidden]`, and the reason that rule exists there in the first place. **Expect this shape on any wrapper whose own `display` is not `block`:** grid, flex, and `inline-flex` all silently defeat the attribute that every other element on the page relies on, and `element.hidden === true` still reads `true` while the box paints.

**The guard asserts the COMPUTED BOX, not the attribute,** because the attribute is the thing that lies. `check_outfit_browser.mjs` reads `getComputedStyle().display` and `getBoundingClientRect().height` on a fresh load, and the two halves are separately load-bearing — verified by mutation: deleting the CSS rule while keeping the attribute reproduces **exactly** the 40px card, and deleting `els.readout.hidden` from `render()` trips the source gate. A checker that only read `.hidden` would have passed both.

**THE WRAPPER IS WRITTEN INSIDE THE SAME CONTIGUOUS GROUP AS ITS CHILDREN, and the existing gate check was extended to pair it.** §3.G's rule is that a comment between two sibling writes is enough to separate them, and `render()`'s gate check already paired every `els.result.hidden` with an `els.swap.hidden` within 260 characters. A wrapper is a fifth thing that must be hidden on every exit, so `els.readout` joined that group and the pairing became mutual rather than counted — a path that hid all three sections but left the card's own border on screen would pass every other assertion in the file.

## N. `graph.html`'s Header Collapses To The Logo, And Four Traps Came With It

The nav was taking the top 55px of a full-viewport 3D scene, so it now collapses to **one 40px control in the logo's slot** and expands on click. Four of the traps are worth more than the feature, and **two of them shipped as defects during the implementation and were caught by screenshotting rather than by reasoning.**

**`.header-3d` IS SHARED WITH `model3d.html`, so `shared.css` WAS NOT TOUCHED AT ALL** — `git diff --stat` on the change shows zero lines of it. Every new rule hangs on a new `.graph-header` class, which is what makes the collapse opt-in per page rather than a property of a modifier two pages use. `check_nav_pages.mjs` independently requires each header to carry exactly **one** `.header-*` row-layout modifier, and it reads that list out of `shared.css` rather than restating it, so a fourth name would have had to be explained there too.

**THE RULE IT REPLACED WAS DEAD, AND THAT IS HOW IT STAYED DEAD SO LONG.** `graph.css` carried a whole `.header-graph` block — gradient, `backdrop-filter`, `border-bottom` — that **matched nothing**, because `graph.html` wore `.header header-3d`. The block described a header that does not exist, so it could not be wrong in any way a run would notice. Renaming it to `.graph-header` makes it live; §3.G2's shape again, one layer down. **A stylesheet rule for a class no page carries is not dead code, it is a rule nobody is maintaining.**

**`position` IS NOT DECLARED IN THE BLOCK, AND THAT IS LOAD-BEARING.** The dead rule said `position: absolute`, which would have resolved `shared.css`'s `.theme-toggle` (`position: absolute; right: 16px`, no `top`/`left` of its own) against the **viewport** instead of the header and dropped it to the vertical middle of the screen. `.header`'s `position: relative` is what anchors it, and shared.css says so in its own comment. Copying the dead block's `position` would have reproduced a bug that never shipped.

**THE FORCED DARK PALETTE IS ONE RULE, NOT TWO, BECAUSE CUSTOM PROPERTIES INHERIT.** `.graph-header` re-declares `--btn-bg`, `--btn-fg`, `--btn-border`, `--bg-card`, `--surface-hover` and `--text-primary` at the **dark** theme's values. A declaration on the element beats `:root` and `[data-theme="light"]` for its whole subtree, so light theme needs **no second rule** — and `--bg-card` is why the dropdown panel and the mobile drawer are dark too, being children. Verified by measuring, not by reading the cascade, at `data-theme="light"`: chip `rgba(238,241,251,0.08)` on `rgb(238,241,251)` ink, header `rgba(15,23,42,0.88)`. **Without those three `--btn-*` values a light-theme reader gets a row of WHITE pills on a `#030712` starfield**, because light theme's `--btn-bg` is `#ffffff`. §3.B1's scoping rule — add a page-prefixed rule, never restate a shared token — is why this is a `.graph-header` block and not three edits to `shared.css`.

**THE HIDDEN GROUP IS SPLIT IN TWO, AND THE SPLIT IS THE RULE.** `.theme-toggle` and `.site-nav-toggle` get `opacity` + `visibility` and **no `transform`**, because `.theme-toggle` is `position: absolute; top: 50%` with `transform: translateY(-50%)` from shared.css — a transform here drops the button by half its 34px height, measured as `matrix(1,0,0,1,0,-17)` on a correct page and a different number on a broken one. This is the exact reason shared.css's reduced-motion block deliberately does **not** set `transform: none`. Sliding them looked right in review and shipped a half-dropped button.

**`visibility: hidden` IS NOT A SECOND COPY OF `opacity: 0`.** A chip at `opacity: 0` is **still in the tab order**, so a keyboard user Tabs into a nav that is not there and activates links into a visually absent bar — the "focusable element that does nothing when activated" shape (§3.L). Measured after the fix: **0 of 21 nav links are tab-reachable while collapsed.**

**A FULL-WIDTH INVISIBLE HEADER IS A CLICK TRAP.** `.header` is a 100%-wide block over a canvas that fills the viewport, so the collapsed bar had to become `pointer-events: none` with `.graph-header > *` opting back in — the same pairing `.graph-open-btn` already uses in this very file. Otherwise every orbit drag starting in the top 55px is eaten by an element that looks like empty space.

**TWO DEFECTS SHIPPED AND WERE CAUGHT BY LOOKING.** The collapsed button rendered as a **blank 40px box**: `let open = false` made the setup call `setOpen(false)` compare `false === false`, early-return, and never draw the first glyph — `btnGlyph` measured `EMPTY`. Fixed by initialising to **`null`**, the one value the header cannot be in, so the first call always paints. And the theme toggle stayed invisible when the bar opened, because it had been added to the `pointer-events` restore rule and not the `opacity`/`visibility` one. **Neither was visible in the source, and one of them is invisible in the DOM too — only a screenshot of the collapsed state found it.**

**A CLICK ON THE CANVAS MUST NOT CLOSE THE NAV, OR THE NAV IS UNUSABLE.** The WebGL stage fills the viewport, so 「click outside the nav」 *is* clicking the canvas — and a canvas drag ends with pointer-down and pointer-up on the same element, which the DOM reports as a `click`. An unguarded document listener therefore closed the bar every time the reader orbited the camera. `pointerdown` records where the press **started** (not where it ended, so a press inside the nav released on the canvas still counts as inside) and the click only closes if the pointer moved **under 6px**. **A press is a click; a drag is not.**

## O. The Drawer Is A Column But Its Children Were Not — On Every Page

The mobile drawer rendered each group as a **748 × 366 px rounded pill** with its sub-menu crushed into a **120 px** column beside it. One line was missing, in `shared.css`, and it had been wrong on **all twelve pages** rather than only the one it was noticed on.

**A `flex-direction` DOES NOT CASCADE TO THE FLEX ITEMS' OWN CHILDREN.** `.site-nav-drawer` sets `flex-direction: column`, which reorients the drawer's direct children. Each of those is a `.site-nav-item`, which is `display: flex` with the **default `row`** — so every grouped item laid its trigger out **side by side** with its panel. Measured at 900×800, **identically on `index.html` and `graph.html`**: trigger `left 16, width 748, height 366`; panel `left 764, width 120, height 366`. The trigger took the whole group's height because it is a stretched flex item, and the panel was squeezed until its rows wrapped. **Expect this shape on any container that is a column whose children are themselves flex.**

**THE RULE BESIDE IT PROVES THE INTENT, which is how this was diagnosable at all.** `.site-nav-drawer .site-nav-panel { padding-left: 14px; border-left }` is meaningless unless the panel sits **below** its trigger. The author wrote the styling for a column and forgot the one declaration that makes it one.

**THE FIX IS ONE LINE** — `.site-nav-drawer .site-nav-item-has-panel { flex-direction: column; }` — and it goes in **`shared.css`, not `graph.css`.** Measuring `index.html` alongside `graph.html` is what made that obvious: two pages with byte-identical numbers are a shared defect, and scoping the fix to the page it was noticed on would have left eleven pages broken and added a fourth header class to explain.

**A 20px `--radius-pill` IS A CHIP RADIUS AND NOT A MENU-ROW RADIUS.** The drawer now uses `--radius-sm` (12px) and `padding: 10px 14px`, matching `.site-nav-row` one level down. A 20px radius on a 388px-wide element reads as a capsule, which is what 26 stacked capsules looked like.

**`max-width: 420px` IS INERT BELOW 420px, WHICH IS WHY IT IS SAFE.** A phone is unchanged by it; a 900px tablet stops stretching every row to the full viewport. It is left-anchored on purpose — it hangs from the left edge under the hamburger that opened it — and the existing `box-shadow` separates the capped block from the page, so `border-bottom` does not have to reach the viewport edge.

**A NON-SCROLLING BODY IS THE SECOND-HALF OF THIS, AND §3.N's PAGE IS THE SECOND PAGE THAT HAS ONE.** `body.graph-body` is `height: 100vh; overflow: hidden`, and `overflow` on the body propagates to the viewport, so **neither the page nor the drawer could scroll**: 1086px of drawer opening at y=55 in an 800px window, with **3 rows below the fold and no way to reach them**. `shared.css:1516` gave `max-height`/`overflow-y` to `.header-sort` on the stated grounds that sorting "is the one page whose body cannot scroll" — true when written, false now. The graph rule lives in **`graph.css` under `.graph-header`** and not by widening that shared selector, because **`.header-3d` is shared with `model3d.html`, which has not been measured for this.** Measured after: 720px tall, `scrollable: true`, and 「3D 模型」 confirmed `reachable: true` after scrolling to the bottom at 390×844.

**A FORCED-DARK SUBTREE CAN BE INCOMPLETE IN ONE TOKEN.** §3.N forces `--btn-*`, `--bg-card` and `--text-primary` on `.graph-header`. `--hairline` and `--hairline-strong` are both derived from **`--hairline-rgb`**, so light theme's `15, 23, 48` was drawing a **dark hairline on the `#161e38` drawer** — and the rule it killed, `.site-nav-drawer .site-nav-panel { border-left }`, exists for exactly one purpose. **Overriding the derived value's INPUT fixes every consumer at once; overriding each consumer is how the list grows without anyone noticing which are missing.**

**WHAT IS GUARDED: NOTHING.** `check_nav_pages.mjs` asserts the drawer's **markup** (`<div class="site-nav-drawer" data-nav-drawer hidden>`) and not its **layout**, so a drawer that renders a 748 × 366 pill passes every check in the suite. **This is the second unguarded header rule in a row (§3.N), and both are the same gap: nothing in the suite reads a header's geometry.** The measurements above are all from hand-driven CDP.

**AND THEN THE ACCORDION, WHICH REMOVES THE PROBLEM INSTEAD OF CONTAINING IT.** Scrolling to reach a menu's last row is a workaround for a menu that is too tall, and the drawer was 1130px because **all twenty sub-items were open at once**. The rule that forced that shipped with its own condition attached — *"the nav is short enough (4 items, 8 rows) that showing everything beats a broken accordion"* — and **the condition stopped being true when NAV grew to 6 items and 25 rows, while the rule stayed.** A justification is a claim about the present, not a decision recorded once.

`navItemHtml` already rendered `<div class="site-nav-panel" hidden>` and `aria-expanded="false"`, so the collapsed state was correct before any script ran; the CSS was the only thing overriding it. Deleting `.site-nav-drawer .site-nav-panel[hidden] { display: block }` and handing drawer groups to `initMobileNav()` makes it an accordion. Measured at 900×620: **1130px → 331px collapsed**, and every state fits without scrolling — collapse 331, one group 481, two groups 540.

**`initNavDropdowns()` MUST SKIP DRAWER ITEMS, or the accordion inverts itself on a touch device.** A tap synthesises `mouseenter` **before** `click`, so the hover handler opened the panel and the click handler then read `panel.hidden` as true and closed it again — one tap, no visible result. And a touch device has no hover at all, so on the one surface where the drawer is actually used, every mechanism except `click` was dead weight. The skip is by `closest('.site-nav-drawer')` rather than by a `.site-nav .site-nav-item-has-panel` selector, because a page that ever mounted the drawer without the desktop row would then get no handler at all, and fail silently.

**GROUPS TOGGLE INDEPENDENTLY, NOT ONE AT A TIME.** A classic accordion closes its siblings, which is right for a settings panel and wrong for navigation: a reader comparing 「色彩生成器」 against 「探索色盤」 wants both open, and a menu that closes the section you are reading reads as a mistake. The height stays bounded anyway — the drawer's `max-height` + `overflow-y` stays as the safety net for someone who opens all four.

**EXPECT THIS SHAPE ANYWHERE A COMMENT CITES A NUMBER AS ITS REASON.** 「8 rows」 was true when written and nobody revisited it, because the rule it justified worked — visibly, correctly, and a third too tall.

## P. maze.html Had No Checker, And Its Patrol Had Never Once Drawn A Path

**THE PAGE HAD ZERO COVERAGE.** Nothing in the manifest mentioned the string `maze` — 51 entries, four pathfinding algorithms, two terrain modes and a four-leg patrol, and `rg maze scripts/` returned only files that happened to list `maze.html` among twenty other pages. This is §3.G4's shape with a longer tail: the sorting page got its checker when six blank canvases shipped, and maze.html waited because nobody was looking at it.

**THREE DEFECTS, AND ONLY ONE OF THEM WAS VISIBLE.** The user reported the patrol's start and goal markers as looking wrong. Reading `maze.html` turned up two more behind it:

1. **THE MARKERS DESCRIBED A RUN THE PAGE WAS NOT DOING.** `drawMarkers()` called `endpoints()` unconditionally and never `starPoints()`. In wall mode that is a single S/G pair, which happens to sit on legs **A's and B's goals** — so the shared start and legs C and D were unmarked. In terrain mode it was worse: `endpoints()` targets the corners of the **passable bounding box**, while `starPoints()` targets the **literal** corners. Different targets, so S/G routinely sat on cells belonging to no leg at all.
2. **EVERY SUCCESSFUL PATROL THREW.** `starRun` returned `{ legs, found, path }` with **no `cost`**, and `finishSearch` did `result.cost.toFixed(1)`. `undefined.toFixed` is a TypeError, and it fired inside a `requestAnimationFrame` callback — so everything after it was skipped: no hops stat, no run-log row, no status line, `run` never nulled, no path animation. The frame loop then spun on an exhausted generator forever. **The patrol had never drawn a path.**
3. **ONLY THE LAST LEG WAS EVER PAINTED.** Each leg cleared `searchVisited` on all 1,600 cells before it ran, so A, B and C were wiped before D started. The canvas showed one leg while `explored` — never reset — reported four.

### The four legs now interleave

Each leg is an independent generator with its own `visited`/`heap`/`prev`, and **nothing in the module touches a node's `searchVisited`** — that is the caller's, and it is how the caller learns what to paint. - **`legs` is rebuilt in `PATROL_LEGS` order, not completion order.** On a grid whose four corners are all equidistant, completion order already *is* `PATROL_LEGS` order and a completion-ordered result is indistinguishable from a sorted one. ## Q. Terrain Cost Is Rec.709 Luma — And That Is A Decision, Not An Omission

`computeTerrainCost()` is two steps and **no colour space at all**: `alpha < 50 → Infinity`, `luminance = 0.2126R + 0.7152G + 0.0722B`, `cost = 1 + (255 − luminance)/255 · (maxCost − 1)`. Hue and saturation are discarded, so pure colours have a **fixed global order on every sprite**. Measured at `maxCost = 6`:

    白 1.000 · 黃 1.361 · 青 2.063 · 綠 2.424 · 洋紅 4.576 · 紅 4.937 · 藍 5.639 · 黑 6.000

**Blue is the dearest and yellow the cheapest purely because Rec.709 gives green 71.5%, red 21.3% and blue 7.2%.** That is a fact about the *formula*, not about what a reader sees on any particular Pokémon — what the search actually prefers is the brightest region of *that* sprite, which is usually a pale belly or wing rather than anything yellow.

**THE REASON IS AN INVARIANT, NOT COLOUR SCIENCE.** Cost is a strictly monotonic function of the brightness the renderer draws, so a reader can look at the grid and predict where A\* will go. A model that diverges from the visible image breaks that promise **silently** — the page still shows the sprite, the numbers still print, and nothing anywhere says the two have come apart. And luminance-based brightness is itself a perceptual model (Rec.709 is video's Y′), so the invariant and perceptual accuracy do not actually fight here.

**Measured over 33,143,750 pixels from 147 sprites**, passable cells only, cost at `maxCost = 6`:

| model | min | p25 | median | p75 | max |
| :--- | ---: | ---: | ---: | ---: | ---: |
| **Rec.709 luma (shipped)** | 1.000 | 2.219 | **3.148** | 4.144 | 6.000 |
| CIELAB L\* | 1.000 | 2.074 | 2.915 | 3.919 | 6.000 |
| OKLab L | 1.000 | 1.936 | **2.643** | 3.504 | 6.000 |

The three disagree **most in the darks**, which is weakness 1 below.

**THE THREE WEAKNESSES, NAMED SO THEY ARE NOT REDISCOVERED AS BUGS.**

1. **Y′ is luma, not luminance.** It is gamma-encoded and this uses it as though it were linear brightness, which over-weights the dark end. That is the whole of the median gap in the table.
2. **Cost steps are not perceptually uniform.** A 0.1 step between two near-black cells is as big a *number* as a 0.1 step between two near-white cells, but only the second is visible. The landscape over-penalises shade.
3. **Blue is nearly invisible to the weights** — 7.2% against green's 71.5%. A vivid blue and a near-black navy cost almost the same.

**The alternatives, and why each was not taken.**

- **B. OKLab L.** Perceptually uniform, and `rgbToOklab()` **already exists** in `assets/js/color-match.js`, whose docblock names this exact class of decision as the reason one conversion must have one implementation. Best evidence-to-effort ratio of the three. Costs 1,600 conversions per 地形對比度 change, and turns 「what you see is what you pay」 from literal into approximate.
- **C. Slope / elevation.** `cost = 1 + k·max(0, h(next) − h(current))`, descending free. What game AI actually does, and the most interesting pedagogically — 「climbing costs, flat is free」 is a real idea, and A\* would route *around* dark regions rather than through them. **Not a fix but a redesign**: cost becomes a property of a *move* rather than a *place*, 「路徑成本」 changes meaning, and `octileHeuristic`'s admissibility has to be re-proved rather than inherited.
- **D. Local contrast.** Charge only for *change*, so a flat pale wing is free and the map's **structure** is what costs. The largest change of the three.

**What would justify moving off the shipped model** is evidence that a reader cannot predict the route from the image — not 「which model looks nicer」. Rec.709 fails that test in the **darks**, not the light, which is where the interesting paths are.

**NOTHING GUARDS THIS**, and that is correct rather than an oversight: the model is a constant, not a claim with a threshold. What `check_maze_page.mjs` asserts is that `computeTerrainCost` is still the single cost function and that the page reads its alpha threshold from the module.

**THE RULE.** `computeTerrainEndpoints()` took the bounding box of **every passable cell**, then `findNearestPassable` at each corner. On a sprite whose silhouette has a detached fragment — a wing tip, a stray anti-aliased pixel — that corner is the FRAGMENT, not the Pokémon, and start and goal land in different components.

### The fix is SURGICAL, and the blast radius is the reason

The old rule is correct for the overwhelming majority and is what the page has always used, so it is tried **first** and returned untouched whenever the pair it produces is actually connected — gated on `terrainReachable()`, a real connectivity check, not a guess. Measured over 257 sprites:

| | |
| :--- | ---: |
| solvable today | 248 |
| **unsolvable today** | **9 (3.5%)** |
| **unsolvable after** | **0** |
| sprites whose endpoints change at all | **9 — the same 9** |
| movement on those 9 | start p50 **1** cell, max 5 · goal p50 **2**, max 16 |

**248 of 257 keep BYTE-IDENTICAL endpoints and the fallback never runs for them.** The unconditional version was measured too and rejected: it moves endpoints on **19 of 257 (7.4%)**, of which **10 are currently working fine** — p50 2 cells, max 16.

**The fallback is correct BY CONSTRUCTION, not by measurement**: the ring scan is restricted to the body, so both ends land inside it and are connected by definition.

### The patrol takes all five points from the body, unconditionally

Same root cause, and here it is NOT surgical, because the semantic is unambiguous: the patrol's five points are *this Pokémon's centre and its four corners*, and a bbox over stray anti-aliased pixels is not that.

### `largestComponent` is in the module so that all of the above could be RUN

Two things the checker found by writing the fixture wrong:

- **`at(x, y)` must return the SAME OBJECT for the same cell.** `seen` is a `Set`, so membership is by identity — the module's standing rule. A caller that builds a fresh object per call does not get a wrong answer, it gets **an unbounded loop**. The first fixture did exactly that and the checker died with `RangeError: Set maximum size exceeded`.
- **The `isPassable` guard inside the traversal is untestable through maze.html's own neighbourFn**, because `terrainNeighbours` already filters impassable cells out of its own output. The fixture has to supply an UNFILTERED neighbourFn or the guard is never exercised — deleting it left the suite green until that fixture existed.

**EXPECT THIS SHAPE WHENEVER A FIX IS DEFENDED BY A SINGLE NUMBER.** The right question was never "does this change the legs" but "can the leg's target be reached at all", and those two have nothing to do with each other.

## U. A Poll That Cannot Survive The State It Is Polling For

**THE FAILURE WAS A STACK TRACE 70 LINES FROM ITS CAUSE.** `check_sorting_page.mjs`'s finish poll read `!document.querySelector('.al-result').hidden` directly. `.al-result` is created at module scope and appended to the lane grid by `buildRace()` as its **last act** (`sorting.html:685`, after the lane cards at 672), so "the result row is not in the DOM yet" is a legitimate state. ### The cause was invisible because the precondition's result was thrown away

### The fix, and the part that could not be mutation-tested

The read became a named `RESULT_PANEL_STATE` helper reporting `{ shown, present }`, and both `READY` results are now `check()`s rather than discarded. A missing panel and a hidden one are the same answer to the question being asked.

**IT IS A NAMED CONSTANT RATHER THAN AN INLINE EXPRESSION BECAUSE THE GUARD WAS OTHERWISE UNTESTABLE.** Restoring the hard dereference stays green whenever the page behaves, because the bad branch is only reached when the element is MISSING — and that only happens on the flake. So a check renames the element's class inside ONE evaluate, runs the very expression the poll uses, and restores it. Mutating `RESULT_PANEL_STATE` back to `!el.hidden` turns that check red **with a message naming the original bug**, rather than crashing.

**AND THE HARNESS CANNOT CARRY THIS, FOR THE SAME REASON.** Three cases aimed at these guards reported 「the anchor string is stale」 on every run: `makeTree(c.mutate, { strip: true })` **strips the rendered half before mutating**, and all three guards live there. It is not a gap a better case could close — the guard's subject is a condition a harness cannot produce either. The proof is the direct mutation above, and the note in the harness says so rather than leaving three cases that look like coverage.

### What was found on the way, and not fixed here

`buildRace()` has a **detachment window**: `raceGrid.innerHTML = ''` at `sorting.html:663` removes the module-scope `raceResult`, and it is only re-attached at 685. Single-threaded, so nothing *should* observe the gap — but if anything between throws, `raceResult` stays detached **permanently** and every later `buildRace()` retries the same path. That is a candidate for the flake this section is about, and the two new `READY` checks are what will name it: they report the lane count alongside the row's absence, so 「5 lanes, row absent」 and 「6 lanes, row absent」 are distinguishable on the next occurrence.

**Not reproduced:** 3 standalone runs and 1 forced pooled run all passed. The condition is contention-dependent and was not produced on demand.

`graph.html`'s 精選分類 row has nine chips. Pressing 傳說寶可夢 draws a web; pressing 超級進化 draws **93 sprites with no edges between them**, scattered by the repulsion force. Measured over `graph_data.json` with the filter's own predicate:

超極巨化 is still 0 links. The honest relation is `gmax ↔ dynamax` and **there are no Dynamax nodes or Dynamax artwork anywhere under `assets/`** (measured: `find assets -iname '*dynamax*'` → 0), so it needs 32 sprites and two more generators.

## W. The Hamburger Closed Itself In The Same Task It Opened — And `element.click()` Agreed With It

`graph.html`'s collapsed header is the one control on the page whose entire affordance is a button, so "clicking it does not open the bar" is the whole report. It reproduced **5 of 5** with dispatched mouse events at the button's own measured centre and **0 of 5** with `element.click()`.

### A handler destroyed the click's own target

`assets/js/graph-header.js` answers a click on the toggle by rewriting the button's contents:

```js
toggle.innerHTML = iconSvg(open ? 'close' : 'menu');   // line 93
```

That destroys the `<svg><path>` the reader pressed. The event **keeps bubbling** to the document with an `e.target` that is no longer in the tree — measured, `isConnected === false`, `document.contains(e.target) === false` — and the click-outside guard read `header.contains(e.target)`:

```js
if (header.contains(e.target)) return;   // false for a detached node, by definition
```

So an **inside** click read as an **outside** one and the bar closed itself. Measured with a MutationObserver: `158ms [header … is-open] | 158ms [header …]`. Both in one microtask batch — same task.

**THIS IS §3.I INVERTED.** There, a handler rewrites a node and the click hits a **detached** node, which does not bubble, so the click is a silent no-op. Here the click bubbles perfectly and the **membership test silently inverts**. Same class — a question about *which element was hit*, asked of an element that no longer answers — reached from the other direction.

### The harness was the stub, and it was the faithful one

`check_graph_browser.mjs` drives every control with `element.click()`. That **passes** where the real press fails, which is §3.G4's failure mode with the roles reversed: there the fixture was faster than the page, here the fixture is *more faithful* than the page thinks it is. The two paths disagree about whether the same click worked — measured `0 of 5` vs `5 of 5` — and nothing in the suite held both.

`element.click()` dispatches synchronously and the browser re-anchors `e.target` before the document handler runs; a real press goes through the compositor with `mousePressed`/`mouseReleased` and does not. Neither is "wrong"; only one of them is what a reader does.

### The fix asks the question at `pointerdown`

`downAt` already recorded **where** the press started, for the 6px drag threshold. It now also records **whether** it started inside:

```js
downAt = { x, y, inside: header.contains(e.target) };
...
if (downAt && downAt.inside) return;
if (header.contains(e.target)) return;   // still right for a click with no pointerdown
```

Both guards, not one: the live check still matters for keyboard-activated and synthetic clicks, which carry no `pointerdown`. Asking at `pointerdown` is the same reasoning the drag threshold already used — **the press is the fact, the click is a report about a press that has since been acted on.**

`rg "contains\(e\.target\)"` across `assets/js/` returns this one site, so the shape is not elsewhere on the site.

### The guard proves the three close paths survived

A fix that only makes the button open is half a fix — closing the bar by dragging to orbit the camera is the defect §3.N's threshold exists to prevent, and a regression there is invisible to "the button opens". `check_graph_browser.mjs` now dispatches real presses for all of it: 3 open/close rounds plus the nav's computed `visibility`, a canvas click that must close, an 80px orbit drag that must **not**, and Escape. **Reverting the one-line guard fails 8 of those assertions** — verified by reverting and re-running, because a guard nobody has seen fail is a claim rather than a check.

## X. 兩個頁面在手機上，控制欄在主內容之上——而且沒有任何東西量過那個寬度

`cries.html`（叫聲總覽）與 `spectrum.html`（叫聲頻譜）是同一個版型：**控制欄（sticky、自己捲動）｜內容欄**。到了 `≤900px`，兩頁都把它翻成單欄、把控制欄排在**前面**、並且 `position: static`：

- `spectrum.css` 的 900px 區塊 — 同一句理由

`spectrum.html` 的 `IntersectionObserver`（root: `.sp-roster`）會在讀者捲近底部時**每次再加 60 列**，所以圖表不只是遠——越接近它越遠。

**cries.html**：

那 1,609px 的組成：`相似清單` 666px + `警語` 262px + `實測數值` 171px + 三個 `<h3>`、權重晶片與其註 ≈ 510px。永遠可見的部分（圖、名、48px 波形、▶ 播放叫聲、看頻譜）≈ 300px。

### 沒有東西看得見，而且不是巧合

- `check_spectrum_browser.mjs` **刻意把視窗拉寬過 900px 斷點**（它的對象是 `.sp-about` 的兩欄）
- `check_cries_browser.mjs` 是 **`manual: true`**
- 沒有任何一項斷言量過手機寬度

這是 §3.O「guarded by nothing」那一類：規則存在，但沒有任何量測在它生效的條件下執行。

### `<details>` 在這裡不能用，因為它會插入一個盒子

第一版用 `<details class="sp-picker" open>` 配 `summary`，因為它免 JavaScript、鍵盤可用、summary 就是自己的可存取名稱。**它在 `spectrum.html` 上破壞了桌面版**，而且量得很乾淨：

| | 原本 | 改用 `<details>` |
| --- | --- | --- |
| rail 自己捲動？ | **false**（溢出 0） | **true**（溢出 4,829px） |
| `.sp-roster` 盒子 | 503px | 5,347px |
| `.sp-roster` 會捲？ | **true** | **false** |

原因：`<details>` 在 **box tree** 裡多插一層 `::details-content`，所以 `.sp-roster` 的 flex 父層不再是 `.sp-left-panel`，而是一個不會縮到比內容更小的匿名區塊。**先量了四個候選修法**（對 `<details>` 用 `display: contents`、`flex: 1 1 0`、wrapper `overflow: hidden`、兩處 `min-height: 0`），**沒有一個改動那個數字**——是那個數字指出了多出的盒子。

所以 disclosure 改成 `<button aria-expanded>` + `<div hidden>`，桌面版用 `.sp-picker { display: contents }` 復原——**位元組相同**，因為它把 roster 放回原處，成為 rail 的直接 flex item。量測確認三項：rail 1000px、不捲動、roster 503px 且捲動、文件 3,640px，全部與原版一致。

**`cries.html` 用 `<details>` 沒有這個問題，因為 `.cy-panel` 是 block**，不是 flex column。而且它在 markup 裡是 `open`，所以沒有 JavaScript 的讀者拿到的就是今天這頁。**兩個頁面長得像同一個 pattern，其實不是**——這是本次最容易被下一個人弄錯的一件事。

### 手機上捲動的是文件，不是 roster

第一版的 `state.rosterScroll` 存的是 `el('sp-roster').scrollTop`，**永遠是 0**。因為 900px 以下 `spectrum.css` 給 `.sp-roster` `overflow: visible`，沒有高度限制的 flex item 由內容決定大小，於是它 **5,300px 的盒子裝 2,640px 的內容，根本不會捲**；在這個寬度上是**文件**在捲。欄位改成 `state.pickerReturnY`（`window.scrollY`，關閉時寫、開啟時還原）。§3.G 的「捲動位置換了容器，欄位就不能共用」，往外多一層。

### 兩次「量到對的數字、但量錯了量」

**一、`getBoundingClientRect()` 會對收合起來的 `<details>` 裡的後代說謊。** 量到 `rosterH: 2707` 與 `rail: 270` 同時為真——不可能。真相是 `rosterVisible: false` 而 rect 回傳 2,707px：Chrome 跳過 `::details-content` 內的佈局，`getBoundingClientRect()` 回傳**記住的舊尺寸**。正確的機制斷言是 `checkVisibility()`。§3.M 說「斷言算出的盒子，不是屬性，因為屬性會說謊」——**這裡連 rect 都說謊，而 `checkVisibility()` 不會**。

**二、捲到 `.cy-probe-head` 會把寶可夢名稱切出畫面。** 第一版捲到 head，`nearest` 對一個完全在視窗之上的元素是**對齊底部**，於是 head 在 y=−45、**名稱在 y=−31**——讀者看到一個播放鍵，卻讀不到那是誰。「播放鍵在畫面上」這條斷言是綠的，頁面仍然是錯的。改成捲 `.cy-panel`。

**三、捲動位置還原有兩層。** 重新展開時會**再觸發一批 60 列**（rail 5,912px → 8,552px），而 `renderRoster()` 換掉 `innerHTML` 會把位置歸零一次。只在開啟時還原等於什麼都沒做。

### 一個 media query 不能決定一個 attribute

「桌面上開、手機上關」**在樣式表裡根本不可表達**：media query 不能設 `open` 或 `hidden`，CSS 也不能收合。所以 `syncPicker()` / `syncProbeDisclosure()` 在開機與**每次跨過斷點時**套用它。**兩個方向不對稱，而且不對稱本身就是設計**：收合是修好缺陷的那一側；展開是防止更糟的那一側，因為桌面版 toggle 是 `display: none`，被旋轉留下的收合 picker 會**讓整個 rail 消失而沒有任何控制項可以打開它**。

而那個寬度**必須寫兩份**（media query 不能讀 custom property，JS 也不能讀 media query）。因此 `check_cries_page.mjs` 與 `check_spectrum_page.mjs` 都**從樣式表讀出那個數字**，並且要求它是**帶 `.cy-panel` / `.sp-left-panel` 的那一個區塊**——`cries.css` 有四個 900px 區塊，其中兩個（`.cy-more-summary` 與 `.cg-picker`）跟這件事無關。純數字比較會被其中任何一個滿足。

### 自己寫的斷言裡找到的三個洞

**一、半開的區間不是區間。** 第一版的斷言只問「每個 id 在 `<details>` 開頭之後」，於是把 `#probe-stats` 移到 `</details>` **之後**的 mutation 通過了。「在 disclosure 裡面」是關於一個區間的陳述，而區間有兩端。§3.P 的發現，指向我自己的斷言。

**二、順序不是兩個「有沒有」。** 「先收合再捲動」對兩個敘述的**位置**做陳述；把兩者對調後，每一個「是否存在」的版本都滿足。改成比較 index。

**三、`[hidden]` 對上 author `display`。** mutation 刪掉 `.sp-picker[hidden] { display: none }` 時 checker 還是綠的——因為我從來沒斷言那條規則。`.sp-picker` 在 900px 以下自己宣告 `display: block`，**任何 author `display` 都贏過 UA 的 `[hidden]`**。`docs/incidents/page-defects.md#m` 量過三種變體，這是同一個形狀的第四個實例。

### 一個 mutation 刪掉太多東西，看起來像刪對了

`test_check_cries_page.mjs` 裡「把警語移出 served DOM」那一案，原来的 pattern 是 `<div class="cy-caveat">[\s\S]*?</div>\n        </div>`。警語現在在 `<details>` 裡，後面接的是 `</div>\n        </details>`，所以那個 pattern 在那裡**沒有匹配**——而它是非貪婪的，所以它**沒有失敗**，它繼續吃到幾百行之後的下一個 `</div>\n        </div>`，把那個也刪了，連 `#autoplay-slot` 一起。harness 於是對一條完全不同的斷言回報「did not behave」。

錨定到警語自己的收尾標籤（十個空格縮排；內層的 `<dl>` 是十二個）。**§3.P 的發現，指向一個 mutation 而不是一個 checker**：「我刪的比我想的多」和「我刪對了、別的東西剛好抓到它」在報告裡長得一樣。

### 守衛是機制加結果，兩個都要

只斷言結果會被運氣滿足：`#sp-hero` 靠近手機畫面頂端，在一個 roster 剛好只畫 60 列的頁面上也是真的，而那個頁面在 600 列時會再壞一次，且什麼都不說。只斷言機制則會被一個「對的理由做對的事」的頁面滿足——§3.O 的形狀。

`check_cry_mobile_layout.mjs` 兩者都量。**它不是 `manual`，而且不是任何一個既有 browser checker 的一部分**，因為前者只管 `spectrum.html`、後者不執行。**它沒有 mutation harness，這個代價寫在檔頭**：每一案都要對自己的樹開一個 Chrome，四案的錢足以買下整個 `test_check_spectrum_page.mjs`；static 那兩半有 harness，mutation 都在那裡。

### 收尾時 event loop 不會自己空閒

checker 印完 `PASS` 之後坐著不動超過 200 秒，原因是 DevTools 的 WebSocket，加上找到 target 的那個 `fetch`——undici 會把那條 socket 留著做 keep-alive。§4 對 runner 自己的 liveness probe 記過同一個坑，那次它呈現為「skip cache 壞了，一次全快取跑花 6.5 秒做 0.09 秒的工作」。

而且 **kill Chrome 然後立刻 exit 會留下 6 MB 的 profile tree**：`tmp-trees.mjs` 在 `process.exit` 時 sweep，而它的 `sweep()` 用的是沒有 retry 的裸 `rmSync`，所以 sweep 在瀏覽器還活著時刪一個 Chrome 正在寫的目錄會丟 `EBUSY`，被那個模組的 `catch {}` 吞掉。量到的是**每次跑留一個 `crl-*` tree、零個孤兒行程**——`ps` 乾淨而磁碟不乾淨，那是兩者中比較難發現的那個。修法是等行程真的沒了再讓 sweep 跑，而不是寫第二份 retry 策略。
