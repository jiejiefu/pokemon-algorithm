# AGENTS.md — Pokémon Algorithm Visualization Lab

## Project Overview
Static HTML/JS/CSS site (GitHub Pages ready) visualizing algorithms with 1025 Pokémon sprites.
- **index.html** — Landing page: hero + 3 feature cards + full 1025 Pokédex grid (click → detail)
- **sorting.html** — Sorting lab: 6 algorithms (Bubble, Selection, Insertion, Quick, Merge, Heap) with animated Canvas grid
- **maze.html** — Pathfinding: BFS/DFS on pixelated Pokémon sprites (40×40 grid, recursive backtracker)
- **pokedex.html** — Searchable/filterable Pokédex with fuzzy autocomplete, type/color/gen filters
- **detail.html** — Pokémon detail page (slug or id query): sprites, multilingual names, RGB color badge, stats radar, type effectiveness, evolution, **moves (4 real tabs)**, descriptions
- **404.html** — GitHub Pages fallback: rewrites `/detail/<slug>` to `detail.html?slug=...&from404=1`

## Critical Runtime Requirement
**Must serve via HTTP server** — `file://` fails due to CORS on `fetch('pokemon_data.json')` and image loads.
- VS Code: "Live Server" extension (right-click index.html → Open with Live Server)
- CLI: `npx serve` / `python -m http.server` / `php -S localhost:8000`

## Key Technical Patterns
- **Generator-based animation**: `sorting-algorithms.js` exports `function* algoSteps(arr)` yielding per frame; `sorting.html` drives via `requestAnimationFrame` calling `.next()`
- **Lerp smoothing**: `PokemonNode.update()` interpolates `x/y → targetX/targetY` at 0.15 speed
- **Canvas grid**: 40 cols × 26 rows (1025 Pokémon), 28px padding
- **Color**: Official PokeAPI color (green/blue/red/yellow/purple/pink/brown/black/white/gray) — replaces computed `color_group`
- **RGB card glow**: `createPokemonCard()` sets `--card-accent-rgb` from `pokemon.rgb`; `shared.css` renders a neutral drop shadow plus a two-layer RGB glow (14px @ 0.55, 40px @ 0.35) on `.card:hover`
- **Slug routing**: `pokemonSlug()` normalizes `names.en`; `pokemonDetailUrl()` returns the Live-Server-safe `detail.html?slug=<slug>`, `pokemonDetailPath()` returns the clean `detail/<slug>` used only for `history.replaceState`
- **Radar chart**: Canvas-based stats visualization in detail page
- **Type effectiveness**: Computed client-side from dual-type combination
- **Move tabs**: `renderMoveSection()` in `shared.js` emits a real `tablist` (WAI-ARIA tabs with roving tabindex, Arrow/Home/End). `detail.html`'s `renderMoves()` gates both fetches behind an `IntersectionObserver` (`rootMargin: 400px`), since learnsets.json is 4.3 MB raw (223 KB gzipped, against 614 KB for the pokemon_data.json every page already loads); both loaders cache on `window` like `loadEvolutionChain()`
- **ES Modules**: All JS uses `type="module"` with relative imports from `assets/js/shared.js`. `pokemon-lexicon.js` imports `shared.js`, so `shared.js` cannot import it back — the `MOVE_*` label maps live in `shared.js` and are re-exported from `pokemon-lexicon.js`
- **Fuzzy search**: `<input list="pokemon-suggestions">` with `<datalist>` populated from all names (id, zh, en, ja)

## Gotchas
1. **No build step** — edit HTML/JS directly; changes reflect on reload
2. **1025 images + JSON** — initial load ~200 MB; first paint shows "載入進度" counter
3. **Generator exhaustion**: `sortGenerator = null` resets; `yield` frequency controls animation speed (insertion sort yields every 5 inserts)
4. **GitHub Pages**: Ensure repo settings → Pages → Source: "Deploy from branch" / root folder
5. **Asset paths**: All HTML files reference `assets/images/pokemon/`, `assets/js/shared.js`, `assets/data/pokemon_data.json`
6. **Virtualenv required**: Python scripts need `.venv` with pandas, openpyxl, httpx, lxml, beautifulsoup4. The interpreter used for this repo is `../.venv/bin/python` (i.e. `Visual_Studio_Code/.venv`), not a project-local `.venv`
7. **Chinese descriptions**: 1025/1025 have text1 (primary), 1025/1025 have text2 (secondary) from tw.portal-pokemon.com. Scraper handles both single-escaped and double-escaped Next.js streaming formats.
8. **Detail page URL**: `detail.html?slug=bulbasaur` is the internal link format (works on Live Server, `python -m http.server`, and GitHub Pages). The legacy `detail.html?id=25` form still works. Clean URLs (`/detail/bulbasaur`) are only resolvable on GitHub Pages, where `404.html` redirects to `?slug=...&from404=1` and `detail.html` restores the clean path with `history.replaceState`. VS Code Live Server returns `Cannot GET /detail/bulbasaur` for direct clean-URL visits — always navigate via the `?slug=` form during local development.
9. **text2 fallback**: If tw.portal-pokemon.com doesn't have text2, it's left empty (no wiki.52poke.com fallback)
10. **No color badge on cards**: `createPokemonCard()` renders types only; the color is expressed solely through the RGB hover glow. The color swatch exists only on the detail page (`.color-badge`). Its fill comes from `pokemon.rgb`, but the detail page does **not** use `getReadableTextColor()` for it: mid-tone Pokémon colours leave neither white nor near-black text at 4.5:1 (Charizard's `rgb(154,138,108)` managed only 3.37:1). `badgeStyle()` in `detail.html` instead picks whichever of white / `rgb(20,17,10)` scores higher, then scales the fill towards black or white in 2% steps only until that text clears 4.5:1, so the swatch still reads as the Pokémon's colour. 976 of 1025 need no adjustment; the worst case lands exactly on 4.50:1 (Steelix). Re-run the contrast probe before changing it — `shared.js`'s `getReadableTextColor()` is a plain luminance pick with no AA guarantee.
11. **Type chart source of truth**: `assets/js/type-chart.js` is generated from the 52poke 屬性相剋表 「第六世代起／正常對戰」 grid and is the *only* sanctioned chart — never hand-write matchups and never copy them from PokeAPI. PokeAPI's per-type `damage_relations` are one-sided: merging `*_damage_from` and `*_damage_to` across all 18 types still leaves most of the 324 cells unspecified, and because the directions never overlap it reports no conflicts, so the gap is silent (`/api/v2/type/normal` has no `half_damage_from`; `psychic` mis-assigns rows). Pokémon Showdown's `data/typechart.ts` on master is a modded chart (carries a `prankster` ability key and a Stellar row). Regenerate with `python scripts/extract_type_chart.py`, which pins all 120 non-neutral cells against a hand-written reference profile and cross-checks every cell's text against its CSS class. Revalidate runtime behaviour with `node scripts/check_type_chart.mjs`.
12. **Dual types multiply, never union**: `typeEffectiveness()` multiplies the two defender rows so 2×½=1× drops out and 2×2=4× / ½×½=¼× emerge. An earlier hand-written version unioned the two types' weakness lists and then ran an inverted dedup pass, which reported Water and Ground as 2× weaknesses for a Fire/Flying Pokémon and surfaced no immunities at all.
13. **The detail page is a single scroll, with one exception**: every section renders at once (hero → facts → stats → type effectiveness → evolution → moves → descriptions → prev/next), so it is printable and linkable. The exception is the moves section, which is four real tabs (等級提升 / 招式學習器 / 遺傳招式 / 傳授招式) to match InfoPoke. Because only the selected panel is in the DOM, the other three are neither printable nor findable with Ctrl+F, so `detail.css` reveals every panel under `@media print` and labels each with `content: attr(data-move-tab-label)` — the attribute is not decoration, removing it silently breaks the print output. All other sections carry `aria-labelledby` pointing at their heading id; decorative icons are inline `<svg aria-hidden="true" focusable="false">`.
14. **The radar canvas is sized from its rendered box**: `drawRadarChart()` reads `clientWidth` and multiplies by `devicePixelRatio` for the backing store, because the canvas is fluid in CSS (`max-width: 320px`, `aspect-ratio: 1`). Setting only the `width`/`height` attributes would render at 1× on retina. It is redrawn on a debounced `resize`. It also shares `STAT_MAX` (255) with the bars so the two views agree — an earlier `/200` scale made strong Pokémon read as a flat hexagon.
15. **`renderEvolutionChain()` assigns `innerHTML` unconditionally**: 505 of the 541 chains in `evolution_chains.json` carry no `variants` key, so an assignment that lived inside the variants branch left the evolution section blank for 93% of Pokémon. Its CSS lives in `detail.css` under "Evolution chain" — that markup is emitted by `shared.js`, so deleting the old inline `<style>` block in `detail.html` silently unstyled it.
16. **Genus translations are scraped, not vendored**: `assets/js/genus-zh.js` is generated from `https://wiki.52poke.com/zh-hant/分类` (1051 rows → 734 genus, 715/715 covered), so regenerating needs network and is deliberately **not** byte-idempotent — upstream edits show up as a diff. That is the point: switching from the old checked-in dump already picked up two corrections (`Ghost Flame Pokémon` 磷火→鬼火, `Hexpert Pokémon` 咒術師→詛咒師), neither of which any of our 1025 Pokémon uses. The `zh-hant` page must be fetched **by URL**: `api.php?action=parse` returns the default *simplified* variant (`全国编号`), so the `全國編號` header marker never matches. `api.php` also rejects the full URL as a title — it normalizes to `Https://…` and reports the page missing — so `PAGE_TITLE` stays a bare `分类` for the revision lookup. Provenance is recorded in `GENUS_SOURCE` alongside the chart's `TYPE_CHART_SOURCE`.
17. **Hero carries 繁體, the badge row carries 簡體**: `NAMES` in `detail.html` has no `zh` entry because the hero `<h1>` is already `names.zh`. It does *not* filter out a simplified name that happens to equal the traditional one — 359 of 1025 are character-for-character identical (妙蛙草, 巴大蝶, 波波) and hiding those made the badge row a different length per page, which read as a bug. All 1025 records carry all 9 `names` keys, so every page now renders exactly 8 badges.
18. **The learnsets are an all-generation union, and each method has one right answer**: `fetch_moves.py` unions every version group, so the counts are far larger than InfoPoke's, which only ever loaded one generation (Bulbasaur is 16/68/19/22 for us vs 12/60/8/6 there). Level-up takes the *lowest* level any game offered, never the latest game's. The four methods are independent and overlap freely — a move reachable three ways appears three times, and the sections must not dedupe across them. 459 of 1025 have no egg moves and 138 no tutor moves, so the empty state is normal, not a bug.
19. **A machine code is not a number**: rows are `[moveId, code, generation]` with codes like `TM01`/`TR09`/`HM06`, and the prefix is load-bearing. PokeAPI ships 8 HMs (`hm01`–`hm08`), 230 TMs (`tm00`–`tm229`, three digits from Gen 9) and 100 TRs (`tr00`–`tr99`) — the TR range overlaps the TM range completely, so storing `9` instead of `TR09` renders one as the other. Bulbasaur has both a real `TM17` and a `TR17`. The number also has no single correct value per move, since a code is reused across games: Bulbasaur has two moves coded `TM01` and three coded `TM31`, each from a different generation. `moveTableHtml()` therefore flags only the codes reused *within the rendered table* with a `†` and puts the source generation in a tooltip.
20. **The two `typeBadge` helpers differ on purpose**: `.type-badge` is defined only in `detail.css` (a 14px hero pill), and the pokedex cards have no rule for it outside the detail page, so their 10px size is inline. `typeBadgeHtml()` is therefore the CSS-sized hero pill and `typeBadgeSmHtml()` the self-contained compact one used by cards and the move tables — using the wrong one silently resizes the cards. Both capitalise the slug first, because PokeAPI returns `normal` while `TYPE_EN_ZH`/`TYPE_COLORS` are keyed `Normal`.
21. **Move rows come in two shapes**: level rows are `[moveId, level]` and machine rows are `[moveId, code, generation]`, but egg and tutor are a *flat list of bare move ids* (`[13, 80, 92]`), because "inherited from a parent that knew it" is the whole fact PokeAPI offers. `moveTableHtml()` normalises with `Array.isArray(row) ? row : [row]`; indexing `row[0]` without that check renders an entire egg list as a single row.
